# 跨產品資料不重複與網路時序防護實作手冊

> 文件用途：提供 SpeechMessageProducts Solution 目前與未來所有產品的共同、強制性實作規範。
>
> 適用產品：ChurchReport、採購協會、建設公司，以及日後新增的網站、API、報表、匯出、背景工作與測試工具。
>
> 核心目標：即使使用者位於高延遲 Wi-Fi、經過透明代理或防火牆、遭遇 HTTP 重送、回應亂序、瀏覽器重複初始化或多節點部署，系統仍不得把同一筆權威資料顯示成兩列，也不得造成 Session Leakage、Memory Leakage 或其他 Resource Leakage。

> 繼承規則：本手冊是 Solution 層級契約。任何日後新增的採購協會、建設公司、教育、醫療、會員、報表、API、工作者、整合服務或測試工具，都必須在建立第一個資料集合與第一個 UI 之前採用本手冊；不得因產品名稱、資料庫、租戶數、部署方式、UI 框架、是否使用 Wi-Fi 或是否經過防火牆而豁免。

> 狀態：這是待執行的程式修改手冊，不代表程式已完成修正。現場根因仍未證實；本手冊以可重現的故障模型建立防線，不以猜測防火牆型號為前提。文件中的流程示意不代表專案已存在同名函式。

> 規格依據：根目錄 `AGENTS.md` 與 `.trellis/spec/backend/duplicate-row-publication-contract.md`。兩者的跨使用者隔離、發布與生命週期要求持續有效。

**實作目標：** 先完成 ChurchReport 初始週報的端到端防護，再以共用契約、框架 adapter 與 CI 測試套件約束未來每個產品。

**現有技術：** ASP.NET Core／.NET 10、Razor、DevExtreme、jQuery、Dataverse、xUnit。未來產品可更換技術，不可取消身份、隔離、原子發布、冪等呈現與資源上限。

**執行方式：** 每一階段先建立會失敗的測試，再修改最小範圍程式，確認通過並做隔離／生命週期審查。此文件不授權自動部署或修改教會設備。

## 0. Solution 層級適用與新產品接入規則

本節是所有未來產品的強制入口。新增產品時，負責人必須在開始撰寫程式前完成下列事項：

1. 閱讀本手冊全文與根目錄 `AGENTS.md`。
2. 建立產品資料流清冊，列出每個 API、頁面、Grid、表格、樹、報表、匯出、cache projection 與背景結果。
3. 為每個 repeatable row 指定資料庫唯一 ID，並記錄資料表／實體、唯一鍵欄位與生命週期；前端不得自行猜測身份。
4. 指定產品的 snapshot owner、scope key、single-flight boundary、cache lifetime 與 resource owner。
5. 先建立「同名不同 ID」、「相同 ID 重複」、「慢回應晚到」、「重複請求」與「caller mutation」測試，再開始實作資料載入。
6. 將產品的驗收證據放入產品自己的測試專案或 `docs` 證據目錄，並在發布審查中引用本手冊的章節。

產品若採用新的 UI 框架、API 協定、背景佇列、分散式 cache 或資料來源，仍必須實作本手冊的相同不變條件；可以更換工具，不可以降低契約。

### 0.1 絕對不得以產品邊界繞過規則

以下理由都不是豁免條件：

- 「這個產品目前只有一間教會使用」。
- 「這個產品沒有遇到過重複資料」。
- 「這個頁面只是一個簡單報表」。
- 「這個資料來源沒有使用 Dataverse」。
- 「這個產品只使用 5G，不會走教會 Wi-Fi」。
- 「這個 Grid 由第三方元件負責渲染」。
- 「只要前端把同名資料隱藏即可」。
- 「單程序 lock 已經足夠」。

所有產品必須在應用層假設網路可能重送、回應可能亂序、請求可能跨節點，並自行保護資料身份、發布原子性、UI 世代與資源生命週期。

### 0.2 新產品完成定義

新產品只有在下列條件全部成立時，才算完成資料呈現功能：

- 伺服器端 stable identity 已定義且有測試。
- 每個實際 UI consumer collection 都有發布前驗證。
- API 回應與背景結果都是 detached snapshot 或 immutable value。
- 非同步前端 loader 有 single-flight 與世代／token 檢查；abort 只是減少不必要工作，不得單獨當作舊回應隔離。純伺服器渲染頁面則在送出 HTML 前驗證資料，不需強制引入 AJAX。
- 所有會改變業務狀態的 POST、PUT、PATCH、DELETE 與背景作業都有適用的冪等／重送策略；不因使用某個 HTTP method 就推定任意業務副作用安全。
- Session、cache、task、timer、connection、stream、subscription 的 owner 與 cleanup 已文件化並測試。
- 慢網路、重複請求、晚到回應與多節點情境已在供應商端自動化模擬通過。
- 任何已知重複列、Session Leakage、Memory Leakage 或 Resource Leakage 都已修正；不得以現場無法重現作為接受理由。

### 0.3 共用核心與產品 adapter 的責任

不要把教會特定欄位搬入所有產品。以以下四個責任拆分；元件名稱為建議新增名稱，不是已存在的 API：

| 元件責任 | 共用契約 | 產品必須提供 |
|---|---|---|
| `RowPublicationGuard` | 驗列非空、身份正規化、集合內唯一、筆數上限；不保留跨請求資料 | key selector、key comparer、consumer 名稱與容量 |
| `PublicationScope`／snapshot boundary | 接受伺服器驗證的完整 scope，只交付完整 detached／immutable 結果 | subject、tenant、product、authorization epoch、business scope、version |
| `CollectionLoadCoordinator` | 世代、單一 owner、過期回應拒絕、有界 refresh、dispose | fetch／XHR／框架 transport 與 Grid／表格 render adapter |
| `PublicationContractTests` | 可重用故障資料、排程控制與共同斷言 | 產品 endpoint、identity、測試身份與 UI adapter |

共用 guard 應是無狀態函式或不含使用者狀態的服務；不得在 static／singleton 保存 Session、上次回應、身份或 request。scope 與 snapshot 的 owner 是目前操作或有明確隔離與上限的 holder。共用前端程式可以全站載入一次，但各元件狀態不能放在一份跨帳號共用的全域陣列。

建議先在 ChurchReport 內以這些責任分檔，完成第一個切片的測試後，再抽出不依賴 ChurchReport／CRM Entity 的共用套件；本手冊不要求一次替換整個 Solution 的框架或資料層。

### 0.4 不同產品的身份範例

| 消費集合 | 正確身份 | 不可替代的顯示欄位 |
|---|---|---|
| 教會某週報的出席列 | 權威 `PresentRecordId` | 會友姓名 |
| 採購單明細 | 採購單明細 ID；同品項分批／不同價格仍可有不同明細 | 品名、料號或排序位置 |
| 建設公司工程里程碑 | 專案範圍內的里程碑／驗收事件 ID | 工程名稱或日期文字 |
| 會員清單 | 權威會員 ID／ContactId | 姓名、電話 |
| 樹狀關係 | 資料庫 parent-child 關係記錄的唯一 ID，或資料庫正式定義的複合唯一鍵 | 子節點名稱 |

不要用「相同文字」判定重複；要先定義一列代表一個實體、明細、關係或事件，再決定身份。

### 0.5 新產品接入清冊與 CI 門禁

實作時新增版本控制下的 `docs/publication-contracts.json` 作為接入清冊。以下是 ChurchReport 第一個 consumer 的格式範例；路徑用 Solution 相對路徑方便不同機器執行，其他產品逐項新增，不覆蓋既有項目：

```json
{
  "schemaVersion": 1,
  "consumers": [
    {
      "product": "ChurchReport",
      "consumer": "WeeklyReport.SmallGroup",
      "endpoint": "GET /SmallGroup/LoadIntegrate",
      "view": "SpeechMessageProducts.ChurchReport/Views/Home/_GeneralGroupGrids.cshtml",
      "identity": "PresentRecordId",
      "identityKind": "persisted-guid",
      "scopeFields": ["product", "subject", "tenant", "authorizationEpoch", "list", "report", "date"],
      "publicationMode": "snapshot-replace",
      "adapter": "DevExtreme",
      "maxRows": 10000,
      "overflowBehavior": "reject-with-explicit-error",
      "contractTestSuite": "WeeklyReportPublicationContractTests"
    }
  ]
}
```

`10000` 是第一個完整快照的建議安全上限，不是現況統計；超量必須明確拒絕並採有版本的分頁方案，不能靜默截斷。每個產品可依實際業務量設定不同上限，測試必須涵蓋邊界與超限。

CI 必須依序：

1. 由建置中的 MVC endpoint metadata、頁面註冊／路由與 framework adapter 清冊核對集合 consumer。以靜態搜尋輔助，不能只靠搜尋 `.DataGrid` 判定所有頁面已涵蓋。
2. 發現新 consumer 未登記時失敗；排除項目只限確實沒有集合的端點，需具體理由，不允許以「新產品」豁免。
3. 對每個 consumer 呼叫相同的契約測試入口；驗證測試確實有執行數量，不能只有測試類別名稱存在。
4. 核對所支援的 adapter／部署模式都有對應測試，測試跳過、缺套件、缺啟動條件不得當成通過。
5. 輸出 product、consumer、版本、測試數量與失敗原因；任一 identity／isolation／lifecycle 契約失敗即阻擋發布。

新增產品不能只有照抄這份 Markdown；必須登記清冊、接入共用元件或等價 adapter，並實際執行測試。共用元件改版時，所有已接入產品需重新驗證，避免一次共用修改造成多產品回歸。

## 1. 先理解本問題：不要把「網路重送」誤當成「資料可以重複」

教會 Wi-Fi、防火牆、TLS 深度檢查、透明代理與負載平衡器，都可能造成下列現象：

1. HTTP 請求延遲變長。
2. TCP 連線被重置或重新建立。
3. GET 請求被代理重試。
4. 不同請求被導向不同後端節點。
5. 瀏覽器先收到舊世代回應，後收到新世代回應。
6. 使用者在頁面尚未完成時再次觸發載入。

這些因素只能解釋「為什麼同一流程可能執行多次」，不能成為顯示重複資料的理由。應用程式必須假設：

> 每一個 GET、POST、refresh、reload、callback 與背景工作都可能被延遲、重送、重入或亂序完成。

因此，修正方向必須放在應用程式本身，而不是要求供應商到每一間教會調整防火牆。

### 1.1 本案已知事實與假設界線

- 使用者確認：在尚未按任何按鈕、剛開啟週報時，偶發出現兩筆會友資料。
- 使用者確認：後台同一出席事件只有一筆出席記錄；不得再以兩筆不同 `PresentRecordId` 的 CRM 資料作為本案既定根因。
- 使用者觀察：教會 Wi-Fi 較容易發生，5G 較少；這是相關性，不是防火牆有問題的證據。
- 現行 `ListManager` 已有 instance gate、候選驗證及 detached read；目前 key 驗證位於候選建立時，不能因此推定所有後續修改與所有輸出端點都已受保護。
- 目前沒有證據證明 DevExtreme 會把重試回應自動追加成兩列。必須在本地測試中驗證實際 adapter、版本與渲染行為。
- 初始開啟流程是第一階段修正範圍；上傳、日期切換與背景作業列為其他入口的後續防護，不冒充初始開啟重複的已確認原因。
- 一般 TCP 重傳不等於 HTTP handler 再執行一次；HTTP 代理重試與前端 callback 重入要分別模擬。

### 1.2 能保證的安全契約與不能承諾的事情

目標是對明確故障模型維持「不發布重複集合、不採用過期回應、不跨身份呈現、不無界保留資源」。正常資料必須完整顯示；有衝突才安全拒絕。把所有請求都擋掉不算完成。

本手冊不承諾在永久斷線時仍能取得最新資料，也不能抵禦具有受信解密能力且蓄意修改 HTML／JavaScript 的中介設備。驗收通過代表已測故障模型符合契約，不是對所有未知程式缺陷作無限保證。

## 2. 永久不變的發布契約

所有產品、所有資料集合與所有 UI 元件都必須遵守以下規則。

### 2.1 穩定列身份

**最高優先原則：一列是否為同一筆資料，只能依據資料庫／權威資料來源的唯一 ID 判斷；不得依據欄位內容判斷。**

例如兩筆資料即使 `FullName`、`Phone`、`Address`、`Status`、日期與所有顯示欄位都完全相同，只要權威唯一 ID 不同，就必須視為兩筆不同資料並完整保留。反過來，同一個唯一 ID 即使姓名或其他內容後來改變，仍然是同一列資料；不得因內容變化而建立第二列。

「資料內容相同」只能作為診斷線索，不能作為刪除、合併、覆蓋或隱藏的條件。任何以內容猜測身份的做法，都必須在 code review 中視為阻擋問題。

每一列正式資料必須攜帶資料庫實際保存、且由伺服器讀取並驗證的唯一身份，例如：

- Dataverse entity ID。
- ContactId（當列本身代表 Contact 時）。
- 採購單明細、工程驗收記錄或其他業務資料表的唯一 ID。
- 資料庫正式定義並施加唯一約束的複合主鍵／唯一鍵；不可自行拼接內容欄位當作等價身份。

驗證必須限定在同一個邏輯消費集合，不能跨所有產品或所有畫面做全域去重。同一會員可以合法出現在兩個不同報表。樹狀圖若允許同一實體出現在不同父節點，應使用資料庫關係記錄的唯一 ID；沒有關係 ID 時需先釐清資料模型，不能臨時附加隨機數來掩蓋重複。

跨資料庫／租戶來源的數字主鍵可能重複，必須先以伺服器驗證的來源命名空間區隔，再比較各自真正的資料庫 ID；這是隔離邊界，不是按顯示內容另造身份。統計報表的合法聚合也不可當成資料去重：先明確定義報表列與其權威唯一鍵，不能用 `GroupBy(FullName)` 隱藏底層記錄。

若身份是 GUID，驗證器應使用 `Guid.TryParse` 後比較 GUID 值，並以同一格式輸出前後端 key。字串型身份則依權威系統定義大小寫與正規化規則，不得通用地轉小寫或修剪到不同身份碰撞。資料版本不是身份：更新內容不能任意換 row key。

禁止使用下列項目作為列身份：

- 姓名。
- 電話。
- 顯示文字。
- 陣列索引。
- 日期時間字串。
- `counter.ToString()`。
- `DateTime.Now.ToLongTimeString()`。
- 使用者傳入的 index 或 key。

同名但不同穩定身份的合法資料必須全部保留；絕不可以用姓名 `Distinct`、`GroupBy` 或字典覆蓋來掩蓋問題。

### 2.1.1 唯一 ID、列鍵與操作鍵必須分離

下列三種識別碼用途不同，不得混用：

| 識別碼 | 代表什麼 | 生命週期與使用方式 |
|---|---|---|
| 權威唯一 ID | 資料庫／Dataverse 的實體或業務事件本身 | 決定兩列是否為同一筆；UI row key、API 驗證與資料更新都以此為準 |
| UI row key | 傳給 Grid／表格的列鍵 | 必須等於或無歧義地衍生自權威唯一 ID；不能用姓名或索引 |
| operation／idempotency key | 一次使用者意圖或外部副作用的重送識別 | 防止同一次 POST／背景作業重做；不能取代資料列唯一 ID，也不能拿來把兩筆資料合成一筆 |

`UI row key` 的「衍生」僅允許唯一 ID 的無損表示，例如 GUID 統一格式、資料庫正式複合主鍵的無歧義序列化，或加上已驗證來源命名空間；不能使用內容 hash、時間、亂數或自行推定的業務相似度。

不要用每次請求新產生的 `Guid.NewGuid()` 當資料列唯一 ID；也不要把 operation key 寫入 `PresentRecordId`、`ContactId` 或其他權威欄位。測試必須各自驗證這三種 key 的碰撞、重播與生命週期。

### 2.1.2 重複 ID 的處理方式

- 同一消費集合出現相同權威唯一 ID：視為資料組裝、查詢或發布衝突，拒絕該集合發布，保留診斷證據，交由修正流程處理。
- 不得自動取第一筆、最後一筆、較新內容、較完整內容或依姓名排序後取一筆。
- 不得在錯誤頁面將第二筆隱藏後回報成功；使用者應看到安全的載入失敗／資料衝突訊息。
- 只有在權威資料來源已明確定義「同一事件的版本」且由 server-side version contract 決定取代關係時，才可做版本替換；那不是依內容去重，也不是任意選一筆。
- 若兩個不同 consumer 都合法呈現同一權威 ID，不能因跨頁面或跨報表看到同名／同 ID 就全域刪除；唯一性檢查的範圍是該 consumer 的邏輯集合。

### 2.2 發布前驗證

在資料交給 Razor、JSON serializer、DataSourceLoader、DevExtreme、報表或匯出器之前，必須在「實際消費該集合的邊界」驗證：

- 列不可為 null。
- 穩定列身份不可空白。
- 同一消費集合中不可出現相同的非空穩定身份。
- 目前使用者、租戶、組織、權限、清單、報表、日期與認證世代必須一致。
- 驗證失敗時 fail closed：拒絕發布，記錄不含敏感資料的診斷資訊。只在完整 scope 與授權仍有效時，才可保留上一份完整快照並標示更新失敗；登出、換帳號、換租戶、換日期或失去權限時必須立即清除舊畫面，不得用舊身份資料當 fallback。

驗證器不得刪除資料來讓畫面「看起來正確」。刪除或合併合法資料會造成資料遺失，並且會掩蓋真正的資料組裝錯誤。

### 2.3 原子發布

資料載入必須分成兩個階段：

```text
建立 operation-local candidate
    ↓
I/O、授權、scope、映射、排序、穩定 ID 驗證全部成功
    ↓
一次性發布完整 snapshot
    ↓
讀取端只取得 detached copy
```

禁止在共享 Session、singleton、cache 或 ListManager 集合中逐筆 append。讀取者只能看到上一份完整快照或下一份完整快照，不能看到半完成集合。

## 3. 伺服器端標準實作方式

### 3.1 建立 operation-local candidate

每一次載入都要在方法區域建立新候選物件。候選物件完成之前，不得修改目前已發布的 Session holder 或 shared snapshot。

```csharp
// 此區塊是流程示意，不是可直接貼入專案的完整實作；函式名稱代表待建立的責任邊界。
// 這份候選資料只屬於本次載入操作；在驗證完成前，不得寫回共享 Session 圖。
var candidate = await BuildCandidateAsync(validatedScope, cancellationToken);

// 驗證實際要交給目前 UI 元件的集合，而不是只驗證中間資料。
ValidatePublishedRows(candidate.Rows, "目前頁面資料");

// 只有完整候選成功後，才能以單次參考交換發布。
PublishCompleteSnapshot(candidate, validatedScope);

// 回傳與共享資料完全分離的讀取副本。
return candidate.CreateDetachedReadCopy();
```

若現有 CRM SDK 只有同步 API，也必須維持單一 owner 與明確生命週期；不可用 `Task.Run` 將同步 CRM 操作丟到背景而捕獲 `HttpContext`、Session、credential 或 request scope。

### 3.2 single-flight 與 scope key

同一個 validated scope 的並行讀取必須 single-flight：

- 同一 Session holder、使用者、租戶、角色、清單、報表、日期、版本與認證世代，只能有一個候選建立流程。
- 其他同 scope 請求等待同一流程完成，或在授權與新鮮度政策允許時取得同 scope 的上一份完整快照。
- 不同 scope 不得共用 mutable candidate。
- lock、SemaphoreSlim 或 Task cache 必須有明確 owner、上限、timeout、取消與釋放路徑。
- 不得使用無界的 static dictionary 保存使用者資料。

目前 ChurchReport 的 `ListManager` instance-level gate 可作為單程序基礎，但不能被誤當成跨程序或跨節點的唯一性保證。跨節點寫入必須交由 Dataverse/database alternate key 或 idempotency key 保證。

「只執行一個 loader」的預設邊界是同一程序、同一 holder、同一完整 key；多節點可各自建立唯讀候選，只要它們都正確授權且只發布完整集合。不要為了省一次讀取引入跨產品全域鎖。若引入共享 async build，必須由 build owner 擁有工作範圍與截止時間；某個等待者取消，不得誤取消仍被其他等待者需要的 build。等待者離開時仍需釋放自己的註冊與引用。

### 3.3 detached read snapshot

Controller、serializer、DataSourceLoader、背景工作與 callback 不得直接取得下列物件的可變參考：

- `HttpContext.Session`。
- `ListManager` 內部 Members collection。
- 全域 `IMemoryCache` 中的 mutable list。
- CRM Entity 及其 attribute dictionary。
- request scope 內的 connection、client 或 disposable。

回傳資料時必須複製到 request-owned、immutable 或足夠深度隔離的 DTO。呼叫端清空或修改回傳清單，不得影響下一個 request 或 Session holder。

### 3.4 不可信的 retry 與冪等寫入

對所有可能產生外部副作用的 POST、背景工作與 CRM Create：

1. 先產生一個伺服器擁有的 business-event idempotency key。
2. 將 key 與完整 validated scope 綁定。
3. 建立或更新時使用 Dataverse/database alternate key 或原子 upsert。
4. 重試時重用同一 key，不產生新的業務事件。
5. timeout 後不得把「不知道伺服器是否完成」當成可以再次 Create 的理由。
6. application lock 只能降低單程序競態，不能取代資料庫唯一性。

不同 operation ID 即使 payload 完全一樣，也不得僅因內容一致就合併。只有相同的伺服器認可操作身份，或資料庫已明確定義的同一事件唯一鍵，才適用重播判斷。payload 摘要只用來檢查「同一操作 key 被改成不同內容」的衝突，不是資料列去重依據。

同一次使用者意圖的 key 必須在第一個有副作用的請求之前就固定：可由預先建立的 server operation ID 或由伺服器推導的業務鍵識別。不能在每次重送進入 Controller 時呼叫 `Guid.NewGuid()`，否則每次都被當作不同操作。operation ID 必須綁定身份、租戶與正規化 payload 摘要；相同 key 搭配不同內容回傳衝突，不得覆蓋另一份內容。

operation 狀態至少區分 `Pending`、`Running`、`Succeeded`、`Failed`、`OutcomeUnknown`。回覆 accepted 只表示接受，timeout 也不證明成功。跨節點 claim／唯一約束必須是資料層原子操作；通知、付款等不在同一資料庫交易內的副作用還需 outbox 或供應方冪等契約，單純 upsert 不能保證所有外部副作用只發生一次。保存期限要涵蓋宣告的重送窗口；過期 key 不得悄悄重新執行舊事件。

對只讀 GET，重複執行不得改變資料或造成 append；對 POST，必須具備冪等語意後才可安全接受代理或 client retry。

## 4. 前端初始載入、refresh 與晚到回應防護

### 4.1 每一個資料來源建立 request coordinator

每個頁面或 Grid data source 必須有自己的狀態：

```javascript
const state = {
    generation: 0,       // 頁面資料世代；換 scope 時遞增
    requestToken: 0,      // 每次載入遞增，阻擋晚到 callback
    activeRequest: null,  // 目前唯一允許的請求
    loading: false,       // single-flight gate
    mounted: false        // 防止同一 DOM host 重複掛載
};
```

所有載入流程都必須遵循：

1. 產生新的 token。
2. 先讓舊 token 失效，再盡力 abort 舊請求；abort 後 callback 仍可能抵達，必須再次檢查 token。
3. 記錄目前 scope 與 generation。
4. 完成回應後先比對 token、generation、scope 與 DOM connection。
5. 不符合者直接丟棄，禁止更新畫面。
6. 符合者以完整集合替換目前內容，不得無條件 append。

最後提交前，前端還要驗證 schema、穩定 key、重複 key 與回應 scope；重複 key 的錯誤回應不能先交給 Grid 再補救。HTTP 200 並不代表一定是正確 JSON，代理登入頁、錯誤 HTML、欄位缺漏也必須安全拒絕。舊請求的 `finally/complete` 只有在仍是 active request 時才可清除 loading，否則可能把新請求的 gate 提早打開。

### 4.1.1 coordinator 狀態轉移

| 事件 | 必要操作 | 結果 |
|---|---|---|
| 初始 mount 重複呼叫 | 檢查同一 host 的唯一 owner；已有 instance 就重用 | 不新增 instance、不重複註冊事件 |
| 同 scope refresh，沒有進行中的請求 | 啟動一個載入 | `loading` |
| 同 scope refresh，已有請求 | 合併成最多一個 pending refresh | 不建立無界 Promise 佇列 |
| scope／搜尋／日期改變 | 先遞增世代、清除舊 scope 畫面，再取消舊請求 | 新請求只屬新 scope |
| 最新成功回應 | 驗 schema、scope、key，再一次替換 | `ready` |
| 過期回應或過期 finally | 不寫 rows、error、loading 或 current request | 保持目前狀態 |
| 最新失敗回應 | 顯示安全錯誤；僅同 scope 可保留已驗證快照 | `error`，可明確重試 |
| unmount／logout | 先失效 token，取消工作、清理元件與引用 | `disposed`，任何晚到回應無效 |

不論採用 fetch、jQuery、React、Vue、Blazor 或 DevExtreme，以上語意相同。不能同時讓頁面 coordinator 與 Grid 內建 loader 各自發送一套初始請求。

### 4.1.2 DevExtreme 接入要點

現有 `.DataSource(d => d.WebApi())` 與 `.Key("PresentRecordId")` 是現行入口。key 設定讓元件識別列，不等於幫應用程式做重複檢查。實作 adapter 時只有一個 transport owner：可由受控 CustomStore 包裝既有 API；保留原本 `loadOptions`、sorting、filter、paging、update／insert／delete 語意，不另建第二條資料載入管線。

受控 `load` 必須在 Promise resolve 給 Grid 前檢查世代與 row key。過期 load 要透過 adapter 的可測取消／過期分支結束，不可 resolve 舊 rows、不可永不結束，也不可簡單回傳空陣列而意外清掉新畫面；這一段必須以專案實際 DevExtreme 版本做瀏覽器測試。

如需防範中介設備誤回傳舊快取，可在請求帶不具授權效力的隨機 `attemptNonce`，由伺服器在既有 DevExtreme response envelope 外掛 metadata／回應 header 回送；前端比對 nonce、目前 scope 與支援的 schema version。保持 `data`、`totalCount`、`summary`、`groupCount` 原格式。Nonce 不可取代伺服器授權，也不允許把密碼／Session ID 當 nonce。伺服器的動態個人化回應仍須 `Cache-Control: no-store, private`；nonce 是錯誤偵測輔助，非抵抗惡意解密代理的保證。

### 4.2 初始 Grid 初始化只能一次

每一個 Grid host 必須在初始化前檢查：

- 是否已存在相同 DevExtreme instance。
- 是否已標記 mounted。
- 是否仍屬目前頁面 generation。
- 是否已有 active request。

重新建立前必須依序：

1. 將舊 coordinator 標記 disposed 並先遞增 token，使所有晚到 callback 失效。
2. 中止與舊 instance 相關的 request、timer、subscription；不依賴 abort 必定成功。
3. 呼叫舊 instance 的 `dispose()`，即使發生例外也以 finally 清除自己持有的引用與 listener。
4. 清除 host 內容與舊狀態標記。
5. 只建立一個新 instance。

不得使用兩段互不知情的初始化程式同時操作同一個 DOM id。

一般資料 refresh 應重用同一 instance，驗證新集合後以元件支援的方式替換資料。只有真正 unmount、身份邊界改變或需要重建元件時才 dispose；不可每個成功回應都重建 Grid，造成編輯狀態遺失與額外資源配置。

### 4.3 refresh 必須序列化

禁止在多個 `setTimeout`、success callback、error callback 或 `OnContentReady` 中直接呼叫 `grid.refresh()`。必須由 coordinator 統一排程：

- refresh 進行中時，後續 refresh 只保留一個 pending flag。
- 舊 refresh 未完成前不再啟動第二個 refresh。
- refresh 回應必須檢查 token 與 generation。
- 日期、使用者、清單或登入世代變更時，直接使舊 refresh 失效。

### 4.4 搜尋與樹狀資料

搜尋頁必須保留目前 ChurchReport `MemberInfoGrid` 已有的優良模式：

- loading gate。
- request abort。
- search token。
- render token。
- 舊 callback 不能覆蓋新結果。
- DataGrid dispose 後再替換 host。

未來產品應重用共用 coordinator 核心及各框架 adapter；不可將 ChurchReport 的 Controller、Session 欄位或 CRM 型別直接當作跨產品共同介面。現有模式是參考，不代表該頁面的所有生命週期情境已經驗證。

### 4.5 分頁、虛擬捲動與串流不能一律清空重建

- 完整 snapshot refresh 採替換；合法 pagination／stream 採有界且可驗證的組裝交易，不是全面禁止 append API。
- 同一 page/cursor 的同一 operation 被重播，可根據已提交的批次身份拒絕再次套用；這是阻止重播，不是把批次內重複 row key 偷偷刪除。
- 同一 snapshot 不同頁出現相同 row key，應拒絕該候選組裝，不能字典覆蓋。
- 分頁需具穩定排序與一致 snapshot version/cursor，不能在資料變動時把不同版本的 offset 分頁拼接。
- 前端只保留有界頁面與重播紀錄；資料來源換 scope／version 時全部失效。頁面或 export 超過上限時應分批處理，不能在記憶體保存整個租戶資料。
- 虛擬化與固定欄可能產生元件內部的 DOM 複本；測試應檢查邏輯資料列與可見呈現，不得單靠計算所有 `<tr>` 就宣告有重複業務列。

## 5. 目前 ChurchReport 的實作順序

以下順序可作為實際修改清單。每一步都要先寫測試，再改程式。

### Step 1：盤點每個資料消費集合

列出所有會友、會員、出席、週報、報表、匯出與背景結果，記錄：

- 權威來源。
- 穩定 row key。
- 使用者／租戶／清單／日期 scope。
- 目前 Controller 或 View。
- 是否直接讀 Session/cache mutable list。
- 是否透過 DataSourceLoader 或 DevExtreme。

ChurchReport 第一批檔案至少包括：

- `SpeechMessageProducts.ChurchReport/Models/ListManager.cs`
- `SpeechMessageProducts.ChurchReport/Models/ListSmallGroupWeeklyReport.cs`
- `SpeechMessageProducts.ChurchReport/Controllers/SmallGroupController/SmallGroupController.DataApi.cs`
- `SpeechMessageProducts.ChurchReport/Controllers/SmallGroupController/SmallGroupController.IntegrateView.cs`
- `SpeechMessageProducts.ChurchReport/Views/Home/_GeneralGroupGrids.cshtml`
- `SpeechMessageProducts.ChurchReport/Views/Home/IntegrateView.cshtml`
- `SpeechMessageProducts.ChurchReport/Views/MemberInfo/MemberInfoGrid.cshtml`
- `SpeechMessageProducts.ChurchReport/Controllers/SmallGroupController/SmallGroupController.Save.cs`

### Step 2：統一穩定身份

已存在的 CRM 出席列使用真正 `PresentRecordId`；Contact 類型列使用真正 `ContactId`。若「尚無出席記錄」的名單實際代表 Contact，應建立明確 DTO／adapter，以 Contact 的資料庫 ID 識別，不能把 ContactId 塞入仍被寫入端解讀為出席 ID 的欄位。

使用 counter、時間字串或每次新生 GUID 的例外路徑必須移除。欠缺資料庫 ID 的正式記錄應拒絕發布；尚未儲存的輸入只屬新增表單的暫存編輯狀態，不可混進正式記錄集合，也不可用臨時 draft key 假冒資料庫 ID 通過檢查。完成明確的寫入操作、取得權威 ID 後再重新載入正式清單；不要為取得 ID 在 GET 中建立資料。

### Step 3：在實際發布邊界驗證

`ListManager.ValidateIntegrateCandidate` 目前已驗證部分 Members 集合。擴充時必須確認所有實際交給 API、Grid、報表與匯出的集合都在最後一個消費邊界再次驗證，不能只驗證某個中間集合。

### Step 4：保留完整快照，禁止原地 append

任何 loader、日期切換、登入、重新同步與 retry 都要建立候選資料；候選完成前不得改寫目前 `m_ListSmallGroupWeeklyReport` 或其 Members。

### Step 5：API 只交付 detached snapshot

`SmallGroupController.DataApi`、`MemberInfoController`、`NewPersonController`、`PersonalController` 及其他資料 API 都要確認不把 Session-owned list 直接交給 `DataSourceLoader`。

### Step 6：建立前端 request coordinator

先處理 `IntegrateView.cshtml` 與 `_GeneralGroupGrids.cshtml` 的初始載入、日期變更與 refresh，再將相同 coordinator 模式移植至其他產品。每個資料來源必須有自己的 token，不得共用全域 token。

### Step 7：處理背景上傳與重複 POST

`SaveIntegrate` 必須：

- 以伺服器產生的 operation/idempotency key 識別同一業務事件。
- 同一 key 只允許一個有效背景作業。
- 客戶端 timeout、斷線或防火牆 retry 不得產生第二個業務事件。
- 背景副本不保存 request scope、Session 或 HttpContext。
- 每一條成功、失敗、取消與例外路徑都要釋放 scope、CRM lease、stream、timer 與 cancellation registration。

### Step 8：加入安全診斷資訊

每個資料載入與發布事件只允許記錄必要且有界的診斷資訊；ID 雜湊仍可能可關聯，不等於匿名：

- TraceIdentifier。
- operation id。
- generation/token（不可包含 credential）。
- 有限期、受控密鑰 HMAC 的 scope tag（有隔離權限時才使用）。
- row count。
- 衝突筆數；如需身份對照，僅記錄有上限且經授權的 HMAC 摘要，不寫完整逐列身份清單。
- loader start/end 時間。
- 是否命中 snapshot。
- 是否拒絕重複 key。
- 後端節點或版本識別。

禁止記錄密碼、Session cookie、LINE token、完整姓名清單或 CRM payload。

診斷採 bounded queue、輪替、保留期限與存取權限。Trace／operation ID 不可作為 metrics label，避免無界高基數。回應中的 trace ID 只用來定位，不可當成授權或客戶端請求世代。

### Step 9：依序交付與驗證，不一次重構所有產品

| 順序 | 修改位置與責任 | 先建立的失敗案例 | 完成條件 |
|---|---|---|---|
| A | `ListManager.cs`、`SmallGroupDataList.cs`、`ListSmallGroupWeeklyReport.cs`：最終 detached 集合驗證 | 候選已驗證後，後續 writer 注入同一 ID；下一次讀取不能發布 | 初始載入與快取命中兩條路都拒絕衝突；呼叫端修改不回寫來源 |
| B | `SmallGroupController.DataApi.cs`、`NewPersonController.cs`：小組／新人實際輸出 | 回傳前映射造成同一 ID 兩列 | 受控錯誤取代重複資料；合法同名資料完整保留 |
| C | `SmallGroupController.IntegrateView.cs`、`SmallGroupController.LineLogin.cs`：首次頁面 model 與 scope | 同時切換 scope 與初始 render | Razor 不持有正在修改的共享集合、不讀到別的 scope |
| D | 建議新增 `wwwroot/js/publication/collection-load-coordinator.js` 與 `devextreme-publication-adapter.js`，接入 `_GeneralGroupGrids.cshtml` | 重複 mount、晚回應、10 次 refresh | 一個邏輯 owner；舊回應無效；控制 Promise 全部結束 |
| E | `IntegrateView.cshtml`：日期與上傳後 refresh 都走同一 adapter | 舊日期回應最後回來、逾時後刷新 | 不覆蓋新日期；不建立第二套 loader |
| F | `SmallGroupController.Save.cs`、背景 runner 與所有副作用 writer | 同 operation 同時到兩個程序、第一次完成但回應遺失 | 只有一個有效業務結果；無界背景排程被拒絕；所有資源 drain |

## 6. Session Leakage、Memory Leakage 與 Resource Leakage 防護

### 6.1 Session isolation

- Session、認證 claim、Contact、tenant、role 與資料 scope 必須在伺服器端重新驗證。
- caller 提供的 list ID、contact ID 或 tenant ID 不是授權來源。
- 不可因 IP 相同就共用 Session。
- 不可因 IP 改變就把新舊身份混合在同一資料圖。
- 多節點部署首選以目前 request 的已驗證身份／scope 重新取得資料，讓暫存遺失可安全重建；若依賴 Session，使用真正 distributed store、相容 Data Protection keys 與正確 cookie scope。`AddDistributedMemoryCache` 仍是程序內記憶體，不是跨節點 store。
- sticky session 只能作效能／相容輔助，不能取代節點故障後的安全重建、驗證或 fail closed。共享 Data Protection key 也不是跨產品共用登入權限的理由。
- 分散式 Session 不是鎖，也不會自動防止最後寫入者覆蓋；scope 狀態仍需版本檢查／原子操作。可以完全不依賴 Session 的產品不必為了本手冊新增 Session。

### 6.2 Memory bounds

- 所有 cache 必須有容量上限與 absolute/sliding expiration。
- 不可把 request、HttpContext、Session、credential、CRM client 或 disposable 捕獲到長壽命 callback。
- snapshot、背景副本與 retry state 必須有明確最大生命週期。
- eviction callback 不得持有 request graph。

### 6.3 Resource cleanup

每一個下列資源都要有單一 owner 與 deterministic cleanup：

- `CancellationTokenRegistration`。
- `SemaphoreSlim`、`WaitHandle`。
- `Timer`。
- `Task` 與 background queue item。
- stream、connection、CRM lease。
- subscription、event handler。
- temporary file、buffer、diagnostic scope。

timeout 或取消之後，不能把狀態不明的 connection、lease 或 request context 交給下一位使用者重用。

Task 的清理通常是停止接單、合作取消、觀察例外、等待 drain 並清除引用，不是機械式對所有 Task 呼叫 Dispose。同步 CRM 若無法真正中止，必須依底層傳輸截止時間控制，觀察工作完成再釋放資源；不能回傳 timeout 就把仍在使用的 client 歸還給下一人。

新增 coordinator 的容量政策固定為每元件最多一個 active request、一個 pending refresh、零個重複 mount owner。供應商瀏覽器測試建議預設 30 秒單次等待截止；同 scope 唯讀失敗最多自動補試一次，最多兩次嘗試、總等待上限 65 秒，使用同一世代但新的 attempt nonce。這是起始產品預設，不是已完成的效能量測；各產品如需調整，必須在清冊中寫出數字、理由與驗證，不允許無限重試。

## 7. 必須加入的自動化測試

測試不需要到教會現場，可在 CI 或本機用可控的 fake loader、延遲、重試與多執行緒模擬。

### 7.1 資料身份測試

- 同名不同穩定 ID：兩列都必須保留。
- 所有顯示欄位都相同但唯一 ID 不同：兩列都必須保留；這是本手冊最重要的防止誤刪測試。
- 唯一 ID 相同但顯示內容不同：視為同一列的衝突更新／重複組裝，必須拒絕，不得依內容挑一筆。
- 同一穩定 ID 重複：發布必須失敗。
- 正式記錄空白資料庫 ID：發布必須失敗，不可補時間／亂數／draft key 混過驗證。
- 尚無出席記錄的 Contact 名單：以真正 ContactId 識別，不能誤送到把該 key 當 PresentRecordId 的編輯 API。
- 不得以姓名去重。

### 7.2 併發與晚到回應測試

- 同一 instance/key 的 32 個相同 scope 並行請求只執行一次 loader；跨 instance 另驗完整性與隔離，不強求只有一次全域讀取。
- 第一次請求延遲，第二次請求先完成；最終只接受第二世代。
- 舊回應最後抵達；不得覆蓋新世代。
- 同一 Grid 初始化兩次；最終只能有一個 instance 與一份 DOM rows。
- refresh 連續觸發 10 次；最多一個 active refresh，結果不得重複。

### 7.3 防火牆／代理模擬測試

建立 test handler 或 proxy simulator，模擬：

- GET 重送。
- POST timeout 後重送。
- response delay。
- response out-of-order。
- TCP-like connection reset。
- 503/504 後重新請求。
- 同一 session 請求被分派到兩個 application instances。

決勝斷言不是「請求只收到一次」，而是：

- 同一資料集合永遠不出現重複穩定 ID。
- 同一業務事件永遠只有一個有效寫入結果。
- 舊回應不能修改目前畫面。
- 所有 waiter、task、lease、registration 與 cache entry 在測試結束後回到基線。

### 7.4 Session isolation 測試

- 使用者 A 與 B 同時請求不同 scope。
- IP 相同但 Session.Id 不同。
- IP 變更但身份仍相同。
- 多節點 instance 交錯處理請求。
- 認證世代變更後不得讀取舊 snapshot。

### 7.5 Soak 與 resource drain 測試

反覆執行載入、取消、timeout、retry、eviction 與背景完成流程，確認：

- retained object 數量不持續上升。
- active task、lease、timer、registration、connection 於 drain 後回到基準。
- cache entry 數量不超過宣告上限。
- 沒有 request scope、Session 或 credential 被長期保存。

### 7.6 可重現的故障排程與數值驗收

測試使用可手動完成的 fake transport／`TaskCompletionSource` 控制順序，不用任意 sleep 等待碰運氣。每個測試的同步原語都要在 finally 釋放；至少包含以下排程：

```text
案例：初始載入的舊 scope 晚到
1. mount scope A，啟動 request A，暫停其回應。
2. 切換到 scope B，啟動 request B；fake A 故意不理會 abort。
3. 完成 B；確認畫面只有 B，且 B 的同名不同 ID 兩列都保留。
4. 完成 A 的 success 與 finally；確認畫面、error、loading 不被 A 改寫。
5. dispose；斷言 active owner/request/timer/listener/pending refresh 均為 0。

案例：同一回應包含重複列
1. 權威 fake repository 只有一筆出席。
2. 在映射或集合組裝階段故意產生相同 ID 兩次。
3. 確認 server guard 拒絕發布，API 不回傳兩筆 rows。
4. 另用 fake transport 繞過 server，直接回兩筆相同 ID 給前端。
5. 確認前端 adapter 拒絕提交且呈現安全錯誤，沒有瞬間畫出重複兩列。
```

快篩至少涵蓋 0／200／3000／10000 毫秒的模擬延遲、A→B 與 B→A 完成順序、每個 GET 重送 2／5 次，以及 32 個同 instance 同 key 的並行讀取。可控假時鐘優先，不讓單元測試真的等完所有時間。

瀏覽器測試至少重複 mount／dispose 200 次；預熱後，每輪停止新工作，等待宣告截止時間與 cleanup，active request、pending refresh、timer、listener owner、lease、waiter 應歸零；cache 可維持宣告上限內的合法保留，但過期／明確清除後不能保留舊身份物件。

供應商壓力／soak 起始門檻為 30 分鐘並混合取消、scope 更換、錯誤與重播。使用相同負載比較預熱後的 retained heap 與配置量：不能只以 process RSS 沒下降就判斷洩漏，也不能只看到 GC 執行就宣布安全。若物件數或保留 heap 隨輪次持續上升，必須以 heap root 確認來源；可回收但無界排隊同樣不合格。

效能回歸以相同硬體／固定資料量下 p95 載入延遲、配置量、吞吐量比較；建議超過基線 10% 即阻擋自動放行並要求分析，不得移除隔離／驗證來換取通過。這個門檻是供應商的初始驗收政策，可經有證據的審查調整，不能無聲略過。

## 8. 發布前強制檢查表

任何產品只要有一項回答為「否」，就不得發布：

- [ ] 每個正式 repeatable row 都有真正的資料庫唯一 ID，UI key 只是它的無損表示。
- [ ] 即使所有內容完全相同，只要資料庫 ID 不同就完整保留；內容變化也不改變原資料的身份。
- [ ] 實際 API／Grid／報表消費集合已在發布前驗證 key。
- [ ] 重複 key 會 fail closed，而不是被刪除或覆蓋。
- [ ] candidate 完成前不會改寫共享集合。
- [ ] API 回傳 detached snapshot，不暴露 Session/cache mutable list。
- [ ] 同 scope 有 single-flight；不同 scope 不共享 mutable state。
- [ ] 前端有 loading gate、request token、abort 或等價的舊回應隔離機制。
- [ ] Grid 初始化與 refresh 不會重複掛載或無條件 append。
- [ ] POST／背景工作具有 idempotency key 與 atomic create-or-update。
- [ ] 防火牆 retry、timeout、晚到回應與多節點已由自動化測試模擬。
- [ ] Session、memory、connection、task、timer、subscription 與 stream 都有 deterministic cleanup。
- [ ] 同名、重複 key、併發、晚到回應、caller mutation、scope 變更與 resource drain 測試全部通過。
- [ ] 所有新增或修改的 `.cs`、`.cshtml` 都有完整繁體中文註解，UTF-8 without BOM、CRLF、final CRLF。

## 9. 絕對禁止的錯誤修法

以下做法即使能讓某次畫面看起來不重複，也不准採用：

```csharp
// 禁止：會刪除同名但不同人的合法資料。
rows = rows.GroupBy(x => x.FullName).Select(g => g.First()).ToList();

// 禁止：字典 indexer 會覆蓋同一 key，掩蓋真正的組裝衝突。
foreach (var row in rows)
{
    map[row.PresentRecordId] = row;
}

// 禁止：把 Session 可變集合直接交給序列化器，會與其他 request 競態。
return DataSourceLoader.Load(InMemoryContext.ListManager.Members, options);
```

上例最後一行是反例示意，不是目前 `ListManager` 的實際欄位名稱。LINQ `ToDictionary` 遇到重複 key 會擲例外，不會靜默覆蓋；仍應使用可識別的安全驗證錯誤，避免把內部 ID 或例外 detail 直接回傳給使用者。

也禁止：

- 只靠增加 `Thread.Sleep` 或任意延遲。
- 只靠把 timeout 調大。
- 只靠瀏覽器端 `Distinct`。
- 只靠單一程序的 static lock 保證跨節點唯一性。
- 只靠防火牆設定「不要重試」而不做應用層冪等。
- 將例外吞掉後繼續發布半完成資料。
- 以增加無界 cache 或保留 request graph 來換取速度。

## 10. 最終驗收標準

實作完成後，供應商可以在自己的 CI、本機與測試環境證明：

1. 在正常網路、慢網路、重複請求、回應亂序與節點切換模擬下，UI 不會顯示同一穩定身份兩次。
2. 同名但不同穩定身份的合法資料不會被刪除。
3. 伺服器回應集合在交給 UI 前已經完成完整驗證。
4. 任何重複資料衝突都會 fail closed 並提供可追蹤 operation/trace 訊息。
5. Session、cache、background task、connection、timer、stream 與 subscription 不會跨使用者或跨 request 洩漏。
6. 取消、timeout、retry、eviction 與 shutdown 後所有資源都能回到宣告基線。
7. 不需要到每一間教會重現問題，因為網路不可靠情境已由自動化測試在供應商端模擬。

這份手冊不是「建議清單」，而是所有現在與未來產品的發布前必要契約。任何已知重複列、Session Leakage、Memory Leakage 或 Resource Leakage 都是 release blocker，不得以「現場不一定發生」作為接受理由。
