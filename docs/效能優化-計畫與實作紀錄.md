## 1. 指導原則

1. **只做可證明的優化。** 每一項變更都要能說出「省下什麼、在哪條路徑上、量級多少」。
2. **安全性不可回退。** 現有的 Session Bleeding 多層防護在優化後必須維持等效或更強。
3. **不為了微小收益承擔行為風險。** 見 §5 明確排除的項目與量化理由。
4. **靜態資源與動態頁面分流。** 安全標頭與 Session 驗證只該作用在動態頁面上。

## 3. 已完成的變更

### 3.1 建置與發佈（Compile / Link / Publish）

#### B1　新增 `Directory.Build.props`（方案根目錄，新檔）

集中所有專案共用的建置旋鈕：

| 設定 | 作用 |
|---|---|
| `SatelliteResourceLanguages=en` | 只保留英文的當地語系化資源組件。輸出的語系子目錄由 16 個降為 2 個。這些 satellite assembly 只影響**框架與 NuGet 套件例外訊息的語言**，不影響應用程式自身的繁體中文內容、`CultureInfo`、日期格式或字串比較行為。 |
| `EnableNETAnalyzers=false`／`AnalysisMode=None`／`EnforceCodeStyleInBuild=false` | 停用 .NET 內建的程式碼品質分析器（CAxxxx）。本方案已在各專案的 `NoWarn` 明確抑制 CA1416、CA2200 等規則，代表分析器輸出並未被用於決策，卻仍在每次編譯耗用 Roslyn 時間。**編譯器本身的診斷（CSxxxx）不受影響**，仍會照常回報。 |
| `RestoreUseStaticGraphEvaluation=true` | 還原時使用靜態相依圖評估，多專案方案的還原較快。 |
| `ProduceReferenceAssembly=true` | 產生參考組件，只改方法內文時下游專案不需重新編譯。.NET SDK 預設已啟用，此處明示以防未來預設值變動。 |
| `AccelerateBuildsInVisualStudio=true` | Visual Studio 增量建置加速。 |
| Release 專屬：`TieredPGO`、`TieredCompilation`、`TieredCompilationQuickJit`、`TieredCompilationQuickJitForLoops` | 統一所有專案的分層編譯設定。 |

`SpeechMessageProducts.ChurchReport.csproj` 原本停用平行建置。本專案有 9 個 `ProjectReference`，序列化建置會浪費多核心資源。

#### B3　`PreserveCompilationContext` 改為 `false`

本專案未註冊 `AddRazorRuntimeCompilation`，不需要保留編譯期中繼資料參考。設為 `false` 後 publish 不再輸出 `refs\` 目錄，`.deps.json` 也不再攜帶龐大的編譯區段。

#### B4　移除硬編碼絕對路徑的 `<Reference>`

原本有一段：

```xml
<Reference Include="DevExtreme.AspNet.Core">
```

同一組件已由 `<PackageReference Include="DevExtreme.AspNet.Core" Version="23.1.5" />` 解析。這段重複的 `Reference` 造成組件被解析兩次，而且把專案綁死在單一開發機的路徑上，在其他機器或 CI 上會找不到檔案。

#### B5　排除從未被引用的靜態資產

`wwwroot` 共約 202 MB，其中 123 MB 不會被任何頁面載入：

| 樣式 | 檔案數 | 大小 | 說明 |

### 3.2 執行期設定

#### R1　新增 `runtimeconfig.template.json`

GC 相關旋鈕（Server GC、Concurrent GC、RetainVM、TieredPGO）原本已由 `.csproj` 屬性正確產生到 `runtimeconfig.json`，經確認無誤，因此範本只放**沒有對應 MSBuild 屬性**的設定：

- `System.Threading.ThreadPool.MinThreads = 64`
- `System.Threading.ThreadPool.MinIOCompletionThreads = 64`

低於最小值時，執行緒會**立即注入**而不受 500 毫秒節流限制；超過後才開始節流。本專案仍有 12 處同步等待非同步的呼叫（見 §5.4），提高下限可避免冷啟動與突發流量時的執行緒池飢餓。執行緒為延遲建立，設定較高的下限不會在閒置時預先配置。

### 3.3 請求管線

#### P1　壓縮等級 `Optimal` → `Fastest`（本次最大的單項執行期改善）

`CompressionLevel.Optimal` 對 Brotli 而言是 **quality 11**，這是 Brotli 最慢的等級，設計用途是「壓縮一次、傳送數百萬次」的靜態資產。本站所有 HTML 與 JSON 都是每次請求即時產生，套用 quality 11 會讓壓縮本身的 CPU 時間遠超過所節省的傳輸時間，而且直接佔用處理請求的執行緒。

`Fastest` 對 Brotli 是 quality 1：壓縮率只差數個百分點，速度快一到兩個數量級。Gzip 同理（Optimal 為 level 6~9，Fastest 為 level 1）。

#### P2　修正靜態檔案快取標頭被 `no-store` 汙染（既有缺陷）

**原本的行為鏈：**

1. 全站 no-cache 中介層對**所有**請求設定 `Cache-Control: no-store, no-cache, must-revalidate, max-age=0`
2. `UseStaticFiles` 的 `OnPrepareResponse` 用 `Headers.Append` **追加** `public,max-age=31536000`
3. 最終標頭變成
   `Cache-Control: no-store, no-cache, must-revalidate, max-age=0, public,max-age=31536000`

瀏覽器與 Proxy 只要看到 `no-store` 就完全不快取，那一整年的 `max-age` 從未生效。每次換頁都重新下載全部 CSS、JS、字型與圖片。

**修正後：**

- 安全標頭（`nosniff`、`Referrer-Policy`、`X-Frame-Options`）對所有請求一律套用，**不變**。
- `no-store` 與 `Vary: Cookie` 只套用在動態頁面。這兩者正是 Session Bleeding 防護的核心，而靜態資源本來就不含任何使用者資料。
- `OnPrepareResponse` 改為**指派**（而非追加）`public,max-age=31536000,immutable`，並清掉可能殘留的 `Pragma`／`Expires`。

**安全性未回退的理由：**
判定為靜態的路徑必須**同時**滿足「副檔名在白名單」且「位於 `/css/`、`/js/`、`/lib/`、`/assets/`、`/images/`、`/img/`、`/fonts/` 等已知靜態目錄下」（`StaticRequestPathHelper.IsStaticAssetPath`）。任何在動態路由後綴上靜態副檔名的 Web Cache Deception 嘗試都不符合前綴條件，會繼續走動態分支拿到 `no-store`，而且已先被 `WebCacheDeceptionMiddleware` 擋成 404。

#### P3　`SessionValidationMiddleware` 移除每請求的同步阻塞

`ISession.GetString` 在 Session 尚未載入時，內部會執行 `LoadAsync().GetAwaiter().GetResult()`，也就是在處理請求的執行緒上**同步阻塞**等待分散式快取。這條中介層位於每個動態請求的必經路徑。

改為先明確 `await context.Session.LoadAsync()`，後續所有 `GetString`／`SetString` 都命中已載入的記憶體副本。這是官方建議用法。

同時：

- 靜態資源直接跳過整段驗證（原本只排除 `/css/`、`/js/`、`/lib/`、`/images/` 等少數前綴，`/fonts/`、`/assets/` 下的字型與 `.map` 仍會走完整驗證並強制載入 Session）。
- 移除每請求一次的 `ToLowerInvariant()` 字串配置（比較本來就用 `OrdinalIgnoreCase`）。
- `ClearSessionAndRedirectToLogin` 的 `CommitAsync().GetAwaiter().GetResult()` 改為 `await`。

#### P4　`GlobalAuthorizationFilter` 移除每請求的反射與設定查找

| 原本 | 改後 |
|---|---|
| 每請求 2 次 `IConfiguration.GetValue<bool?>` | 建構時讀一次，存入 readonly 欄位 |
| 每請求 2 次 `GetCustomAttributes(inherit: true)` 完整反射掃描 + 2 次 LINQ | 以 `ActionDescriptor.Id` 為鍵的 `ConcurrentDictionary` 快取 |

**快取為何不含任何請求狀態：** 快取的值是 `bool`，只由編譯期的 `[AllowAnonymous]` 標註決定，不含使用者、Session、租戶或 Claims。鍵是 MVC 啟動時產生的穩定 Action 識別碼，數量等於 Action 總數（有界），不隨請求數成長。

`context.Filters.OfType<IAllowAnonymousFilter>()` 因為過濾器集合是每請求組出來的，**維持每次檢查、不快取**。

#### P5　全域過濾器改為單例

`options.Filters.Add<T>()` 會登記成 `TypeFilter`，MVC 在**每個請求**用 `ActivatorUtilities` 重新建立一個實例。三個全域過濾器都是無狀態的：

| 過濾器 | 改法 |
|---|---|
| `ThemeViewDataFilter` | `AddSingleton` + `Filters.AddService<T>()` |
| `GlobalAuthorizationFilter` | `AddSingleton` + `Filters.AddService<T>()` |
| `StrictNoCacheFilter` | 無任何相依項，改用 `static readonly Instance` 共用實例 |

所有請求相關資料都由方法參數的 `context` 傳入，因此改為單例後不會有任何跨請求狀態共用。

#### P6　`BaseChurchController.GetStableHash` 消除每請求的加密物件配置

原本每次呼叫都執行 `SHA256.Create()`：配置實作物件 → 向作業系統開啟 CNG 演算法控制代碼 → 雜湊數十位元組 → 立刻 Dispose。本方法位於 `EnsureCorrectUserData` 內，是每個已登入請求的必經路徑。

改用 .NET 5 起提供的靜態 `SHA256.HashData`，配合 `stackalloc`（≤256 位元組）與 `ArrayPool`（超長輸入），全程零堆積配置。

**相容性：** 演算法、輸入位元組、Base64 編碼與「取前 8 字元」的截斷方式全部不變，產生的字串與修改前完全相同，既有快取鍵格式不受影響。
**安全性：** 租用的緩衝區以 `Return(rented, clearArray: true)` 歸還，避免密碼的 UTF-8 位元組殘留在共用池中。

#### P7　`MiniAppDetectionMiddleware` 減少每請求配置

- 靜態資源直接跳過（這些請求不會進到 Controller 或 View，沒有人會讀 `HttpContext.Items`）。
- `Headers.UserAgent` 在單值情形下直接取索引，避免 `StringValues.ToString()` 的字串配置。

### 3.4 記憶體與 Session 洩漏修正

#### M1　`CheckSessionOutAttribute` 的跨使用者 Session 洩漏（最嚴重）

```csharp
// 原本
public class CheckSessionOutAttribute : ActionFilterAttribute
{
    String SessionId = "";                                   // ← 實例欄位
    public async override void OnActionExecuting(...)        // ← async void
    {
        if (SessionId == "") SessionId = ...Session.Id;      // 第一位使用者寫入
        else if (SessionId != ...Session.Id) { /* 導向錯誤頁 */ }
    }
}
```

**缺陷一：跨使用者狀態。** MVC 會快取過濾器屬性的實例並在**所有請求、所有使用者**之間重複使用同一個物件。第一位造訪者會把自己的 Session Id 寫進共用欄位，之後**每一位其他使用者**都會被判定為「Session 不符」而導向錯誤頁。該欄位在多執行緒下也沒有任何同步保護。

**缺陷二：`async void`。** 方法內沒有任何 `await`，但 `async void` 會讓例外脫離 MVC 的過濾器管線而直接終結行程，且框架不會等待方法完成就繼續執行 Action，設定 `filterContext.Result` 可能失效。

**修正：** 基準 Session Id 改存於該請求自己的 Session 之中（Session 本身就是 per-user 儲存空間，天然隔離），方法改為同步的 `override void`。

**目前影響範圍：** 這個屬性沒有被任何 Action 套用，因此尚未造成線上事故。修正的意義在於移除一個等著被誤用的地雷。

#### M2　Kestrel `MaxRequestBufferSize = null`（無上限）

`MaxRequestBufferSize` 是 Kestrel 對尚未被應用程式讀取的請求資料所保留的緩衝上限，也是它施加**背壓**的依據。設為 `null` 會完全解除背壓：客戶端可以比應用程式讀取速度更快地推送資料，Kestrel 只能一直把資料累積在記憶體裡。配上 1000 條並行連線上限，足以耗盡整台機器的記憶體。

這不是傳統意義的「洩漏」（記憶體最終會回收），但在負載下的可觀察行為與洩漏完全相同。

**修正：** 設為 1 MB（Kestrel 預設值）。這**不**限制請求主體大小，只是流量控制視窗；大檔上傳仍可正常運作，只是改為串流而非全部先進記憶體。

#### M3　`RequestHeadersTimeout` 從 30 分鐘縮短為 60 秒

標頭逾時是「客戶端從建立連線到送完完整請求標頭」的時限，沒有任何正常客戶端需要超過數秒。設成 30 分鐘等於允許單一來源開啟大量連線、每次只送一個位元組，長時間佔住連線物件與其緩衝區（slowloris），讓 M2 的風險更容易被觸發。

60 秒對最慢的行動網路仍然非常寬鬆。此設定**不**影響請求主體的傳輸時間，大檔上傳不受限制。

#### M4　LINE OAuth 流程的 `new HttpClient()`

`AuthenticationController.LineLoginOAuth.cs` 有兩處 `using (var httpClient = new HttpClient())`。`HttpClient.Dispose` 並不會立即關閉底層 TCP 連線，連線會停留在 TIME_WAIT 約 240 秒。每次 LINE 登入建立兩條新連線，在登入尖峰時可耗盡通訊埠而出現 `SocketException`。

**修正：** 改用 `IHttpClientFactory`（`services.AddHttpClient()` 早已註冊）。它集中管理並定期輪替 `HttpMessageHandler`，讓連線得以重用（消除通訊埠耗盡）同時避免 DNS 陳舊。

**額外的身分隔離強化：** `GetLineUserProfile` 原本把 Bearer 權杖寫進 `httpClient.DefaultRequestHeaders`。`DefaultRequestHeaders` 屬於 HttpClient 實例，一旦日後有人把 client 快取重用，前一位使用者的權杖就會跟著送出。改為用 `HttpRequestMessage` 攜帶授權標頭，讓這個錯誤在結構上不可能發生。

#### M5　`BaseChurchController._userValidationCache` 的 O(n) 全表掃描

原本每一個「已登入且通過密碼比對」的請求都會走訪整個快取字典，並無條件配置一個 `List<string>`（即使一筆都不需要移除）。單一請求成本是 O(線上 Session 數)，1000 個並行 Session 就是每請求 1000 次走訪，整體呈 O(並行數平方)。

**修正：** 兩道節流。

1. **時間節流：** 兩次全表清掃至少間隔 30 秒，以 `Interlocked.CompareExchange` 確保同時只有一條執行緒執行清掃。
2. **筆數硬上界：** 一旦快取達到 4096 筆就立即清掃，確保時間節流不會讓字典無限成長。

外加延遲配置清單（沒有可移除項目時完全零配置）與 `StringComparison.Ordinal` 比較。

**為何節流不影響安全：** 這個清掃純粹是記憶體衛生。快取讀取路徑本身就檢查 `cacheAge < 30 秒` 與 `PasswordHash == currentPasswordHash`，而快取鍵是 `{sessionId}_{passwordHash}`，屬於其他 Session 或其他密碼的項目根本查不到。晚幾秒移除不會讓任何使用者看到別人的資料，也不會延長任何憑證的有效期。

#### M6　`ContextDictionary` 的常駐計時器

這個靜態 Session 字典在生產程式碼中已無使用者（`BaseChurchController` 直接建立 request-scoped 的 `InMemoryDataContextSmallGroup`），目前只有測試會用到。其靜態建構函式會建立一個每 5 分鐘喚醒、且永遠不會被 Dispose 的 `Timer`。

由於靜態建構函式只在型別**首次被觸碰**時執行，只要沒有人碰這個型別就不會有常駐計時器。已在欄位上加註明確的維護不變量，警告不要在啟動路徑加入對此型別的參考。

| 新增程式碼的編碼 | UTF-8 without BOM、CRLF；530 行新增內容經掃描無亂碼 |

### 4.1 ReadyToRun 確認有效

`.csproj` 設有 `PublishReadyToRun=true` 但沒有 `RuntimeIdentifier`，一般會讓人擔心這個設定被靜默忽略。實測確認**有生效**：

| | 大小 | ReadyToRun 標頭 |
|---|---:|---|
| `bin\Release\net10.0\` 的組件（僅 IL） | 4.08 MB | 無 |
| `publish` 輸出的組件 | 8.04 MB | 有 `RTR` 簽章 |

原生預先編譯的機器碼確實被寫入，冷啟動不需要從零 JIT 整個組件。

### 4.2 兩個沒有作用的既有設定（未變更，僅記錄）

- `<EnableAVX>true</EnableAVX>` —— .NET SDK 沒有這個 MSBuild 屬性，是無作用的宣告。向量化由 JIT 依執行時的 CPU 能力自動決定，不需要也無法由此開關控制。
- 發佈指令碼中的 `/p:IlcOptimizationPreference=Speed` 與 `/p:IlcOptimizationData=true` —— 這兩個屬於 NativeAOT（ILCompiler）。目前的發佈是 `--self-contained false` 的框架相依模式，不會執行 ILCompiler，因此這兩個參數不產生任何效果。

兩者都無害，保留不影響任何行為，但不應據以認為它們帶來了效能。

## 5. 明確排除的項目與量化理由

### 5.1 不改用 Endpoint Routing

目前 `options.EnableEndpointRouting = false` 配上 `app.UseMvc()` 與約 50 條傳統路由。Endpoint Routing 使用 DFA 比對器，傳統路由是線性走訪路由表。

**理由：** 50 條路由的線性比對每請求約 50–100 微秒，DFA 約 1 微秒，單請求省下約 100 微秒。但這個應用的每個請求都包含 Dataverse/CRM 往返，量級是 50–200 毫秒。收益是總延遲的 **0.05% – 0.2%**，卻要重排整條中介層管線（`UseRouting` 與 `UseEndpoints` 之間的驗證順序），而管線順序正是 Session Bleeding 防護的正確性所在。風險報酬比不成立。

### 5.2 不改用 System.Text.Json

`AddNewtonsoftJson` 比 `System.Text.Json` 慢約 2–3 倍。但 `DevExtreme.AspNet.Data` 依賴 Newtonsoft 的序列化語意，且全站 AJAX 契約（日期格式、null 處理、大小寫）都建立在目前的 `DefaultContractResolver` 上。替換會改變線上 JSON 輸出格式。

### 5.3 不設定 MemoryCache `SizeLimit`

現有註解已說明曾因 `SizeLimit` 導致登入卡住。設定後任何沒有指定 `Size` 的 `Set` 都會擲回例外，全站有數十處快取寫入點。目前 `CacheService` 的絕對過期（10 分鐘）與滑動過期（5 分鐘）已界定上界，且它以 `RegisterPostEvictionCallback` 正確地在項目被逐出時解除鍵追蹤，沒有洩漏。

### 5.4 不重構剩餘的同步等待非同步呼叫

全方案僅 12 處，且多數在冷路徑（關機、通知）：

| 檔案 | 說明 |
|---|---|
| `BaseChurchController.cs:1071` | Session Commit |
| `PaymentNotificationService.cs:128` | 付款後 LINE 通知 |
| `DonationFeePaymentProcessor.cs:309` | 付款後工作流程 |
| `ChurchReportLineAdminNotificationService.cs:110` | 管理者通知 |
| `PushUtility.cs` × 3、`DataverseTrace.cs`、`DebugTraceMonitorLifetime.cs` 等 | 背景與關機路徑 |

要移除必須把整條呼叫鏈改為非同步，涉及大量控制器簽章變更，行為風險高於收益。已改以提高 `ThreadPool.MinThreads` 緩解飢餓風險（§3.2 R1）。

**修正紀錄：** 初版計畫誤以為 `ListManagementDataManager.cs` 有 37 處同步阻塞。實際比對後確認那些是名為 `Result` 的**屬性**（`m_AddController.Result`），不是 `Task.Result`。該檔案沒有任何同步等待非同步的呼叫。

### 5.5 不移除 `ContextDictionary`

生產程式碼已無使用者，但 `ChurchReport.MemberInfo.Tests` 仍依賴它，刪除會破壞測試。改為降低其常駐成本（§3.4 M6）。

## 6. 既有問題（本次未處理，需另案決定）

### 6.1 測試：22 個既有失敗

`ChurchReport.MemberInfo.Tests` 有 22 個架構／命名測試失敗。已在**未修改的 HEAD** 上獨立驗證，失敗數與項目完全相同，與本次工作無關。

**根因：** 這些測試以 `Type.GetType("ChurchReport.Controllers.PaymentReturnController, ChurchReport")` 解析型別，但實際組件名稱是 `SpeechMessageProducts.ChurchReport`（見 `.csproj` 的 `<AssemblyName>`）。測試輸出目錄中也只有 `SpeechMessageProducts.ChurchReport.dll`，不存在名為 `ChurchReport` 的組件，因此 `Type.GetType` 必然回傳 `null`。

**建議：** 把測試中的組件名稱改為 `SpeechMessageProducts.ChurchReport`，或改用 `typeof(SomeKnownType).Assembly.GetType(...)`。這是測試本身的缺陷，不是產品程式碼的問題。

### 6.2 效能：54 處 `ColumnSet(true)`（最大的未開發改善空間）

`ColumnSet(true)` 會向 Dataverse 索取實體的**所有**欄位。以本系統的 `contact` 實體而言，這代表每次查詢都拉回上百個自訂屬性，而呼叫端通常只用到其中幾個。這會同時放大 Dataverse 端的處理時間、網路傳輸量與本機的反序列化成本。

考量到 CRM 往返本來就佔請求延遲的絕大部分，這是全系統**最大的單一效能改善機會**，量級遠超過本次所有管線優化的總和。

**未在本次處理的理由：** 要修正必須逐一分析每個呼叫端實際用到哪些欄位。漏掉一個欄位不會編譯失敗，也不會拋例外，只會讓該欄位靜默變成 `null`，是難以察覺的資料正確性風險。這需要逐案驗證，不適合放在一次自動化的效能整理中。

**建議做法：** 以流量最高的路徑為序（登入、`MemberInfoController`、`SmallGroup` 相關），逐一改為明確欄位清單，每改一個就以實際頁面驗證。

### 6.3 已處理：`BaseChurchController.cs` 的註解全面重寫

#### 亂碼無法還原（已用量化證據確認）

該檔案在本次工作之前就有大量亂碼註解，推測是早期 Big5 與 UTF-8 混用造成。已做過完整的還原測試：

| 檢測項目 | 數值 |
|---|---:|
| 註解中的 CJK 字元總數 | 2,793 |
| 已變成 `?` 替代字元的數量 | 2,202 |
| 佔可見字元比例 | **44%** |

`?`（0x3F）是編碼轉換時的替代字元，代表原始位元組在轉換當下就已被丟棄。以 `cp950`、`big5`、`big5hkscs`、`gbk`、`gb18030`、`cp932`、`cp949`、`latin-1`、`cp1252` 共 9 種編碼逐一嘗試反向還原，**全數失敗**。原文已永久遺失，任何演算法都無法重建。

#### 外部工具的兩次破壞

工作進行中，Codex 兩度修改該檔案，把所有註解替換成同一句占位文字：

> `/// 此說明已依目前實作整理，並維持繁體中文與 UTF-8 編碼。`

第一次還在方法內文插入了 65 個未配對的 `#region` 指示詞，造成建置失敗（CS1038）。該次的損壞版本已保存至暫存區備查。

這種替換等於把「無法閱讀的資訊」換成「零資訊」，反而更糟：原本的亂碼至少還保留了段落結構與少量可辨識的字，占位文字則連那些都沒有了。

#### 處置：依實際實作重寫全部註解

既然原文無法還原，改為逐一閱讀程式碼後重新撰寫。共重寫 **78 個註解區塊**，涵蓋：

- 類別層級說明（設計動機、四類能力、執行緒與生命週期、典型用法）
- 全部欄位、屬性與常數的 XML 文件
- 全部方法的 `<summary>` / `<remarks>` / `<param>` / `<returns>` / `<exception>`
- 方法內文的逐步驟說明

撰寫原則是解釋**為什麼**而非複述程式碼。例如 `_userValidationCache` 的說明會回答「為什麼鍵要包含密碼雜湊」與「為什麼這不構成跨使用者洩漏」，而不只是說「這是一個字典」。

同時修正了兩處程式碼字串中的亂碼：`#region` 的名稱，以及一則 `Debug.WriteLine` 的訊息。
