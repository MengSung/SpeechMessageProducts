02 三產品各有自己的 Channel 池與多租戶組織

三條通路完整分開；共用底層不會把三產品的官方帳號、客戶資料或授權合併。

好牧人的 50 個 Channel 只屬好牧人；好管家的 50 個只屬好管家；好學會也有自己的 50 個。合計約 150 個是規劃總數，不能當成能跨產品借用的共同池。

D365 組織是產品資料邊界；Account 是該組織內的租戶業務身分。goodshepherd20 的一筆租戶 Account 代表一間教會，construction 代表一家建設公司，association 代表一個協會。Account 本身不會自動啟用租戶安全隔離。

每產品維持自己的 Webhook 路由與部署設定，可在其產品入口內依 Channel 路由至正確設定。建議以產品分開 Host／App Pool 或等效服務邊界；初期可共用實體主機，但需獨立身分、資源上限與停止／更新程序。這是部署建議，並非已存在的架構。

03 共用的是版本化能力 各產品保留自己的執行範圍

採共用程式庫與部署規格、產品各自組合的方式，讓修正可重用，也讓更新與故障可以分開控制。

可共用驗章、設定解析、授權介面、D365 存取契約、去重與重試、通知、檔案授權及部署工具。共用程式不應知道奉獻、報修或會費的業務規則；產品透過介面提供處理器與策略。

共用 schema 與 UI 範本可以版本化，但每個組織各有自己的組件實例、資料列與核定部署紀錄。定義有更新，不等於三組織自動同步；應先驗證相容性，再逐組織推進。三個組織使用相同 Solution 名稱不會因此跨組織覆寫；拆分產品套件是為了明確相依與變更責任。

比較三種方法：三產品全部各寫一份，隔離直觀但修正重複；共用程式而獨立執行，最符合目前規模與順序；集中成一個跨產品服務則增加路由、共用故障與授權負擔，暫無必要。建議選第二種，不先建立大型微服務平台。

能力可重用的內容須分開的內容
LINE 通訊驗章、API 包裝、重試契約產品／環境／Provider／Channel 設定與秘密。
租戶授權驗證流程與介面Account、會員關係、角色與授權版本。
D365 與佈建連線契約、差異規劃、驗證組織目標、服務身分、schema 與 UI 實例。
佇列與快取有界容器與清理方法產品、組織、租戶、身分與操作資料。
產品業務通用通知與附件能力奉獻、報修、會員／會費等業務模型。

共用通知機制也要依各產品部署設定選擇目的地，不能拿產品 B 的 Channel token 為產品 A 發送。

04 目前分支的能力與待補強範圍

底層不是從零開始。Schema 與 UI Solution 都已有程式，但它們的支援範圍不同。

本輪本機核對以 HEAD 8301eec2 為基準，保留工作樹其他變更。原始碼存在只證明有實作；本次未建置產品、未重跑產品測試、未在三個新組織實測。

Schema 引擎已有匯出 metadata、plan、apply、verify，包含新增 entity、attribute、lookup、key、Solution 組件與針對實體發佈；並有部署前快照、指紋再驗證、衝突拒絕與已發佈 metadata 驗證。[R1、R2]

UI 引擎已有固定 SpeechMessageUi Solution 匯出入。它不是通用 Form/View 產生器；目前會刻意移除 account/contact 表單，而且匯入後執行 PublishAllXml。後續需評估產品專屬 UI 管理與發佈策略。[R3、R4]

本機項目已見能力這次規劃的缺口
SchemaDeploymentEngine結構差異與受控新增三產品分層清單與逐組織驗證。
UiSolutionDeployment固定 Solution 匯出／匯入UI 專屬差異計畫、精確身分與發佈範圍。
OrganizationCatalog核定組織 Guard目前只有 goodshepherdback；新目標不能直接套用。
LINE 共用專案現有通訊與選單程式兩專案直接參考 GoodShepherd.Core，需釐清依賴方向。
Contact 綁定new_lineid 與備援欄位多租戶、多 Provider、多 Channel 的完整身分規則。

欄位 schema 的 plan/apply/verify 不等於 UI 已具有相同生命週期；不能把兩者畫成一個已完成工具。

05 一個事件如何找到正確的租戶

Channel 只決定這個事件來自哪個官方帳號；同一 Channel 有多個租戶時，還必須驗證使用者屬於哪個 Account。

首先由受控產品路由選擇 Channel 設定候選，再用該 Channel secret 對原始 body 驗章。路徑、JSON 中的 Channel 或 Account 值只能協助選擇候選，不能自行取得權限。驗章成功後仍要核對事件目的地與受控設定。[L3]

接著辨識 Provider 範圍下的 LINE userId、對應產品內的 Contact 或會員身分，再查證其 Account 成員關係與角色。若只屬一個租戶可直接建立操作範圍；若屬多個，必須由伺服器驗證可選名單及目前選擇。選單、QR code 或 postback 帶來的 Account ID 都不能取代此步。

建議先用兩個租戶共用一個 Channel 做最小驗證。A 租戶的使用者把 B 的 Account ID 放入請求時應拒絕；合法使用者切換租戶時重建授權範圍，不能沿用舊快取或舊角色。

LINE userId 在不同 Provider 下可能不同；同一 Provider 的識別也不代表三產品可自動共用會員資格。現有 new_lineid 綁定先盤點再擴充，不預設一定新增一張全域使用者表。[L2、R8]

步驟伺服器需要證明
1 產品與 Channel受控路由、有效簽章、目的地及設定相符。
2 使用者身分Provider/userId 解析到本產品有效身分。
3 Account 與角色使用者確有該租戶成員關係，且狀態與權限有效。
4 業務操作查詢、寫入、附件、背景重試全部帶已驗證範圍。
5 結果發布完整授權與資料 ID 檢查成功才回傳；失敗不發布部分資料。

多租戶會員是否允許、一人能否跨教會／公司／協會，是產品規則待決事項；底層應能拒絕模糊或未綁定的事件。

06 Account 欄位與畫面篩選不能取代安全隔離

D365 直接登入者與經由 Web/LINE 存取者，要分別設計並測試權限。

經由產品 API 存取時，即使 D365 服務帳號權限很大，應用層仍須先確認完整租戶與使用者授權，再查詢與寫入；查詢快取、檔案連結、匯出及背景工作也必須遵守相同範圍。

直接登入 D365 的人員，資料可見性由 D365 原生權限、資料擁有權、Team、分享、Business Unit 及 Field Security 等共同決定。需依各實體的 OwnershipType 及人員模型設計，不能把 account lookup 當成自動的列級權限。[M8]

建議先以租戶 Owner Team 加最小角色評估 User/Team-owned 業務實體的隔離，確認是否需要 BU 分層與跨租戶服務人員例外；不要在未驗證前一次建立大量 BU。Organization-owned 表尤其不能因加上 Account 欄位就宣稱具有逐租戶原生安全。

Form 的角色、欄位隱藏與 View 的 FetchXML 篩選主要影響畫面。使用者仍可能經由其他檢視、進階尋找、匯出或 API 存取，必須測試這些路徑。管理者跨租戶查看要是明確授權且可稽核的行為。

使用情境必要隔離驗收
LINE／Web 租戶 A偽造 B 的 ID、換 Channel、舊授權與重放事件都不能讀寫 B。
D365 租戶操作人員其他 View、搜尋、lookup、匯出與直接 API 仍僅能存取核定資料。
跨租戶平台管理者明確角色、操作理由與稽核；不以普通使用者快取共用結果。
背景重試與通知保存的是可再驗證的純值範圍，不保存 HttpContext、Session 或活的 CRM client。

正式資料以資料庫 ID 識別；同名且不同 ID 必須保留，同一集合重複 ID 則拒絕發布並診斷。

07 資料模型先重用 再補真正缺少的結構

共用底層不是把所有東西建進 D365。應按業務責任、容量、機密性及生命週期安排儲存。

先盤點標準 account/contact、既有自訂欄位與關係。Account 除了租戶，也可能承載其他公司資料；若同表有多種用途，需明確租戶判定規則，不可把任意 Account 都當成有效租戶。

現有 speechmessagecore.schema.json 有九個實體項目，包含教會專屬結構。new_linechannel、new_outboundtask、new_localizedtext 是共用候選，仍須核對語意；奉獻分類、奉獻 lookup 與課程欄位不能整包部署到好管家／好學會。[R6]

共用 schema 定義與產品擴充清單分層管理，但保留既有 logical name、publisher 與相依契約。若資料模型需要升級，另訂遷移計畫；不能為了新命名重新建立所有表。

Webhook 收件、重試與去重可評估耐久技術儲存，但須與業務寫入協調失敗窗口；先重用現有出站任務契約。若新增平台 SQL，應在 D365 組織資料庫外，不直接改 CRM 系統表。[M1]

類型建議位置關鍵條件
租戶、會員、案件、活動各產品 D365 組織正式 ID、Account 範圍、擁有權與稽核。
Channel 設定與對應既有受控設定／D365指定唯一權威來源，密文及秘密引用延續既有契約。
憑證與 token受保護秘密來源不進文件、Git、URL 或日誌；分產品／環境／Channel。
重試與收件狀態有界耐久技術儲存唯一鍵、保存期、重放權限及故障恢復。
照片、簽名及附件受控檔案儲存下載再授權；敏感檔與公開素材分開。

目前不是新建資料表的許可；每個候選先列「既有／要擴充／確實新建」再審核。

08 表單與檢視依產品及角色設計

一個產品有很多 Account，通常仍共用該產品的表單與檢視定義；不需要每新增租戶就複製一套 UI。

例如 construction 裡的全坤與另一家建設公司，可以使用同一個案件表單與待處理案件 View；各自能看到的資料由授權與擁有權決定。association 的不同協會也可共用同一套會員／活動 UI。

表單宜按角色或作業目的區分，例如管理設定、日常處理與唯讀查詢；差異只在租戶名稱、Logo 或選項時，優先用受控資料設定，不建立數百份 Form。確有不同流程或欄位體驗時，再納入產品版本管理。

Account 與 Contact 是共同的資料型別，但三產品的畫面不必相同。可重用版面片段、欄位群與驗證方法，保留各自完整 Form/View 定義與組件身分。以下是待核定的畫面草案，不宣稱已建立。

產品Form 草案View 草案
好牧人教會設定、會友資料、首版業務作業表單所屬教會會友、待處理業務、通知結果。
好管家建設公司設定、維修案件、派工與簽收待派工、處理中、待驗收、逾期案件。
好學會協會設定、會員、活動與會費作業有效會員、待審會員、活動報名、未繳會費。
共同設計規則穩定組件 ID、版本、欄位相依、角色與 App正式資料列 ID、可用篩選與排序、資料權限測試。

「我的租戶」若用 View 表達，必須與已設計的 Team／Owner／授權模型一致；不能硬編碼某一個 Account GUID 當通用範本。

09 D365 支援程式化建立 Form 與 View

可以透過 WinRM 啟動部署程序，再使用 SDK 或 Solution 建立。WinRM 是執行通道，D365 才是接受自訂操作的服務。

Form 定義存於 SystemForm，布局由 FormXml 表達；在 EntityMetadata.CanCreateForms 允許的實體，可使用 CreateRequest 或 CopySystemFormRequest 建立。複製後是獨立表單，原表單變更不會自動繼承到副本；更新要有版本管理與相依檢查。[M5]

公用 View 是 SavedQuery，可由程式建立 QueryType=0 的 View，設定 ReturnedTypeCode、FetchXml、LayoutXml 等。FetchXml 決定查詢，LayoutXml 決定欄位與顯示；個人 View 的 UserQuery 是另一種擁有權模型，不應混為部署用公用 View。[M6]

Advanced Find、Associated、Quick Find 與 Lookup 這些特殊系統檢視不是任意新增多份的公用 View；官方文件列為更新既有檢視。managed property 可能限制自訂，需先檢查。View 的啟用狀態不會隨 Solution 原樣攜帶，匯入後要核對；只能有一個 active public default View。[M6]

建立 UI 組件後，還要確認 Solution 包含範圍、相關 Web Resource、App 元件、App 可見角色及 Form 設定。App 支援 AddAppComponents、角色關聯及 PublishXml，但不能推定每個現有客戶端都已配置同一種 App。[M7]

組件支援方式不能省略
FormSystemForm／FormXml；Create 或 CopyCanCreateForms、自訂限制、相依與實際畫面。
公用 ViewSavedQuery；QueryType=0FetchXML/布局欄位一致、狀態、預設與資料權限。
App 與導覽App 組件／角色關聯及發佈真實使用者登入後能找到並使用。

官方平台有能力，並不代表目前專案已提供全部自動化入口；本版的後續工作清單會明列差距。

10 現有 UI 工具可以沿用 但不能直接宣稱全自動

最需要補強的是受控的產品 UI 版本、差異計畫及精確發佈；現有固定封裝流程可作為基礎。

UiSolutionDeployment 使用 ExportSolution 與 ImportSolution 處理固定名稱 SpeechMessageUi 的未受管理 Solution，匯入設定 PublishWorkflows=false、OverwriteUnmanagedCustomizations=false。這些旗標不等於任意匯入都沒有畫面影響。[R3]

UiSolutionArchive 依現有 D26 規則移除 account/contact 的 FormXml 與相關根參照，但保留非表單部分。這是一個明確現行限制；若新產品需要部署這兩個實體的表單，應另設產品 UI 套件或精確政策，而非刪除防護就繼續匯入。[R4]

Schema 引擎使用針對實體的 PublishXml，UI 匯入目前執行 PublishAllXml，會擴及整個組織。即使改為發布指定實體，也可能帶出該實體其他未核定的 Form/View 變更；不能假定可按任意 FormId 或 Solution 名稱單獨發布。先比較該發佈範圍的所有未發佈差異，有未核定項就停止。B2 須解決此問題，才可核定實際 UI 套用。[R1、R3、M10、M11]

建議先以受控範本與可檢查的 Solution／XML 定義管理 UI，搭配 SDK 盤點、差異驗證與必要的明確操作。待產品有實際需求再擴成 UI 宣告式產生器，不先打造大型通用表單設計平台。

現況限制後續具體交付
固定 SpeechMessageUi共用與各產品的 UI 相依清單、版本與套件邊界。
排除 account/contact Form針對產品 Form 的精確允許規則與既有表單保護測試。
未見通用 UI plan/verify依 FormId/ViewId 盤點、XML 差異、相依與已發佈驗證。
UI 使用 PublishAllXml發布範圍設計、未核定變更拒絕與並行編輯漂移測試。

本輪只是提出缺口與修訂方案；既有 D26、發布程式及任何組織設定都沒有變更。

11 WinRM 遠端佈建的八個關卡

未來逐組織執行，不用手工重複點選；每次仍應先產出能看懂的差異清單，再核定實際變更。

控制鏈是工作站 → WinRM → 核定執行主機 → 部署工具 → D365 SDK/Solution → 指定組織。能登入 Windows 不等於具有 D365 自訂權限；部署身分與產品執行身分應按用途管理。

工作站經 WinRM 再存取 CRM 可能遇到 second-hop 認證問題；把程式放到 VM 執行不會自動解決。先選定核准身分與認證方案，不自行啟用 CredSSP、放寬驗證或保存密碼到腳本。[M3]

先前 D365APP01 與 IP 的連線紀錄只是歷史證據。真正執行前應核對主機、HTTPS endpoint、unique name、OrganizationId、版本及環境。完成或失敗都在 finally 關閉 PSSession，並排空及釋放 SDK 租約與本次程序資源。

關卡輸入與完成證據
1 核對目標已核定環境與目標清冊；身分不符立即停止。
2 讀取現況metadata、UI XML、Solution、角色／App 相依及未發佈變更快照。
3 產生差異新增、更新、既有、衝突清單；版本、範圍及指紋。
4 審查核定逐組織確認影響、適當備份、已驗證可行的回復方式與維護時段。
5 重驗後套用目標與指紋未漂移才執行核定項目；每步記錄正式 ID。
6 配置與發佈欄位→UI→角色/App；現有 UI 為全量發布，先補強範圍控制或核定完整影響。
7 結構及 UI 驗證已發佈 metadata、Active key、Form/View/App 實際狀態。
8 使用者驗收真實角色、正常／越權／重試流程通過，才推進下一組織。

目前 Catalog 不支援直接納入三新測試名稱；同主機不同路徑也受 host 唯一規則限制。要先設計 Guard 擴充，不偽造 DNS 或改標 production 繞過。

12 Form 與 View 的版本和失敗恢復

UI 變更要像 schema 一樣可以比較、追溯與重試；三個組織之間沒有單一原子部署交易。

每個 UI 定義應記錄產品、版本、entity logical name、組件類型、穩定部署識別、目標 FormId／SavedQueryId、XML 雜湊、相依欄位與資源。不能只依顯示名稱找到第一筆就覆寫；同名不同 ID 的既有表單可能是合法自訂，須列為待判定。

建議順序是 schema 與關係／key → 必要 Web Resource → Form 與公用 View → Solution/App/角色及預設配置 → 核定發佈 → 已發佈驗證 → 使用者操作。每一步記錄已完成項目；不能因最後一步失敗就盲目從頭新增。

執行前同時比較受管組件目前與未發佈狀態，若他人已在修改同一組件則停止重新規劃。XML 可做正規化比較，但不能忽略會影響布局、事件、欄位或安全的差異。跨組織 ID 若不同需明確映射，不從名稱推定相同。

回復前須有部署前同範圍的 UI 定義與正式 ID，並重驗差異。舊版 Solution 重匯不保證移除新增組件或無損還原；現有封裝還排除 account/contact Form，不能當完整快照。可按核定計畫恢復特定 UI 或向前修正；停用／刪除需另檢查相依與核定。Metadata 快照與 Solution 匯出不是資料庫備份，不因單一產品失敗還原整台共用 VM，也不盲刪已有資料的新欄位。

失敗情境可操作的處置

14 Channel 數量與圖文選單容量

三產品分開估算，每個官方帳號各有自己的容量；某產品空出的名額不能直接補另一個產品。

2026-11-25 再次核對 LINE 官方完整參考：每官方帳號最多 1000 個 rich menu；建立 rich menu 為每 Channel、該 endpoint 每小時 100 次請求。此限制不是每租戶 1000 個，也不是全產品合計 1000 個。容量與速率分開計算，正式實作前仍再次核對當日規範與其他 API 限制。[L4]

好牧人的示例：一個 Channel 分配 20 間教會，每間使用中 20 個選單，即 400 個；若換版期間新舊全量並存，再加 400；保留 100，峰值為 900。這只是容量假設，不表示已設定或一定需要 20 個選單。

角色、語系與版本會影響選單數，應按實際選單設計估算。分批換版可以降低峰值，但要追蹤綁定與失敗保留，不能先刪除仍在使用的選單。50 個 Channel 是擴充目標，初期可按需求逐步啟用。

好管家及好學會每 Channel 服務多少租戶，須依功能、角色、會員規模與使用量另算。三產品的 API 限速、訊息配額、排程公平性及故障恢復都要獨立管理；數量合計不能直接推估效能。

教學項目計算方式
使用中20 教會 × 每教會 20 個 = 400。
全量換版暫存另一套 400；若分批需另算峰值。
保留及峰值400 + 400 + 100 = 900，每 Channel 剩 100。
擴充含義50 × 20 = 1000 教會只是好牧人配置假設，不是已測吞吐量。

HTML 計算器可切換產品，另外兩產品不自動填入每 Channel 20 租戶；所有計算都只在本機頁面。
