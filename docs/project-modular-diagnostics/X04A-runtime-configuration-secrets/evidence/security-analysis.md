# X04A Security Analysis

## Confirmed Critical: Secrets Committed In Runtime Configuration

`SpeechMessageProducts.ChurchReport/appsettings.json` contains live-looking secrets and credentials in version-controlled runtime config:

- LINE Messaging channel access tokens at `appsettings.json:170` and `appsettings.json:174`.
- LINE Login channel secret at `appsettings.json:187`.
- LINE Mini App channel secret at `appsettings.json:212`.
- CRM username and password at `appsettings.json:250-251`, with a commented duplicate at `appsettings.json:257-258`.
- LINE Pay channel secret at `appsettings.json:271`.
- Payment provider credentials and key material at `appsettings.json:296-301`, `appsettings.json:312-313`, `appsettings.json:323-327`, `appsettings.json:342-346`, `appsettings.json:357-361`, `appsettings.json:370`, and `appsettings.json:379`.
- Taishin store key/IV placeholder defaults at `appsettings.json:501-502`.

The production override file does not replace these secrets. `appsettings.Production.json:1-57` only overrides logging, host, profiling, payment debug logging, session, memory, connection pool, health check, and GC settings. The base file therefore remains the effective source for secret-bearing sections unless external configuration is supplied by deployment.

Impact:

- Any repository reader can obtain application, CRM, LINE, and payment credentials.
- Rotation cannot be verified by runtime configuration alone.
- Environment isolation is weak because base config mixes production-looking URLs, sandbox keys, placeholders, and live-looking provider values.
- Secret values can leak into published artifacts because the project includes `appsettings.json` and `appsettings.Production.json` as content.

## Confirmed Low: Static OAuth State Placeholder Remains In Config

`appsettings.json:190` sets `LineLogin:State` to a fixed string. Local source review shows current runtime OAuth state is generated per request in `AuthenticationController.LineLoginOAuth.cs:104-105`, validated from session at `:151-158`, and generated by `GenerateRandomState` at `:331`. Therefore this is not treated as a confirmed runtime CSRF weakness. It remains an X04A cleanup finding because deployable config should not keep a security-control placeholder that could be accidentally consumed later.

## Confirmed High: Environment Drift And Unsafe Defaults

The base file combines:

- Production-like callback URLs under `LineLogin`, `MiniApp`, QPay, MyPay, and TSPG.
- Sandbox/default payment profiles at `appsettings.json:289-334`.
- `Cash_Environment` set to a test environment at `appsettings.json:278-279`.
- `LinePay:IsSandbox` set to `true` at `appsettings.json:269-272`.
- `Security:EnforceGlobalAuthorization` set to `false` and `Security:AllowSessionIdentityFallback` set to `true` at `appsettings.json:69-72`.

Because `appsettings.Production.json` does not override these sections, production startup can inherit test-mode payment behavior and permissive security flags unless deployment injects overrides. This is a runtime configuration governance issue even when the behavior is implemented in B01/B05.

## Confirmed Medium: Secret Masking Exists Only For One Debug Log Section

`PaymentDebugLog:MaskSensitiveData` is true in `appsettings.json:43-47` and `appsettings.Production.json:18-22`, but no equivalent X04A-wide policy validates that secret-bearing keys are masked in other logs, diagnostics, or startup failures. X04A should define a denylist/allowlist of secret key patterns and a startup diagnostic rule that reports presence without values.

## Rejected Or Out Of Scope

- Session password fields in business models are B01/B03/B05 concerns unless they are sourced from appsettings.
- Deployment script checklist text belongs to X04B, though it confirms the deployment process expects manual secret review.
