01

Claude 設計與 Codex 設計，哪裡真的不同？

Claude 的概念很接近；差異集中在五個會影響可部署性的地方。

Claude Draw.io 的主線

產品→ConnectionMode→Profile→ConnectorKind→Pool → CRM

它做得好的：把「Hosting 模式」與「Connector 類型」分成兩軸；明確畫出 F5 Embedded、per-Organization Pool、借出／歸還。

Codex 最終合併主線

產品→HostingMode→同一 ControlPlane→Generation→三種精確 Connector→Pool＋Capacity → CRM

我補上的：Embedded 不繞過治理；Official 拆成 CE 8.2／9.1；實體 Pool 綁 Generation；容量按物理 Organization 聚合；故障資源隔離後才回收。

1
DirectData8 改名並改語意為 Governed EmbeddedClaude 指出原本 DirectData8 會繞過 Profile／ControlPlane，這個批判成立；同進程只省 HTTP，不應省掉治理。現行程式仍需實作與 Gate，不能宣稱已完成。
2
「一份 Pool 實作」改成「一份租約政策＋不同資源池」Data8 池的是連線物件；官方 Worker 池的是進程／Pipe。可以共用 Acquire、Timeout、Reset、Quarantine、Drain 的政策與測試，不應假裝底層物件完全相同。
3
Official Worker 不能只保留不用測目前專案的官方 NuGet Worker 是現行主路線。停掉 CI 與平行測試會讓退路失去可信度；CE 8.2 與 9.1 必須各自固定版本並各自過 Gate。
4
Pool key 加上 Profile Generationper-Organization 是容量維度，不足以描述換憑證／換 Connector 的 Active＋Draining 兩個實體池；實體池必須綁不可變世代。
5
Embedded 與 Gateway 不宣稱安全等價Embedded 可共用治理程式碼，但沒有 HTTP／進程／Credential 邊界；上線前仍要以 Local Gateway 跑一次真實邊界 Gate。
02

我採用 Claude 的什麼？又改掉什麼？

不是全盤否定，也不是照單全收。

採用

雙軸命名

HostingMode 表示治理層所在進程；ConnectorKind 表示 Profile 使用的傳輸。兩者不混成一個開關。

採用

F5 優先

開發可用 Governed Embedded；要測 HTTP／授權／序列化，再切 Local Gateway。Central 是正式部署拓樸。

採用

共同治理主線

Operation Registry、容量准入、Profile replace-and-drain、稽核與健康檢查在三種 Hosting 都存在。

修正

Connector 不是 compile-time 開關

它是部署期寫入不可變 Profile Generation 的選擇；request-time 不可切換，也不可 fallback。

修正

Pool 不是三份複製碼

共享通用租約／生命週期政策；Data8 與 Worker 各自擁有符合資源型態的 adapter pool。

不接受

把官方 Worker 停在「退路」

官方 Worker 目前就是 CE 8.2／9.1 的主要實作；未通過的路徑可以 NotReady，但不能靠不測試來假裝可回滾。

03

三種 Hosting 怎麼選？

這是「治理層跑在哪裡」的決策，不是 Connector 的決策。

Governed Embedded

網站進程內執行 ControlPlane／Profile／Pool。最適合 VS F5 與快速開發，但與正式環境少了 HTTP／進程隔離。

開發便利性最高 · 仍需 Local Gateway 邊界驗證

Local Gateway

產品呼叫 localhost Gateway；Gateway 再管理 Worker。與 Central 共用契約，可驗證 HTTP、授權、序列化與 process lifecycle。

開發整合與邊界測試首選

Central Gateway

多產品共用正式服務；集中 Profile、容量、稽核、健康、故障回收與 Credential 邊界。

正式部署首選
04

Pool 的好處不是「永遠不建立」，而是安全地重用

三個條件用同一個生命週期表達：借出、使用、清除、歸還；故障物件永不回池。

1Admit取得 Org permit
2Rent同一世代借出
3Bind本次 caller 狀態
4Executebounded timeout
5Reset清除＋健康判定
6Return歸還＋釋放 permit
故障分支：Timeout、WCF／Pipe 錯誤或狀態無法重設 → Quarantine → Data8 Close／Abort，或 Worker Drain／Terminate／Recycle；不能把壞資源放回集合。
05

這是 Claude 圖沒有完全說清楚、但會直接影響效能與 Leakage 風險的地方。

06

Phase 4–6 會怎麼用這張圖？

不是把 Data8 直接刪掉，而是讓每個選項有自己的證據。

PHASE 4 · COMPATIBILITY

每個 Connector 個別通過

CE 8.2／9.1 操作矩陣、錯誤、timeout、Profile 隔離、確定性 cleanup。官方 Worker 與 Data8 不互相代替。

PHASE 5 · CAPACITY & FAULT

證明治理可長時間工作

多產品、同 Org 聚合容量、崩潰隔離、Active／Draining、回收、壓測與 soak。Embedded 仍要補 Local Gateway 邊界證據。

PHASE 6 · ROLLOUT

依環境選 Hosting，依 Profile 選 Connector

正式預設 Central，開發預設 Embedded 或 Local；移除未治理舊引用，不因名稱而刪除已通過 Gate 的 Data8。

07

我的最終建議

Claude 有一個關鍵修正值得直接採納；其餘用工程契約補齊。

✓

採用 Governed Embedded，不採用繞過治理的 DirectData8

這能保留你最在意的 VS 2026 F5 體驗，同時讓開發與正式環境共用 ControlPlane／Profile／Pool 政策。Local Gateway 仍保留，專門驗證 HTTP／授權／進程邊界；Central Gateway 是正式部署。

  • 每個 Profile Generation 固定一個 ConnectorKind；不在請求中切換。
  • 實體池 per Generation；容量預算 per Organization。
  • Data8 保留為可選 Connector，但在獨立 Gate 未通過前標記 NotReady。
  • 官方 CE 8.2／9.1 Worker 維持目前主路線，不能只留檔案而停止驗證。
