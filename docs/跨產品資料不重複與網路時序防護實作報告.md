# 跨產品資料不重複與網路時序防護實作報告

## 用途與保證範圍

本報告記錄 ChurchReport 週報重複資料問題的實際修正，並提供移植到採購協會、建設公司及其他產品的步驟。永久規範仍以 [跨產品資料不重複與網路時序防護實作手冊.md](跨產品資料不重複與網路時序防護實作手冊.md)、`AGENTS.md` 與 `.trellis/spec/backend/duplicate-row-publication-contract.md` 為準。

目前實作已對「同一權威資料列被組裝兩次、快取命中後活物件被修改、慢網路造成舊回應晚到、重複 refresh、Grid 重複掛載、Session 物件圖外洩與未受控背景工作」建立防線。對已定義且已測試的故障模型，同一個 `PresentRecordId` 不會被正常發布成兩列；偵測到衝突時會拒絕發布。不同 `PresentRecordId` 即使姓名和內容相同仍會完整保留。

這不是對所有未知程式缺陷、尚未接入的新產品、未測試的第三方 JavaScript 或惡意竄改設備作無限保證。每個新增資料集合都必須完成本報告的接入測試，才能宣稱受契約保護。

## 問題判斷

使用者觀察到教會 Wi-Fi 比 5G 更容易發生，而且初始開啟週報、尚未按按鈕時也可能出現兩列。後台同一週報只有一筆出席記錄，因此不能假設是兩筆不同資料庫記錄，也不能用姓名去重。Wi-Fi、防火牆、透明代理或較慢網路只能改變延遲、重送與完成順序；應用程式必須自行隔離這些時序。

## 已完成的後端修正

1. 新增 `RowPublicationGuard`，在 API、Razor、DataSourceLoader 的實際 consumer boundary 依 `PresentRecordId` 驗證 null row、空 ID、重複 ID 與最大列數。驗證器無 Session、HttpContext、credential、CRM client 或來源集合參考。
2. `ListManager` 的 cache-hit 路徑重新建立 detached snapshot，並對實際交付集合再次驗證，防止 legacy writer 修改已發布物件圖。
3. `SmallGroupData.InsertMember` 與 `SmallGroupDataList.AddNewPersonToMember` 在同一 instance synchronization root 內執行檢查與加入，避免 check-then-add race 及 partial publication。
4. 移除捕獲活 Session graph 的 `Task.Factory.StartNew(... LongRunning)` fire-and-forget 流程，改在目前 request 內完成受控發布。不得把 HttpContext、Session、credential、CRM client 或 request scoped service 捕獲到未觀察背景工作。
5. `SmallGroupController.DataApi` 與 `NewPersonController` 在呼叫 `DataSourceLoader.Load` 前再驗證各自集合；同一筆資料出現在不同合法 consumer 不會被錯誤地全域刪除。

## 已完成的前端修正

`wwwroot/js/collection-load-coordinator.js` 為每個 owner 限制一個 active transport、一個 pending refresh 與單調遞增 generation。舊 success/error callback 即使 abort 失敗或晚到，也會被拒絕；abort 只用於減少傳輸工作。重複 mount 會先 dispose 舊 owner；dispose 會失效 generation、取消 transport、清除 callback 與 pending refresh。WeakMap 不會對已移除 DOM 建立無界強引用。

DevExtreme adapter 包裝既有 `store.load`，不建立第二條 AJAX 管線。初始化契約不成立時會記錄不含資料列與 credential 的診斷、釋放已建立 coordinator 並 fail closed，不回退到未防護載入。

## Session、Memory 與 Resource Leakage 防護

本次修改沒有新增跨請求 static 使用者狀態、全域使用者集合、無界 cache 或無界 queue。Controller 交付的是 detached snapshot；前端 coordinator 不保存 rows、Session、credential 或 response data。transport、callback、pending refresh、DOM owner、背景工作與同步根都有明確 owner，並在取消、失敗、晚到回應、重複 mount、Grid dispose 與 pagehide 路徑清理或失效。

伺服器仍會重新驗證 subject、tenant、authorization scope、list/report/date 與 authentication epoch。caller 提供的 ID 不會成為授權來源。跨程序寫入仍須使用資料庫／Dataverse alternate key 或 idempotency key；單程序 lock 不足以保證跨節點唯一性。

## 移植到其他產品的流程

1. 閱讀 `AGENTS.md`、本手冊與後端 publication contract。
2. 列出產品所有 API、頁面、Grid、表格、報表、匯出、cache projection 與背景結果。
3. 為每個 repeatable row 指定真正資料庫唯一 ID，登記到 `docs/publication-contracts.json`；不同來源需使用已驗證命名空間隔離。
4. 先建立同名不同 ID、完全相同內容不同 ID、相同 ID、空 ID、慢回應、晚到回應、重複 refresh、caller mutation、scope 變更與 resource drain 測試。
5. 建立 operation-local candidate；完成 I/O、授權、scope、mapping、排序與 ID 驗證後，才一次發布 snapshot。
6. 在每個實際 serializer、Grid、報表與匯出邊界再次驗證，回傳 detached immutable value 或 request-owned copy。
7. 每個前端 owner 接一個 coordinator，限制 active transport 與 pending refresh，使用 generation 拒絕舊回應，dispose 時清理所有 callback 與 transport。
8. 所有 POST、PUT、PATCH、DELETE 與背景副作用使用 server-generated idempotency／alternate key 和資料庫 atomic create-or-update。
9. 用 fake repository、fake transport、可控延遲與 proxy simulator 在供應商端模擬 GET 重送、POST timeout retry、response out-of-order、節點切換與取消，不需到每間教會現場測試。
10. 將測試命令、產品 consumer、stable ID、scope、maxRows、adapter 與驗證數量登記到清冊和 CI；任一 identity、isolation 或 lifecycle 測試失敗即阻擋發布。

## 禁止的修法

不得使用姓名 `Distinct`、`GroupBy`、字典覆寫、前端過濾、`Thread.Sleep`、單純增加 timeout、關閉防火牆 retry、單程序 static lock 或吞掉例外來製造「看起來沒有重複」的畫面。這些做法會刪除合法同名資料、掩蓋組裝衝突，或造成 Session、Memory、Resource leakage。

## 發布判定

ChurchReport 已完成本報告列出的第一階段初始週報防護，並有程式、測試與雙模型審查證據。未來產品只有在自己的 consumer 清冊、stable ID、detached snapshot、時序 coordinator、冪等寫入、Session isolation 與 resource drain 測試全部通過後，才能宣稱完成接入。
