03 共用程式與三份獨立組織的關係

建議採同一套可版本化的共用程式與 schema 定義，在各組織部署獨立副本。

共用 schema 定義是一份受控規格，不是在三個資料庫之間同步同一筆資料。各組織的實體、欄位、Alternate Key、Solution 組件及部署證據都各自存在；是否需要這個組件，仍依產品依賴決定。

第一階段可共用同一台主機或程式庫，先維持各產品獨立部署設定及執行身分。建議採獨立產品 Host／App Pool 或等效服務邊界，讓重啟、密鑰更新與異常較容易控制；實際基礎設施選型留待環境確認，這不是現在必須拆成許多微服務。

共用底層的依賴方向應是產品處理器依賴共用契約。底層不知道奉獻、報修或會費如何運作。產品自行提供策略／Adapter，再由受控的組合入口注入。

建議命名 Common Schema、GoodShepherd Extensions、Construction Extensions 與 Association Extensions 僅用於解說。這次不另訂實際 Solution 名稱或更換既有 publisher prefix；已有邏輯名稱須先查依賴，不能為了好看而重建。

05 哪些資料應放進 D365

D365 保存業務事實與可管理設定；高頻技術紀錄、機密材料及大檔案要依用途分開規劃。

共用底層不等於每一項機制都要新增 D365 entity。先確認現有標準實體、客製欄位及現有儲存契約能否承擔，才提出新增。

平台技術儲存可採受控的獨立資料庫或佇列服務，但這是選型建議，不表示目前已有或必須立刻新建 SQL。若使用平台 SQL，必須是 D365 組織資料庫以外的資料庫；不能直接在 CRM 系統資料表插改 metadata。[M1]

私人維修照片、住戶簽名、付款憑證與公開 Logo 的存取條件不同。前者需伺服器授權、短效下載、大小及保存期限限制；不能因三產品共用檔案介面，就把所有附件放入公開位置。

資料類型建議位置設計重點
會員、案件、活動、奉獻等業務資料各自 D365 組織標準實體優先；業務 ID、角色及租戶範圍明確。
Channel 非秘密設定與可維護對應D365 或受控部署設定沿用既有契約；指定唯一權威來源，避免兩邊各改一份。
token、secret、認證及加密金鑰受保護的獨立設定／秘密來源每產品、環境、Channel 分離；不放教材、Git 或日誌。
Webhook 去重、短期收件及重試狀態評估耐久技術儲存唯一鍵、TTL、容量、重放權限與清理證據。
監控與錯誤、部署稽核受限日誌／部署證據目錄去識別、保留上限；metadata 快照不含資料備份。
檔案內容既有受控附件或檔案儲存D365 保存業務關聯；依敏感度與容量選位置。

跨組織共用技術儲存也必須分區；共用帳號或同一資料庫名稱不能代替授權。

06 schema 候選清單與不應直接複製的部分

現有 speechmessagecore.schema.json 混合共用與教會領域，需要拆分評估，不能整包套到好管家與好學會。

現有 manifest 使用 SpeechMessageCore／SpeechMessagePublisher，prefix 為 new，activePhase 為 8。九項為 account、contact、三個共用候選、new_offeringcategory、new_fee、new_dedication_booking、new_stor_lessons；其中部分是既有實體的欄位延伸，不是九張全新表。[R2]

下表是候選分類，不是本輪部署清單。每個新增欄位都需記錄目的、型別／長度、必填性、預設／回填、lookup 對象、擁有權、權限、稽核、唯一鍵、讀寫者與版本。

尤其 account 在好牧人可能代表教會，建設產品可能有建商、社區、管委會，協會又可能有法人會員。語意未核對前，不應將所有 account 都當作租戶。

07 身分與隔離必須先於功能擴充

LINE 的人、CRM 的聯絡人、D365 的登入使用者與教會租戶是不同概念，不能用同一個 ID 混在一起。

LINE User ID 與 Provider 有關：相同 Provider 下可一致，不同 Provider 下會不同。因此外部身分應保存已驗證 Provider 與 User ID 的關係，並在本產品、環境、組織與租戶範圍授權；跨產品看見同一 User ID 不能自動合併會員或繼承權限。[L2]

Webhook 先依伺服器配置選出候選 Channel，用原始 body 與正確 Channel secret 驗章，通過後再檢查 destination、事件來源及租戶綁定。未驗證的路由參數、教會 ID、Contact ID 或表單隱藏欄位都不是授權依據。[L3]

共用快取、隊列、連線租約與背景工作，必須有完整分區與期限。隔離鍵至少含產品、環境、核定組織身分、Channel／租戶、使用者與業務範圍；是否還需角色、日期、資料版本及登入 epoch，依各操作判定；登入 epoch 指每次登入或重新授權的版本標記。[R7]

每筆正式資料以資料庫穩定 ID 辨識。同名不同 ID 的紀錄全部保留；同一輸出集合出現重複 ID 應拒絕發佈並診斷。建立結果先在本次操作內完成授權、讀取與驗證，再一次發佈完整快照。

檢查案例通過條件
A 教會使用 B 教會的 Contact ID伺服器拒絕，錯誤不洩露 B 的資料。
A/B 同時操作或切換產品回覆、快取、錯誤、租約及背景工作無互用狀態。
同事件重送與跨程序競爭耐久唯一鍵防止重複業務結果；不只靠記憶體鎖。
取消、逾時、重啟與停止資源能排空／Dispose；未確定傳輸狀態的連線不轉借。

原生角色、Team／Business Unit 與應用程式授權需一起設計。服務帳號可以讀取，不代表終端使用者被允許讀取。

08 LINE 三產品路由與好牧人的容量

三產品維持獨立 Webhook。好牧人未來多 Channel 的擴充，應放在產品內的通道目錄與配額管理。

建議每產品有自己的 HTTPS Webhook 入口或可獨立配置的路由；好牧人多 Channel 可用受控路由識別候選 Channel。URL 本身不是秘密，也不是授權。圖中的入口都是示意，尚未建立任何網址或開啟 LINE 設定。

約十間新教會的 Pilot，可先評估一個好牧人 Channel；前提是圖文選單配置、訊息量、配額、權限與運維驗證都足夠。不是為了容量願景而先一次建立 50 個 Channel。

官方 Messaging API 文件列出每個 LINE 官方帳號可建立最多 1000 個 rich menu，且建立 rich menu 有每小時 100 次請求限制。容量不能只算『教會數 × 每間選單數』，還要加發布中版本與保留量。建立／刪除等 API 的限速範圍、alias 限制及訊息方案，啟用前須再次核對。[L4]

示例：20 間 × 每間 20 個 = 400 個使用中；全量新舊並存需再留 400，加 100 預備量共 900。若每間 40 個，則 800＋800＋100＝1700，無法以 1000 的上限全量換版。數值是教學假設，並非已決定每間使用數。

管理項目應有契約
Channel 指派先驗證剩餘容量；調度須耐久鎖定／原子保留，失敗可釋放。
rich menu 發布記錄已建立、已切換及可刪舊版本；分批切換並遵守當下 API 限速。
通知業務結果去重；外部送達不宣稱絕對 exactly once。逾時不明先對帳／採受支援重試策略。
環境切換新舊 Channel、Provider、Webhook、秘密與測試收件人逐項核對。

HTML 容量計算器是離線試算；沒有讀取你的 LINE 帳號、選單或即時配額。

09 複製組織啟用前的檢查

goodshepherd20 的 clone 能節省建模時間，但必須先確認哪些資料、設定與外送機制一同帶入。

來源可能含真實會友 LINE ID、付款與附件，盤點前按敏感資料處理。複製來源本身不等於資料已洩漏，也不能保證所有 GUID、秘密或設定一定改變。應依清冊盤點真實狀態，確認 endpoint、OrganizationId、unique name 與資料作用域，不能憑顯示名稱判定安全。

將來第一次經核定的連線應以唯讀盤點為主。先了解外送來源與既有狀態，再提出只影響此組織的可回復隔離方案；本次不遠端關閉 Plugin、Workflow、排程或清空資料。

新產品測試只能使用核定合成資料／測試收件人。不能把複製的舊 LINE User ID 當作新的 Pilot 名單，也不能把來源環境的加密金鑰一起共用，只為了讓舊 token 可以解密。需要更換或撤銷時另列具體項目。

盤點類別證據與處理決策
業務資料聯絡人、LINE 綁定、奉獻／付款、附件、測試資料；決定保留、遮罩或經核定清理。
外送與排程Plugin step、Workflow、非同步工作、outbound task、郵件信箱；確認所有出站路徑。
秘密及外部端點Channel、金流、發票、SMTP、SDK step secure config；只盤點引用及狀態，不輸出值。
schema 與依賴Solution、publisher、managed 狀態、欄位型別、關聯、key 狀態與 Plugin 相依。
安全與環境身分角色、使用者／Team、服務身分、OrganizationId、endpoint、版本及核定用途。

不得為隔離單一 clone 而直接停止整台 CRM 非同步服務或回收所有產品 App Pool；共享主機的影響範圍必須先查明。

10 WinRM 可以做什麼 與不能替代什麼

可以用 WinRM 遠端啟動已核定的部署工具，再讓工具經 D365 支援的 API 建立實體及欄位。

操作路徑是工作站 → WinRM → 受控 Windows 執行主機 → 部署工具 → D365 Organization Service。執行主機可以是合適的管理主機，不一定要在 CRM 服務主機本身；需先確認 SDK/runtime 與驗證方式相容。[M1–M4]

Windows Remoting 權限與 D365 自訂權限分開。WinRM 登入成功，不代表可建立 schema。應按操作列出 D365 所需權限、Solution／publisher 相依與服務身分；不可直接假定一個角色名稱就涵蓋所有任務。

工作站到 VM，再從 VM 連到 D365，可能遇到 second-hop。即使工具在 VM 內執行，也不保證問題自動消失。是否需要轉送身分，取決於工具實際用哪個身分連 D365。應驗證登入身分、認證模式與端點；如需服務帳號、受限端點或委派設計，另行評估，不能自動開 CredSSP、放寬 TrustedHosts 或略過 TLS 驗證。[M3]

2026-11-24 曾驗證 D365-9.1 對應 D365APP01／192.168.50.20，這只是歷史維護資訊。下一次必須重新確認主機與目標身分，不能當作今天已連線。D365DC01 不視為已驗證。

關卡具體要求
遠端主機核對 hostname、IP、環境及入口；只用已核定身分。
組織 API核對 endpoint＋unique name＋OrganizationId＋版本，不以顯示名稱代替。
寫入權限每組織分開，採任務所需權限；秘密不入參數、檔案範例與日誌。
執行完成有界逾時、取消與輸出；finally Remove-PSSession，排空並釋放 SDK 租約及程序。

WinRM 是遠端執行通道，不是直接改 CRM SQL 資料表的授權；本次沒有使用 WinRM 連線。

11 每個組織各走一遍部署與驗證關卡

先在核定的非正式環境演練。實際三產品部署時，一個組織通過後才處理下一個，各自保留計畫與證據。

先完成新組織 Guard 與部署工具的離線適配，並通過針對未知組織、同主機不同路徑、錯誤 OrganizationId、過期核定與部分失敗的測試。未完成這些工作前，現有 CLI 不能直接拿來對三個新組織執行。

先核定唯讀目標，export-metadata 也在此範圍內。部署概念順序：辨識目標 → export-metadata → 產生 plan → 審核差異與核定目標 → apply → publish／verify → 權限與業務 smoke test。這是流程說明，非可直接貼上的部署命令。

每份 plan 應附目標身分、環境、schema 版本及雜湊、before 指紋、待新增實體／欄位／key、既有衝突、操作者、時間及核定記錄。寫入前重新讀取並核對指紋，狀態漂移就停止重新規劃。

Metadata 建立完成仍不等於使用者可操作：表單、View、權限、欄位顯示、Plugin 相依與產品功能需另驗證。索引 Pending／InProgress 也不能當成功。

結果下一步
無差異記錄 no-op 與 verify 證據，不重複建立。
名稱相同但型別／所有權衝突停止；列出差異，不能猜測轉型或偷偷刪掉重建。
中途部分建立成功停止記錄已完成項目；重新讀取 metadata、產生新 plan，核定後只補缺項。
需要回復先停止新功能外送及寫入，優先前向修正；必要的資料庫還原依獨立核定方案。

Metadata 快照與 Solution 匯出不是資料庫備份；多組織間沒有一筆原子交易。不要把整台共享 VM 還原當作通用 rollback。

12 開發順序與每一步的完成定義

以小型垂直流程為開發單位，每次包含畫面、API、資料、權限、異常處理與必要實機驗證。

你提出『一個功能開發、實機驗證、審核後再下一個』是合理方向。建議補上依賴與分層驗證：離線測試先擋住明顯問題，再到經核定的整合環境，最後才由真實試用者按情境驗收。不要把每次功能驗證都直接等同正式上線。

共同底層做到可以支援第一條完整流程後，就回到產品開發。只有遇到第二個可證明共用的需求時再抽象，避免一次先做通用表單、任意流程設計器、全產品排程引擎與跨產品會員中心。

順序產出與離開關卡
0 確認環境與 clone 清冊環境用途、核定目標、外送來源與資料處理決策可供審查。
1 盤點與拆分共用邊界schema 候選與產品專屬清楚；Guard 適配及依賴改造有測試計畫。
2 最小共用通路Channel 路由、驗章、身分綁定、租戶授權、去重、錯誤與資源清理。
3 好牧人第一條垂直流程兩間教會同 Channel：加入 → 綁定 → 選單 → 一項核定業務 → 通知／管理端查核。
4 補齊 Pilot 流程依優先需求完成會友、活動／課程、奉獻等納入範圍的完整流程；不預設全數均入首版。
5 約十間新教會 Pilot按核定矩陣完成全流程、錯誤恢復、權限及營運驗收。
6 好管家 然後好學會分別導入建案／報修／派工／簽名，以及會員／活動／會費；以訪談定案。

每步由產品負責人確認情境與驗收，開發者提供實作／測試證據，維運者確認部署與回復；可由同一人兼任，但責任不能省略。

13 Pilot 必須驗證完整旅程與異常情境

第一條垂直流程是技術試跑，約十間教會的 Pilot 則是產品驗收，兩者範圍不同。

Pilot 前建立功能 × 角色 × 教會 × 狀態矩陣，列入每一項承諾給試用教會的流程。每項須有測試資料、操作者、預期結果、實際證據與判定；排除的功能必須明列，不能默默縮減成只測一項報到。

入場條件：環境用途核定、clone 外送風險已處理、Channel 與秘密來源核對、主要流程通過整合驗證、監控及回復演練可用。出場條件：核定必要情境全數通過，無未解決隔離、重複資料、資料遺失或資源洩漏缺陷，使用者確認業務結果。

效能門檻須量測後核定：Webhook 接收、背景處理與外部傳送各有 timeout、併發、queue 上限、TTL、記憶體／連線基準。停用或 drain 後計數應回到宣告基準，不能用一次成功點擊代表長時間穩定。

情境群必要案例與證據
正常旅程加入、綁定、角色、選單、核定業務、通知、管理端查詢一致。
資料隔離兩間同 Channel、同名不同 ID、跨教會 ID、跨產品路由、切換角色後重新授權。
失敗與重送重複 Webhook、資料庫暫斷、LINE 429／5xx、逾時不明、程序重啟及補償。
資料發布來源重複 ID 拒絕、完整快照切換、載入失敗不發布半套、呼叫端修改不污染共用結果。
資源與營運長時間運作、取消、queue 滿載、停止排空、例外紀錄及通知開關四種組合。

告警沿用既有共用契約：兩個輸出皆開時先寫檔並成功 flush，再送 LINE；單獨開關亦需驗證。通知不帶秘密與完整個資。[R7]
