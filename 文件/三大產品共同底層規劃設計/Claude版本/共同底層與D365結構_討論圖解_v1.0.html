三產品共同底層與 D365 9.1 結構

腦力激盪討論稿：先做共同底層嗎？實體與欄位怎麼「伸手」建到三個組織？

01現況（今天實際查到的）

D365 9.1 組織goodshepherd20（好牧人，從 goodshepherdback 複製）、construction（好管家）、association（好學會）都已建立；三個網址都能連到 D365，並正確轉到 ADFS 登入（2026-11-25 實測）。
LINE 官方帳號好牧人、好管家、好學會三個 Channel 已建立。好管家目前的頭像還是好牧人的 Logo（編輯限制解除後可換）。
佈署專案的組織清單d365/registration/organizations.json 只登錄了 goodshepherdback 一筆；程式也只支援「一個」測試組織（TestOrganization 取唯一一筆）。
結構清單只有一份 speechmessagecore.schema.json（9 個實體）；其中 new_fee、new_dedication_booking、new_stor_lessons、new_offeringcategory 是教會專屬，不該建到好管家、好學會。
主機連線D365-9.1 與 DC01 的 WinRM（5985）可連；PowerShell Direct 需要系統管理員權限的程序（Claude 與 Codex 平常不是）。

02問題一：現在先開發三產品的共同底層嗎？

我的看法：是。地基（F0–F12）本來就是共同底層，第一步就做它。三個組織和三個 LINE 帳號都建好了，我建議地基多做一小件事：把共用引擎需要的「資料結構」也做成共用的一層，一次佈署到三個組織。產品自己的結構（好管家的報修單、好學會的課程與會籍）仍然等到該產品開工才建，不提前。
共用什麼內容在哪一包做
程式共用（地基已涵蓋）Webhook 管線、推播出口、LIFF 身分、排程、權限與修改紀錄、審核卡片、圖片代管、觀測、測試租戶工具F1–F12
結構共用（建議新增）租戶欄位、LINE Channel、對外待辦、文字覆寫、發送紀錄、角色與權限、修改紀錄、審核單，三個組織同名同欄位新工作包 FS（約 3 天）
產品結構（不提前）好牧人的名額池（F3）；好管家的建案、屋車、報修、派工；好學會的課程、上課單、會籍、認證F3、H、I 各自開工時

03問題二：實體與欄位能不能直接「伸手」建到三個組織？

我的看法：可以，但建議走「佈署專案＋結構清單」這條路，透過 D365 的中繼資料 API（HTTPS、IFD／ADFS 登入）建立，不是用 WinRM。WinRM 是用來操作主機（建組織、IIS、服務、備份），不是用來改 D365 的資料結構；直接寫 SQL 則是 Microsoft 不支援、會弄壞組織的做法。
做法怎麼做好處缺點結論
① 佈署專案＋結構清單（建議）在 repo 寫結構清單 → plan 列出差異 → 你或 Codex 看過 → apply 建立 → verify 核對。透過 Organization Service 的 CreateEntity／CreateAttribute。可重複：三個組織、之後的正式組織、測試複本都用同一份清單；有紀錄、可回溯；P0～P8 已驗證過這套。要先改佈署專案支援多個測試組織（約半天～1 天）。建議
② WinRM／PowerShell 跑 SDK 指令碼從主機遠端執行 PowerShell，呼叫同樣的中繼資料 API。不用改程式就能做。沒有清單、三個組織要各做一次、日後轉正式與測試複本很難一模一樣；還需要系統管理員權限。只用在主機作業
③ D365 網頁手動建立在自訂化畫面一個一個建。最直覺。三個組織做三次、容易不一致、沒有紀錄；之後正式組織還要再做一次。只用在表單、檢視（ui-export 收進 repo）
④ 直接寫 SQL 資料表改 MSCRM 資料庫。—Microsoft 不支援；中繼資料快取不一致會讓組織壞掉，無法升級。禁止
WinRM 適合做的事（主機層）
  • 建立、匯入、停用組織（Microsoft.Crm.PowerShell：New-CrmOrganization、Import-CrmOrganization）
  • IIS 站台與應用程式集區（2.0、好管家、好學會的主機）
  • Windows 服務、防火牆、SQL 備份與還原（COPY_ONLY）
  • 在 DC01 建立各產品的服務帳號（AD）

04三個組織的結構分層

05建議新增：FS　結構分層與三組織佈署（建議新增，約 3 個工作天，放在 F1 之後、F3 之前）

  1. 把 speechmessagecore.schema.json 拆成「平台層」與「好牧人層」兩份；新增好管家、好學會的空白產品層清單（H、I 開工時才填）。
  2. 佈署專案支援多個測試組織：organizations.json 登錄 goodshepherd20、construction、association（皆為 test），指令以 --org 指定，不再假設只有一個。
  3. 平台層 plan → apply → verify 到三個組織；goodshepherd20 因為是複製來的，plan 應該只會列出少量差異。
  4. 測試：construction 與 association 的 plan 裡不能出現任何教會專屬實體；同一份清單在三個組織 verify 都通過。

不做：不建好管家、好學會的產品實體；不建表單與檢視（之後用 ui-export）。

06開始前要備齊的

服務帳號建議每個產品一個 AD 服務帳號（例：svc-goodshepherd20、svc-goodbutler、svc-goodguild），各自只在自己的組織有權限；建立 AD 帳號需要 DC01 管理員權限（你，或以系統管理員身分啟動的 Codex）。
加入組織服務帳號要加入對應組織成為使用者，並給「系統自訂員」以上角色，佈署專案才能建實體。
產品代碼D365 連線池用的 Product 值：GoodShepherd2、GoodButler、GoodGuild（建議，定了就不改）。
jesusbackD15 還沒決定：它跟 goodshepherd20 的角色是否重疊。

07請你回答（可填寫後複製回覆）

Q1　同意在地基加一包「FS 結構分層與三組織佈署」（約 3 天），把共用引擎的資料結構一次佈署到三個組織？
我的建議：建議同意：之後 F5、F8、F9 新增的共用實體會自動三個組織都有，不必每個產品再做一次。
Q2　結構佈署由誰執行：Codex（照 D24 自主執行、留一頁紀錄），還是由我在這個對話裡執行？
我的建議：建議 Codex：計畫與規則都是為 Codex 寫的；我負責審查。
Q3　每個產品各自一個服務帳號？
我的建議：建議是：一個帳號外洩或被鎖，不會影響另外兩個產品（四產品連線架構圖原本就這樣設計）。
Q4　好管家、好學會這兩個官方帳號的角色：是「產品共用帳號」（所有建設公司／協會共用，像好牧人），還是只當申請與說明窗口、每家公司另有自己的官方帳號？
我的建議：這會決定 D14；共用帳號就要做名額與宮格配額（像好牧人），每家自己的帳號則比較簡單。
Q5　好牧人這個新 Channel，是 goodshepherd20 的專屬 Channel（P0-1），還是名額池的第一個 Channel（好牧人01）？
我的建議：建議先當專屬 Channel 用於開發，名額池測試另用 T01–T03。
