## 4. 共用設計（各單元都依這一節，不要各自發明）

### 4.1 組織清單 `d365\registration\organizations.json`

```json
{
  "schemaVersion": 1,
  "organizations": [
    {
      "name": "goodshepherdback",
      "kind": "test",
      "host": "goodshepherdback.speechmessage.com.tw",
      "switchState": "off",
      "tierOverrides": []
    }
  ]
}
```

- `name`：D365 的組織唯一名稱，也是 User Secrets 的鍵（`Deployment:Organizations:<name>:OrganizationUrl`、`Username`、`Password`、`TokenKey`）。`kind` 只有 `test`、`production`。`host` 是允許連線的主機；路徑固定是 `/XRMServices/2011/Organization.svc`，HTTPS、預設埠。User Secrets 裡的網址與 `host` 不一致就拒絕。
- `switchState`：這個組織**現在應該是**哪一種狀態——`off`、`shadow`、`live`。`verify --org <name>` 依它算出每個步驟應有的樣子（§4.3）。正式組織切換成功後，由 Codex 把它改成新狀態並提交，再 `verify` 到 0。
- `tierOverrides`：這個組織與清單預設不同的分級，每筆 `{ "target": "<模組代號或型別完整名稱>", "tier": "live｜dormant", "reason": "…", "decidedBy": "…", "decidedAt": "YYYY-MM-DD HH:mm Asia/Taipei (UTC+08:00)" }`。型別的設定優先於模組的設定。把 `dormant` 改成 `live` 的那一筆，`decidedBy` 必須是使用者（正式組織）或寫「演練」（測試組織）。
- 檢查：名稱或主機重複拒絕；不認得的欄位拒絕；`kind=test` 的只能有 goodshepherdback。本目標結束時這個檔只有上面這一筆，goodshepherdback 的 `tierOverrides` 用來讓演練涵蓋 `dormant` 但有 Live 路徑的項目（D7-12、D7-9）。

### 4.2 註冊清單新增的 `live` 區塊（`schemaVersion` 維持 2，只加欄位）

每個步驟與每個活動各加一段：

```json
"live": {
  "tier": "live",
  "tokenKey": false,
  "reason": "",
  "evidence": { "file": "", "sha256": "", "at": "", "result": "" }
}
```

- `tier`：`live` 或 `dormant`（D7-6）。`dormant` 一定要有 `reason`，內容以提案編號開頭。
- `tokenKey`：只有步驟有這一欄；`true` 表示這個步驟在 Live 要寫入 `${secret:TokenKey}`（`StorLessonSigningPlugin`、`AppointmentPlugin`、`WeeklyReportNotificationPlugin`、`PresentRecordPlugin`；以各外殼實際有沒有讀安全設定為準）。活動一律沒有。
- `evidence`：`live-check` 通過後填（檔名、SHA-256、台北時間、`result="pass"`）。沒有跑過就保持空白。
- `diagnostics` 模組不加 `live` 區塊；它不參與任何組織層級的切換，在正式組織永遠停用。
- 既有的 `enabledByOrganization` 不動、不加其他組織的鍵；它只代表「`switchState=off` 時的啟用狀態」。

### 4.4 切換 plan、執行紀錄與 `verify`

**`plan --org <組織> --switch-to <off｜shadow｜live>`**（只讀）產生 `artifacts\d365\<組織>\<時間>\switch-plan.json` 與同名 `.md`：

- 內容：`schemaVersion`、組織名稱、伺服器回報的組織識別碼（`WhoAmI`）、`kind`、目前狀態的指紋、目標狀態、清單與組織清單各自的 SHA-256、兩個組件「組織上的內容雜湊」與「本機已打包 DLL 的雜湊」、依序的操作清單。
- 操作種類只有這些：`SetStepConfiguration`（改 `mode`；安全設定只記「佔位／空白」）、`EnableStep`、`DisableStep`、`DisableLegacyStep`、`RepointWorkflow`（流程識別碼、舊活動型別 → 新活動型別、原本是否啟用）、`KeepLegacy`（不執行；說明某個舊項目為什麼留著，需要使用者決定）、`Manual`（不執行；工具做不到、要人工處理的事）。
- 切到 `live` 的固定順序：① 全部 `SetStepConfiguration`（此時步驟還是停用的）→ ② `DisableLegacyStep` → ③ `RepointWorkflow` → ④ `EnableStep`（先同步步驟、再非同步步驟）。切回的順序相反。
- 產生時就拒絕的情況：組件還沒佈署，或組織上的內容雜湊與本機打包的不同（要先 `plan`／`apply` 佈署）；違反 D7-7；`kind=production` 而且目標是 `live`，卻有 `tier=live` 的項目沒有通過的 `evidence`（D7-6）；一個流程同時引用「要改指的」與「不改指的」舊活動（列成 `KeepLegacy`，整個流程不動）。
- `.md` 另有一段「仍登錄的舊組件、舊步驟、仍引用舊活動的流程」（D7-21），以及一段可以直接貼進核定書的摘要（附錄乙）。

**`switch --org <組織> --plan <檔> --plan-sha256 <雜湊>`：** 檔案雜湊不符拒絕；重新計算目前狀態的指紋、組織識別碼、清單雜湊，任何一項與 plan 不同就拒絕（plan 過期）；執行前自動 `export` 與 `export-legacy`；每做完一個操作就把「做之前、做之後」寫進 `switch-log.json`；任何一步失敗，立刻把已經做過的操作依紀錄反向回復，結束碼非 0。`kind=production` 另外要 `--production` 與標準輸入的組織名稱。

**`rollback --org <組織> --from <switch-log.json>`：** 依紀錄反向回復已執行的操作：步驟的啟用狀態、設定（回到影子設定的步驟，安全設定清成空白）、舊步驟的啟用狀態、流程的定義（還原成紀錄裡保存的原定義）與啟用狀態。既有的 `rollback --from <export.json>` 行為不變。

**`verify`：** `verify --org <組織>` 以 `organizations.json` 的 `switchState` 為期望；`verify --org <組織> --plan <switch-plan.json>` 以該 plan 的目標為期望（演練時用，D7-18）。兩者都另外檢查 D7-7。

**正式組織的限制：** `kind=production` 一律要 `--production`；不允許 `smoke`、`shadow`、`switch --module`、`live-check`、`ui-export`；`export-legacy` 在正式組織看到啟用中的舊項目時**不停止**，照實列出（測試組織維持現有行為）。寫入類指令（`apply`、`switch --plan`、`rollback`、結構的 `apply`、`protect-token`、`assign-channel`、`ui-import`、`church-defaults --apply`）在正式組織另外要組織名稱確認，而且只接受帶雜湊的 plan。

5. **維護時段內依序執行：** 結構 `apply` → `protect-token`、`assign-channel`（需要時）→ 註冊 `apply`（步驟停用）→ `church-defaults --apply` → 主機開關就緒 → `switch --plan`（到 `live`）→ `verify --plan` → 更新 `organizations.json` 的 `switchState` 並提交 → `verify`。
6. **任一步失敗：** 立刻 `rollback`，`verify` 回到切換前，回報；同一個組織同一天不再重試。
7. **觀察一週：** 每天一次 `observe`，結果記進該組織的操作紀錄；出現一天內修不好的差異就回復該組織。
8. **結案：** 觀察期滿、沒有新增錯誤、該組織每間教會通過語系驗證 → 在進度頁記一筆。舊組件的移除依 `P7-PROP-004` 另外核定。
9. **組織順序：** 使用量最小的教會 → 最大的教會；一次只動一個組織。

## 7. 什麼時候才找使用者

照 00 §9。本階段預期只有這幾種情況，其餘自己處理、事後留紀錄：

1. 前置 A 需要系統管理員權限（P7-00 的清單已經一次問完；之後不重複問）。
2. 需要新的警告抑制、降低既有檢查、放寬架構規則才做得下去。
3. 發現必須連正式組織才能完成本目標的某一步（不應該發生；發生就停）。
4. 發現某個已經預設 `live` 的項目，為了通過 Live 實機檢查必須改變「寫入 D365 的欄位與值」或「送到 LINE 的內容」，而且不在該模組期望檔已列的刻意差異裡（先把該項目改成 `dormant` 繼續做，階段審查時一併回報，不必當下停工）。
5. 同一個自動操作失敗兩次（00 §9-7），或演練中無法回到 `off`。
6. 任一段在 D7-28 的處理之後仍然超過時間盒或 15 個提交。
7. 前置檢查發現 goodshepherdback 有啟用中的舊步驟或舊流程，或 D34 的清理失效而且無法自行重做。

找使用者時一次講清楚：發生什麼、試過什麼、三個選項（第一個是建議）。等待期間繼續做不受影響的單元。
