# P4 金流驗收步驟與結果

本文件記錄階段 4 的核定驗收流程與實際狀態。P4-06 的「已驗收（沙箱連線未驗證）」是使用者 2026-11-13 核定的條件式結案狀態，不等同永豐沙箱撥款查詢通過；任何正式組織切換及真實付款仍在本文件範圍之外。

## 驗收步驟

| 步驟 | 執行方式與判定 | 實際結果 |
|---|---|---|
| 1. 合成回寫 | 在開發機執行 `Live_AllotWriteBack_SyntheticBatch_MatchesLegacy`。核對撥款金額、手續費、教會日曆日期、撥款編號四欄；本案回應為合成永豐資料。 | 通過 1/1。四欄依合成回應比對一致；不是永豐實際回應。 |
| 2. 冪等 | 執行 `Live_SameFeeEnqueuedTwice_ExecutesOnce`。同一收費單建立兩次待辦，核對待辦 ID 相同，且 attempts 與收費單修改時間不變。 | goodshepherdback 測試組織實機通過 1/1。 |
| 3. 永豐沙箱撥款查詢 | 執行 `Live_AllotQuery_SandboxRoundTrip`。預期核對待辦終態、供應商已驗證回應及必要撥款欄位；所有設定只從 User Secrets 讀取。 | 修正後唯一一次執行失敗 1 案。呼叫已到 Order 階段並收到 HTTP 400；安全診斷為 `Order:400`，沒有 APIM 代碼或可驗證供應商狀態。原因未明，不宣稱沙箱通過，也不再重跑。 |
| 4. 離線診斷與日期回歸 | 執行 P4-06 parser 回歸、`SinopacProviderTests`，以及 GoodShepherd.Core 的 net10／net48 日期測試。 | APIM 非物件錯誤根節點回歸 1/1；`SinopacProviderTests` 15/15。指定 UTC 16:00～23:59 日期案例在雙目標測試通過；完整程式守門見 P4-06 回報。 |
| 5. 測試資料收尾 | 唯讀確認本次測試 Contact、Fee、Outbound Task 殘留數為 0；確認 Church A profile 已還原及 `new_sinopacprofile` 欄位保留。 | 測試 Contact、Fee、Outbound Task 均為 0。profile 還原與欄位保留依本機操作紀錄／metadata verify 證據；沒有任何正式組織、商店、LINE Channel 或付款操作。 |
| 6. 沙箱補驗前置 | 使用者先向永豐確認 HTTP 400 排除方式、開發機對外 IP 白名單需求及測試金鑰／商店代號配套；取得答覆後再依另行核准的補驗步驟執行。 | 待辦。必須在階段 7 第一個正式組織切換前完成；未完成前不得進行該次切換。 |

## 驗收狀態

- P4-01～P4-05：依各包回報已驗收。
- P4-06：**已驗收（沙箱連線未驗證）**。合成回寫、冪等、離線診斷與清理有證據；永豐 Sandbox Order HTTP 400 的原因及實際撥款查詢結果未驗證。
- 使用者 2026-11-13 決定取消階段 4 剩餘工作的時間盒；只適用階段 4 收尾，不修改 3.5 計畫正文。
- P4-PROP-008：永豐沙箱連線補驗是階段 7 首次正式組織切換前置。這項提案不代表已完成補驗。
