## 2. 定案事項（使用者交付本檔即核定；不要再提案）

| 編號 | 定案 | 原因 |
|---|---|---|
| D5-1 | **順序固定、不平行**（§0 第 3 點）。「更新回復前置」排在 P5-01 之後、P5-03 之前，用現有的階段 0 佈署功能完成。如果它卡在等使用者重啟服務，先接著做 P5-02、P5-03，使用者處理完再回來；**它完成之前，不把任何模組的步驟佈署到 goodshepherdback** | 05 檔的依賴表；先用已驗證的佈署功能做 FileVersion 實驗，不讓新寫的佈署程式混進來 |
| D5-2 | **影子比對有兩個基準；實機部分「先舊後新」分兩輪跑**（修訂 1）。基準一＝離線黃金資料（P5-02）：規則測試要用，而且只有它看得到舊程式打算推什麼訊息。基準二＝goodshepherdback 上舊步驟實際執行的結果。實機每個情境跑兩輪：**第一輪**只啟用該模組的舊步驟（或舊流程），建立測試記錄、觸發、等它跑完，讀回它實際改了哪些欄位，然後立刻停用；**第二輪**只啟用新步驟（影子模式），用一模一樣的另一組測試記錄觸發，讀影子記錄。兩輪互相比，也各自與期望檔比。**舊、新步驟不同時啟用**：同時啟用會互相讀到對方剛寫的值，執行順序又不固定，會出現假的差異。新步驟在本階段仍然不以 Live 啟用。舊步驟只在第一輪的期間啟用，結束（包括失敗、取消）一定回到停用 | 使用者 2026-11-14 指示；goodshepherdback 上的舊 DLL 才是教會真正在用的版本，可能與舊原始檔不同（F24） |
| D5-3 | **舊程式在 harness 跑不起來時：** 某個舊專案在 harness 裡 2 小時內編不過或跑不起來，就不再花時間，改以 D5-2 的實機第一輪當唯一基準（`basis=legacy-live-only`）。連第一輪也不能跑的（D5-18 的例外），才改成「閱讀對照」：逐條讀舊程式寫出期望值，每條附舊檔名與行號，回報、進度頁與註冊清單都標成「未經舊程式實跑」，並登錄一筆提案「P7-02 演練時補驗」。不因此停工 | 取代 05 檔 P5-02 的「改用影子模式在 goodshepherdback 比對」 |
| D5-4 | **情境檔一份三用**（格式見 §4.2）：同一份合成情境 → harness 產生舊程式黃金資料 → 人工審過的期望檔 → 規則測試、外殼測試與 goodshepherdback 影子比對都用同一份期望檔。黃金資料由工具產生、**不得手改**；與舊程式刻意不同的地方只能寫在期望檔的 `declaredDifferences` | 一個情境只定義一次；「差異為 0」有可以自動檢查的定義 |

- P5-04 沒有舊程式：只有 `scenarios.json` 與 `expected.json`，`declaredDifferences` 為空。
- 三個檔都不得有真實個資、Token、LINE userId、商店代號。

### 4.3 影子記錄（新外殼在影子模式寫進追蹤的內容）

- 每一筆打算做的寫入或推播寫成**一行**，以 `SMV-SHADOW|1|` 開頭，後面是精簡 JSON：序號、動作、實體、ID、欄位名稱與值。值超過 120 個字元改記長度與 SHA-256。推播記會友 ID、範本代號、Retry Key、訊息則數、內容的 SHA-256。
- 一次執行的影子記錄合計不超過 8,000 個字元；超過時只寫到上限，最後補一行 `SMV-SHADOW|1|{"overflow":true,"total":<筆數>}`。`shadow` 指令看到 overflow 一律判定「無法比對」（不是 0 差異），要把情境拆小。
- 不寫 Token、tokenKey、LINE userId、訊息內文原文、個資欄位的值（姓名、電話、Email、地址一律記雜湊）。
- 最後一行固定是 `SMV-SHADOW|1|{"end":true,"count":<筆數>}`，讓解析器知道記錄完整。
