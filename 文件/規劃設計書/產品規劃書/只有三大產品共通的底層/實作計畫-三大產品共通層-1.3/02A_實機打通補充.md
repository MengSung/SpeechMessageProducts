## 1. 修正後重試（取代 02 §10 最後一段）

1. 同一個自動實機操作「原樣」失敗兩次，仍然不做第三次原樣重試。
2. 但只要同時滿足下列四項，就可以做一次「修正後重試」：
   - ①已用離線測試**重現實際失敗的同一個例外型別或錯誤訊息特徵**（先紅）；
   - ②修正後該測試轉綠，且受影響的測試全綠；
   - ③回復路徑已準備好（備份、回復指令或「新建的保持停止」），並寫進報告；
   - ④已取得 `test-env.lock`。
3. 每個操作最多兩次修正後重試。用完仍失敗，就在 `需要你協助.md` 寫一筆「通知」（說明卡在哪、已試過什麼、需要誰），然後照 §4 繼續別的工作。
4. **唯讀診斷不算重試**：為了找根因，可以把同一個大查詢拆成較小、範圍明確的唯讀查詢（例如逐實體、逐欄位、單頁），次數不限，但每次都只讀、只連測試組織、不印秘密與個資。拆小查詢不得用來繞過已失敗的寫入操作。
5. 每次修正後重試，在決策紀錄記一行：時間｜工作包｜操作｜失敗特徵｜修了什麼（提交 SHA）｜結果。

## 2. goodshepherd20 停用政策（解決 FS Step 3b 的「H1 unknown」）

goodshepherd20 是複製來的**測試組織**，LINE 憑證與會友 `new_lineid` 依使用者決定沒有清除，所以複製帶來的自動化可能對真實會友推播。「行為不明」不是保留的理由，而是停用的理由（02 §10 第 2、3 條：可回復、失敗即拒絕優先）。規則：

1. **一律停用**：
   - 所有流程執行個體：等待中、暫停中的全部取消；
   - 所有背景與即時 Workflow，以及自訂 Action（Business Process Flow 不動），盤點清冊明確標「保留」的除外；
   - 所有**非 Microsoft** Plugin 組件的 SDK 步驟（判斷依據：組件名稱不以 `Microsoft.` 開頭，且不是 D365 系統內建的 managed 組件）；
   - 郵件與伺服器端同步（信箱的 incoming／outgoing／ACT 設成不投遞）。
2. **不停用**：Microsoft 系統組件的步驟；業務規則（Business Rule）；本計畫 FS、F3 之後自己註冊的平台 Plugin（由部署程式在 apply 時啟用）。
3. **不需要逐一證明行為**：不必再分類 7,280 個步驟或 146 個流程各自做什麼；「非 Microsoft → 停用」就是分類規則。H1 以本節結案，在報告寫「依 02A §2 結案」。
4. **可回復**：沿用 FS 已完成的作法——每筆修改前先把原值寫進主檔與 SHA 側檔並 flush，按保存的 ID 可以全部還原；只動 goodshepherd20，不停整台 CRM 的非同步服務。
5. **驗收**：等待中的流程執行個體＝0；啟用中的非 Microsoft Plugin 步驟＝0（盤點清冊標「保留」的除外）；信箱不投遞；goodshepherdback 的筆數與狀態不變（前後各讀一次比對）。
6. **2026-11-28 使用者更正**：goodshepherd20 裡的會友與 LINE 資料都是**假的測試資料**，不是真實會友。因此本節的停用是「測試環境整潔」，不是個資防護，驗收簡化為：
   - 第 5 點各項各讀回一次即可，不必再逐筆查證每個 Plugin 步驟或信箱的歷史狀態；
   - 信箱設為不投遞若有個別失敗，記錄在報告後繼續，不阻擋 FS 的 plan／apply；
   - 其他安全規則照舊：不 broadcast、絕不呼叫複製來的舊 Channel「好牧人教會系統(非線上展示系統)」、log 不記秘密與 LINE userId、不連正式組織。
   - 00 §2 第 10 條、§0 O2、01 P0-6 中「真實會友資料」的描述，以本點為準。

## 3. 平台 SQL 的 TLS（P0-2④）

不改使用者電腦的憑證信任清單，也不用 `TrustServerCertificate=true` 放寬驗證。改用**憑證釘選**：

1. 線 B 從 VM 的 SQL Server 匯出它目前使用的 TLS 憑證**公鑰**（.cer，不含私鑰），存放在 repo 之外的固定位置（例：`C:\ProgramData\SpeechMessage\certs\d365-9.1-sql.cer`），在報告記它的 SHA-256 指紋。
2. 連線字串用 `Encrypt=Strict`，並以 Microsoft.Data.SqlClient 的 `ServerCertificate=<該 .cer 路徑>` 釘選；憑證指紋不符就拒絕連線（失敗即拒絕）。
3. 之後依 01 P0-2④ 建資料庫、登入與最小權限，驗證 `select 1`。
4. 若使用的 SqlClient 版本不支援 `ServerCertificate`，先依 02 §10 選最小範圍的做法（例如只在平台主機專案升級 SqlClient），寫進決策紀錄。

## 4. 實機欠債上限

1. 「實機待補」分兩種：
   - **可自行處理**：只需要 Codex 能操作的測試環境（D365 測試組織、VM 的 IIS／SQL、Node 轉接）；
   - **外部阻擋**：需要使用者（例如手機、M1）或需要另一條線的工作包先完成。
2. 每條線開始**新的**工作包之前，自己這條線「可自行處理」的實機待補不得超過 1 包。超過就先做 §5 的實機打通，做完或用完 §1 的重試額度才開新包。
3. 進行中的 F3（線 A）、F8（線 B）先完成目前的離線閘門並合併，不中途放棄；合併後才開始實機打通。
4. 90 的狀態欄：沒有通過實機的包，寫「自動測試通過（實機待補）」，不寫「完成」。只有五項完成定義都達成才寫「完成」。

| 鎖 | 管什麼 |
|---|---|
| `test-env-d365.lock` | 三個 D365 測試組織的任何寫入（quiesce、schema／UI apply、Plugin 註冊、資料寫入、測試租戶建立與清理）；VM 上 IIS 的任何變更（2.0 測試站部署、應用程式集區、CRM 站台設定），因為 CRM 跑在同一個 IIS；本機 Node 轉接程式的修改與重啟 |

2. **SQL 執行個體層級的變更**（伺服器設定、憑證繫結、服務重啟、伺服器角色）會影響同一個執行個體上的 CRM 資料庫，必須同時持有 `test-env-d365.lock` 與 `test-env-sql.lock`。
3. **需要多把鎖時固定順序**：`d365` → `sql` → `line`，放開時反向。後面的鎖拿不到，就先放開已拿到的，再等，避免兩條線互相卡死。

5. **過渡**：本節生效時仍存在的舊 `test-env.lock`，由持有的那條線做完目前這一步後放開，之後只用新鎖。舊鎖放開之前，另一條線把它當成 `test-env-d365.lock` 被持有（D365 與 IIS 都不動），但可以取得 `test-env-sql.lock`、`test-env-line.lock` 做不相干的工作。

## 10. 效率規則（2026-11-28 使用者核定）

**為什麼改**：Claude 分析兩條線 2026-11-27 08:24 起 24 小時的 Codex 紀錄：線 A 執行 2,371 個指令，其中 572 個輸出超過 2 萬字（合計約 2,000 萬字），對話因此壓縮 60 次（中位數每 23 分鐘一次）；每次壓縮後依 02 §3 重讀全文，共讀 `90` 168 次、`01` 150 次、`02` 136 次、`00` 101 次、`02A` 73 次、`AGENTS.md` 69 次；完整方案測試跑了 20 次（約 154 分鐘）。同一段時間，線 A 取得測試環境鎖後真正執行 D365 部署工具的時間合計只有約 4 分鐘。慢的不是測試環境，是輸出太大 → 壓縮 → 重讀全文 → 又壓縮的循環。以下三條用來打斷這個循環，安全規則與 02 §4 守門內容都不變。

### 10.1 輸出瘦身

1. 每個指令印進對話的內容，以約 100 行或 8,000 字為上限。
2. 會產生大量輸出的指令（`dotnet build`／`dotnet test`、部署工具、遠端腳本、`git log`／`git diff`），完整輸出一律寫進 repo 外的 `C:\ProgramData\SpeechMessage\evidence\` log 檔；對話只印 exit code、通過／失敗數、用 `Select-String` 篩出的錯誤行或最後 20～40 行，以及 log 的 SHA-256。
3. 不整份讀超過約 200 行的檔案；用 `Select-String`（可加 `-Context`）或指定行號範圍，只讀需要的段落。
4. log 檔照舊不得含秘密、完整個資與 LINE userId；報告只寫 SHA-256，不貼原始 log（00 §2 第 8 條）。

### 10.2 續跑精簡（取代 02 §3「續跑」第 1 點）

1. `AGENTS.md` 由 Codex 在對話開始時自動載入，壓縮後仍保留在對話中，**不必再用指令重讀**；只有整合分支有新提交改到 `AGENTS.md` 時才重讀。
2. 壓縮後續跑只讀：自己的狀態檔、自己決策紀錄的最後 20 行、`需要你協助.md` 最新 5 列、目前這一步在 01 或 02A 的那一段（用 `Select-String` 找標題後只讀該段）；02 §3 第 2～4 點照舊。
3. 00、01、02、02A 的全文只在兩種情況重讀：①開始一個新工作包；②整合分支有新提交改到該檔（用 `git log -1 --format=%h -- <檔案>` 和上次讀時記下的提交比對）。
4. `90_工作包清冊.md` 只在更新自己那一列時，用 `Select-String` 讀自己那幾列；不讀全文。

### 10.3 測試分層（補充 02 §4 第 2 步與 02 §5.2 的執行時機）

1. **開發中**只跑受影響的測試專案或篩選（例如 `dotnet test <測試專案> --filter <相關類別或名稱>`），不跑全方案。
2. **全方案守門**（02 §4 第 2 步整段指令）只在這些時間點跑：①送外部審查之前；②審查修正後、送下一輪審查之前（每輪一次，不是每改一處一次）；③依 02 §5.2 rebase 後有新的**程式**變更時。
3. **只有文件變更時不重跑建置與一般測試**：和上一次全方案守門通過時的樹相比，差異（包含自己的修改與 rebase 進來的提交）只有 `.md`、`wp-reports/` 底下的檔案、`90_工作包清冊.md`、`實作進度資料-線?.js` 時，只重跑檔案說明檢查、編碼檢查與進度頁測試（`node --test tools/RepoQuality/Tests/Test-ProgressPage.cjs tools/RepoQuality/Tests/Test-ThreeProductsProgress.cjs`），沿用上一次建置與一般測試的結果，並在報告寫明沿用的是哪一次（時間與 log SHA-256）。（2026-11-28 核對：方案內的 .NET 測試不讀這些文件；只有合成的暫存 `wp-reports` 檔。）
4. 同一個樹（同一個 commit 內容）已經通過全方案守門，就不重跑。
5. 合併前仍必須有一次全方案守門通過，且當時的程式內容與要合併的內容相同（差異只限上面第 3 點的文件類檔案）。
