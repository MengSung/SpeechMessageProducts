## 1. 開工（線 A 做一次；不計入工作包；目標 1 小時）

1. 在整合工作樹確認目前提交是 `0ab4c2fd` 或之後。`git status --porcelain` 只允許下列變更：
   - `.ccg\` 底下：屬於其他工具的狀態檔。不動、不提交、不還原。
   - 本計畫 1.3 的變更：`文件\規劃設計書\產品規劃書\只有三大產品共通的底層\` 與 `文件\規劃設計書\_封存_請勿依據\實作計畫-三大產品共通層-1.2\`。

   有其他變更時，不 stash、不 reset，依 §7 第 4 項找使用者。
2. 把 `AGENTS.md` 的「## 現行實作計畫唯一依據（…）」整節換成下面這段，原文照抄。這一節是檔案的最後一節，換到檔案結尾為止，結尾保留一個 CRLF。

```markdown
## 現行實作計畫唯一依據（2026-11-25）

實作計畫只依 `文件\規劃設計書\產品規劃書\只有三大產品共通的底層\實作計畫-三大產品共通層-1.3\`（00、01、02、90）。`_封存_請勿依據\` 只供查閱，不得作為依據或修改；實作計畫 3.5 已於 2026-11-22 到達專案終點，共通層 1.2 已由 1.3 取代，兩者都只供查閱。整體路線參考 `文件\規劃設計書\產品規劃書\完整三大產品\實作計畫-三大產品-2.5\`，不據以開新工作包。
使用者 2026-11-25 授權兩條平行線（兩個 Codex 對話框）依 1.3 全自動執行共通層（P0 的 Codex 項目、F0–F12、FS、M1）；到達 1.3 的 02 §9 終點後停止，下一階段（G1）需使用者另行授權。進度記在 90 的狀態欄。全程不得連線任何正式組織（含 D365 8.2 現行正式組織）、正式 Channel 或正式金流。
```

3. 提交。只加這些路徑，不得用 `git add -A` 或 `git commit -a`：

```powershell
$integ = 'D:\音訊科技產品\系統平台\SpeechMessageProducts\.worktrees\1.0.0.12.GoodShepherd2.0.Worktree'
git -C $integ add -- AGENTS.md "文件/規劃設計書/產品規劃書/只有三大產品共通的底層" "文件/規劃設計書/_封存_請勿依據/實作計畫-三大產品共通層-1.2"

git -C $integ ls-remote origin 1.0.0.12.GoodShepherd2.0.Worktree
git -C $integ rev-parse HEAD
```

   最後兩行的 SHA 必須相同。使用者若已自行提交計畫，只會加入 `AGENTS.md`。

4. 從剛推送的提交建立兩個工作樹。已存在就不要重建；分支已存在就直接用。


5. 建立 `C:\ProgramData\SpeechMessage\lanes\` 與 `C:\ProgramData\SpeechMessage\locks\`，寫自己的狀態檔（§3），建立 `需要你協助.md`（§7 的表頭）。
6. 做 §6 的開工檢查，把結果寫進 `需要你協助.md`。缺項不停工。

User Secrets 存在使用者設定檔，兩個工作樹共用同一份；任何秘密值都不印出、不寫進 repo。

## 2. 每一包的循環

1. **開工**：
   - 讀 01 該包。
   - 在狀態檔寫上工作包、步驟，以及「預計修改的既有檔案」（照 01 該包的 Modify 列）。
   - 把整合分支 rebase 進來：`git -C <自己的工作樹> rebase 1.0.0.12.GoodShepherd2.0.Worktree`。
   - 把 `git -C <自己的工作樹> rev-parse HEAD` 記成「本包起點」，寫進狀態檔。
2. **實作**：照 01 的步驟、時間盒與驗收條件做。要用測試環境時先取得測試環境鎖（§5），用完立刻放開。
3. **閘門**：§4 全部通過。
4. **回報**：
   - 寫一頁 `wp-reports/3P-<WP>-<名稱>.md`，加一節「手機待驗」。
   - 更新 90 自己那一列：狀態、待補、日期時間（Asia/Taipei）、提交 SHA。
   - 更新本資料夾裡自己的進度資料檔（線 A：`實作進度資料-線A.js`；線 B：`實作進度資料-線B.js`）：
     - 本包的狀態（與 90 相同的值）、開始與完成時間、提交 SHA、待補、報告路徑（從 repo 根目錄算起，例如 `wp-reports/3P-F0-基線矩陣.md`）；
     - 同時把自己的下一包改成「進行中」並填開始時間；
     - 在 `log` 最前面加一筆以 `YYYY-MM-DD HH:mm Asia/Taipei (UTC+08:00)｜` 開頭的紀錄，並更新 `lastUpdated`；舊紀錄不刪。
     - 只改自己那一檔，兩條線都不改 `實作進度.html`。這兩個檔是 2026-11-25 22:15 之後才加入的；分支裡還沒有時，先 rebase 整合分支。
     - 改完用瀏覽器開 `實作進度.html`，頁首不能有紅色警告。
   - 提交 `<WP> docs: 驗收報告`。
5. **合併**：照 §5 的合併鎖流程合併、推送，更新狀態檔。
6. 立刻開始下一包。

## 3. 狀態檔與續跑

**狀態檔**：每條線只寫自己的 `lane-A.md` 或 `lane-B.md`，可以讀對方的。每個步驟開始時、工作中至少每 30 分鐘、等待時每次檢查後都更新。每次更新狀態檔之後，再執行一次 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "%USERPROFILE%\.speechmessage\Update-3PLiveProgress.ps1" -Once`（約 30 秒，只寫 `C:\ProgramData\SpeechMessage\lanes\live-*.js`，讓使用者的即時進度頁更新；2026-11-26 使用者要求）。這一步失敗不影響工作、不重試、不算守門。狀態檔與 `需要你協助.md` 一律 UTF-8（無 BOM）、每個欄位獨立一行、CRLF 換行；用 PowerShell 寫入時用 `[IO.File]::WriteAllLines(<路徑>, <字串陣列>, (New-Object Text.UTF8Encoding($false)))`，不要把多行接成一個字串，也不要用 Windows PowerShell 5.1 的 `Set-Content`／`Out-File` 預設編碼；寫完讀回確認行數（2026-11-26 曾寫成單一行）。固定八行：

```text
更新：2026-12-01 10:15 Asia/Taipei (UTC+08:00)
工作包：F1
本包起點：<SHA>
步驟：Step 3 實作
預計修改的既有檔案：LineMessagingProcessor.AspNetCore/Webhooks/WebhookServiceRegistration.cs；…
狀態：進行中（其他可用值：等待 F2（線 B）／等待使用者／完成）
最後合併：<本線在整合分支上最後一個提交的 SHA>
下一步：Step 4 執行確認通過
```

**續跑**：每一輪開始時、內容被壓縮之後，都先做這一步。**2026-11-28 起，第 1 點改依 `02A_實機打通補充.md` §10.2（不重讀 `AGENTS.md`；00／01／02／02A 只在開新包或該檔有新提交時重讀全文）；輸出大小依 §10.1。**

1. 讀 `AGENTS.md`、00、本檔、自己的狀態檔與自己的決策紀錄。
2. 執行 `git -C <自己的工作樹> log --oneline -20` 與 `git -C <自己的工作樹> status`，再讀未完成的報告草稿。
3. 從第一個沒完成的步驟接著做。已合併的包不重做，已通過的守門不重跑。
4. 鎖檔寫的是自己這條線、但狀態檔顯示沒在用，就是自己上一輪留下的，刪掉它。

**每條線各自的紀錄檔**（避免兩條線同時改同一個檔）：`wp-reports/3P-決策紀錄-線A.md`、`-線B.md`；`wp-reports/3P-之後再說-線A.md`、`-線B.md`。

## 4. 自動閘門（取代「停下等使用者核准」）

照順序做，指令照抄。

1. **驗收條件**：01 該包每一條 Expected 與測試名稱都有結果，寫在報告裡。
2. **守門**：在自己的工作樹執行，每一行都必須 exit 0。（2026-11-28 起，什麼時候跑全方案、只有文件變更時可沿用上次結果，依 `02A_實機打通補充.md` §10.3；守門內容本身不變。）

```powershell
Set-Location "<自己的工作樹>"
dotnet build ".\SpeechMessageProducts.sln" -c Release
dotnet test ".\SpeechMessageProducts.sln" -c Release --filter "Category!=P7Live&Category!=P8Live&Category!=PaymentsLive&Category!=SqlIntegration&Category!=Live3P"
python tools/RepoQuality/check_file_documentation.py
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools\RepoQuality\Test-TextEncoding.ps1 -Scope Changed -Base <本包起點>
dotnet sln ".\SpeechMessageProducts.sln" list
```

   - **測試篩選一定要照抄這一行（2026-11-25 22:30 修正）**：各測試專案的 runsettings 原本就排除 P7Live、P8Live、PaymentsLive、SqlIntegration，但命令列加了 `--filter` 會蓋掉 runsettings，所以篩選必須自己列出全部。P7Live、P8Live、PaymentsLive 是 3.5 時期對 goodshepherdback 與永豐沙箱的實機測試，本階段一律不跑；SqlIntegration 照原本的基線排除。只跑本包實機測試的指令（`Category=Live3P&WP=…`）不受影響。
   - 檔案說明檢查的基線是 0 失敗；有失敗就修到 0，不得擴張排除範圍。
   - **本包的實機測試**：§6 的準備事項齊了才跑，而且必須通過；缺項時在報告與 90 的「待補」寫「實機待補：<缺什麼>」。指令如下（取得測試環境鎖後執行）：

```powershell
dotnet test ".\SpeechMessageProducts.sln" -c Release --filter "Category=Live3P&WP=<本包編號>"
```

   - **失敗的守門不是環境限制**：建置、一般測試、檔案說明、編碼任何一項失敗都要修好，不得寫成「已知限制」放行。
3. **外部審查**（Claude 只回 Critical／High）：
   - 先 `Set-Location "<自己的工作樹>"`，再寫提示檔 `.ccg\dual-model-runs\3P-<WP>-review-input.md`（該資料夾已被 `.gitignore` 排除）。內容：
     - 本包起點到 HEAD 的差異範圍；
     - 01 該包的驗收條件；
     - 00 §2 第 4 條停止放行清單；
     - 一句「只回 Critical／High；不得新增完成定義」。
   - 提示檔不得放入任何秘密值。執行（照抄）：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\docs\scripts\Start-CcgDualModelRun.ps1" -Role reviewer -Title "3P-<WP>-lane-<a 或 b>" -PromptFile ".\.ccg\dual-model-runs\3P-<WP>-review-input.md" -RepositoryPath "<自己的工作樹>" -OutputDirectory ".\.ccg\dual-model-runs" -ClaudeOnly
```

   - 報告寫「單模型（使用者指定 ClaudeOnly）」。
   - **有 Critical／High**：修好（提交 `<WP> fix: …`）→ 重跑受影響的測試與第 2 步守門 → 再審。最多 3 輪。
   - **第 3 輪後仍有**：
     - 屬於 00 §2 第 4 條停止放行的，一定要修好；修不好時依 §7 第 3 項找使用者。
     - 其餘寫進報告的「已知限制」與自己的之後再說，本包以「完成（縮減）」結案。
   - **Medium／Low**：只寫進之後再說。
   - **審查入口失敗**：依 `AGENTS.md` 修本機工具後重跑一次。仍沒有可用輸出時，依 `.trellis\spec\guides\cross-user-isolation-and-performance-review.md` 自審，報告寫「未取得外部審查」，繼續做；終點的整體審查會再涵蓋。

**時間盒與落後**：照 00 §2 第 5、14、15 條自動處理，不必問。每次延後或縮減都寫一行決策紀錄，並在 `需要你協助.md` 寫一筆「通知」。

## 5. 合併、鎖、等待與共用檔

### 5.1 測試環境鎖

「測試環境」包括：
- D365 測試組織（goodshepherd20、construction、association）的佈署與資料寫入；
- VM 上的 2.0 測試站與平台 SQL；
- 本機 Node 轉接程式；
- 對 T01、T02、好管家 Channel 的推播與宮格操作。

同一時間只給一條線用。用之前先把整合分支 rebase 進來再部署，才不會把另一條線剛合併的成果蓋掉。**2026-11-28 起，這把單一鎖改為 `02A_實機打通補充.md` §8 的三把資源鎖（D365＋IIS、平台 SQL、LINE）；與本節衝突時以 02A 為準。**

```powershell
$lock = 'C:\ProgramData\SpeechMessage\locks\test-env.lock'
New-Item -ItemType Directory -Force (Split-Path $lock) | Out-Null
```

### 5.2 合併鎖

`C:\ProgramData\SpeechMessage\locks\integration-merge.lock`，取得與放開的寫法同 5.1。

1. **不持鎖**：在自己的工作樹 rebase 整合分支，跑一次 §4 第 2 步的守門。
2. **取得合併鎖**後再 rebase 一次：
   - 整合分支沒有新提交：直接做第 3 步。
   - 有新提交：重跑建置與一般測試（仍持鎖）。
3. **在整合工作樹合併**：
   1. `git merge --ff-only cl/lane-<a 或 b>`
   2. `git push origin 1.0.0.12.GoodShepherd2.0.Worktree`
   3. 用 `git ls-remote` 核對
   4. 放開合併鎖，更新狀態檔
4. **合併被擋住**：整合工作樹有「這次合併會碰到的檔案」的未提交修改時：
   - 不 stash、不 reset、不丟棄；
   - 放開鎖，依 §7 第 4 項找使用者；
   - 只有 `.ccg\` 底下有修改時，照常合併。

### 5.3 等待另一條線

- 下一包要先完成的包還沒進整合分支時：先看自己這條線後面，有沒有「要先完成的包都已合併」的包。有就先做，沒有就等。
- 等待時每 10 分鐘檢查一次整合分支：執行 `git -C <整合工作樹> log --oneline`，找以該包編號開頭的提交。單次 `Start-Sleep` 不超過 300 秒。
- 等待期間可以讀程式，也可以在自己的工作樹寫下一包的測試草稿。不得替另一條線實作，也不得改它的檔。
- 另一條線的狀態檔超過 2 小時沒更新，而且狀態不是「完成」、「等待…」或「等待使用者」：視為那條線停了。
  - 在 `需要你協助.md` 寫一筆「不必停」，請使用者到那個對話框回「繼續」。
  - 自己照常等，或先做別的。
- 測試環境鎖被對方持有超過 2 小時，而且對方狀態檔超過 1 小時沒更新：同上。不得刪除別人的鎖。

## 7. 什麼時候找使用者（只有這些）

**不必停**（寫進 `需要你協助.md` 後繼續做別的）：

**要停**（該條線停下，在對話框用一則短訊息說明要使用者做什麼，並寫進 `需要你協助.md`）：

2. **秘密進了提交**：秘密包括 token、密碼、金鑰、LINE userId。
   - 還沒推送：不推送、停止、回報移除方式。
   - 已推送：一樣回報。
3. **停止放行修不好**：00 §2 第 4 條的情況在 1.5 倍時間盒內修不好，而且自己這條線沒有其他可做的包。
4. **合併或 rebase 卡住**：整合工作樹有會被合併碰到的他人未提交修改；或 rebase 衝突無法依 §5.4 的規則處理。

6. **使用者說「停」**。

4. 範圍小的優先：改得少、新檔少；01 沒指定的套件與專案不新增。
