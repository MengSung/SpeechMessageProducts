## 1. 開工（只做一次）

前提：使用者已同意，本資料夾與 `AGENTS.md` 的切換已提交到整合分支（00 §6）。由**線 A** 執行；線 B 等 `cl-lane-b` 出現後才開始。

```powershell
git -C "D:\音訊科技產品\系統平台\SpeechMessageProducts\.worktrees\1.0.0.12.GoodShepherd2.0.Worktree" log -1 --oneline
git -C "D:\音訊科技產品\系統平台\SpeechMessageProducts\.worktrees\1.0.0.12.GoodShepherd2.0.Worktree" worktree add "D:\音訊科技產品\系統平台\SpeechMessageProducts\.worktrees\cl-lane-a" -b cl/lane-a 1.0.0.12.GoodShepherd2.0.Worktree
git -C "D:\音訊科技產品\系統平台\SpeechMessageProducts\.worktrees\1.0.0.12.GoodShepherd2.0.Worktree" worktree add "D:\音訊科技產品\系統平台\SpeechMessageProducts\.worktrees\cl-lane-b" -b cl/lane-b 1.0.0.12.GoodShepherd2.0.Worktree
```

- 兩個工作樹各自 `dotnet restore`；User Secrets 存在使用者設定檔，兩個工作樹共用同一份（administrator 帳密只放這裡，不寫進 repo、不印出）。
- 工作樹已存在時不要重建；`cl/lane-a`、`cl/lane-b` 分支已存在時直接使用。

## 2. 每一包的循環

1. 每一包開始前：把整合分支的最新內容併進自己的分支（git rebase 1.0.0.12.GoodShepherd2.0.Worktree）。
2. 照 01 的步驟做；需要用測試環境（D365 測試組織、2.0 測試網站、平台 SQL）時，先取得共用鎖，用完立刻放開。
3. 做完寫一頁報告，停下來等使用者核准（Claude 會先審過一次）。
4. 使用者在那個對話框回「核准 F3」→ Codex 再 rebase 一次、全方案建置與測試通過 → 快轉合併到整合分支並推送；另一條線剛好也在合併時，快轉會失敗，就重來一次。
5. 要先完成的包在另一條線還沒合併時，就等；不能替另一條線做。

開始一包前、以及核准後合併前，都先把整合分支併進來：

```powershell
git -C "<自己的工作樹>" rebase 1.0.0.12.GoodShepherd2.0.Worktree
```

使用者回「核准 <工作包>」後：

```powershell
git -C "<自己的工作樹>" rebase 1.0.0.12.GoodShepherd2.0.Worktree
dotnet build "<自己的工作樹>\SpeechMessageProducts.sln" -c Release
dotnet test "<自己的工作樹>\SpeechMessageProducts.sln" -c Release --filter "Category!=P8Live&Category!=Live3P"
dotnet sln "<自己的工作樹>\SpeechMessageProducts.sln" list
git -C "D:\音訊科技產品\系統平台\SpeechMessageProducts\.worktrees\1.0.0.12.GoodShepherd2.0.Worktree" merge --ff-only cl/lane-<a 或 b>
git -C "D:\音訊科技產品\系統平台\SpeechMessageProducts\.worktrees\1.0.0.12.GoodShepherd2.0.Worktree" push origin 1.0.0.12.GoodShepherd2.0.Worktree
```

- 快轉合併失敗（另一條線剛合併）：回到 rebase 重來。
- 整合工作樹有未提交的修改擋住合併：停下來回報使用者，不得 stash、reset 或丟棄任何修改。
- rebase 衝突：依第 4 節處理；處理不了就停下來回報，不得用 `--theirs`／`--ours` 整批覆蓋。

## 3. 測試環境共用鎖

- 測試環境同一時間只給一條線用：用之前建立鎖檔 C:\ProgramData\SpeechMessage\locks\test-env.lock（寫上線別、工作包、開始時間），用完刪掉；看到別人的鎖就等，超過 2 小時沒放開就回報使用者。
- 用測試環境前，先把整合分支最新內容併進來再部署，才不會把另一條線已核准的成果蓋掉。
- FS 也會把佈署專案的寫入鎖改到這台電腦共用的位置，讓兩個工作樹對同一個 D365 組織的寫入一定排隊（程式層的保險）。
- 測試 Channel：線 A 用 T01、T02；線 B 用 T03。測試租戶代碼：線 A 用 c1xx、線 B 用 c2xx；清理時只清自己的前綴。

```powershell
$lock = 'C:\ProgramData\SpeechMessage\locks\test-env.lock'
New-Item -ItemType Directory -Force (Split-Path $lock) | Out-Null
# 取得：檔案不存在才建立；已存在就等，不得刪除別人的鎖
"lane=A wp=F3 start=$(Get-Date -Format o)" | Out-File -FilePath $lock -NoClobber -Encoding utf8
# 用完放開（只刪自己建立的鎖）
Remove-Item $lock
```

- 「測試環境」包括：D365 測試組織（goodshepherd20、construction、association）的佈署與資料寫入、2.0 測試網站（IIS）的部署、平台 SQL、對測試 Channel 的推播與宮格建立。
- 用測試環境前先把整合分支併進來再部署，才不會把另一條線已核准的成果蓋掉。
- M1 在兩條線都完成後才做，只有線 A 一條，可以使用 c001、c002、b001、b002 這幾個代碼。
