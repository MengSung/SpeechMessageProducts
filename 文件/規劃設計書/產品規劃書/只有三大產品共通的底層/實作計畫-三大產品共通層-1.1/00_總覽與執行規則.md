## 2. 固定規則（不得自行變更）

1. **完成定義（五項，不加碼）**：①一頁規格／本計畫列出的驗收條件全部通過；②自動測試（含跨教會隔離測試）全綠、全方案建置通過；③測試環境實機驗收報告一頁，附截圖；④檔案說明、UTF-8 無 BOM、CRLF、資源釋放符合 `AGENTS.md`；⑤使用者審核通過。
2. **狀態只能照階梯宣稱**：程式完成 → 自動測試通過 → 測試環境驗證 → Pilot 通過 → 正式可用。最後一階需要使用者另行授權。
3. **證據等級**：每個「已有／已驗證」的說法要能指到測試名稱、log 的 SHA-256 或截圖；否則寫「待驗證」。
4. **立即停止放行**（任一發生就停下、修好才繼續）：跨教會／Channel／產品／使用者外洩；合法不同 ID 被合併或重複 ID 被靜默吃掉；停止、取消、逾時後資源沒回基線；秘密或完整個資進 log；出現 broadcast 呼叫或推播混入他教會 userId；宮格無上限建立或實際數與帳上不一致仍配發；測試誤連正式組織、正式 Channel 或正式金流；真正失敗沒有告警或無法追查。
5. **時間盒**：每個 WP 以計畫標示的工作天為上限。到期可延長到 1.5 倍，只用來完成驗收條件；仍做不完就把未完成的驗收條件寫進「之後再說」或計畫修正提案，WP 以「已驗收（縮減）」結案並在回報中列明縮減了什麼。
6. **平行上限**：同時最多兩個 WP；兩個必須互不相依、不改同一個檔案（D31）。
7. **提交**：一個提交只屬於一個 WP，訊息以 WP 編號開頭；會讓方案建置失敗的內容不得提交；WP 驗收後才推送（D30）。
8. **回報**：每個 WP 一頁（`wp-reports/3P-<WP>-<名稱>.md`）：每條驗收條件的結果、截圖、已知限制；原始 log 不進 repo，只寫 SHA-256（D32）。
9. **新點子**：寫進 `wp-reports/3P-之後再說.md`，不在當輪做；計畫只由使用者改版（D35）。
10. **環境**：D365 9.1 三個產品組織（好牧人 `goodshepherd20`、好管家 `construction`、好學會 `association`，2026-11-25 已建立）上線前都是測試組織；開發測試期間三個組織共用 administrator 連線（帳密只放 User Secrets 或開發設定檔，不印出、不進 log 或回報；轉正式前依 D16 決定是否換成各產品專屬帳號）；goodshepherd20 由 goodshepherdback 複製，G5-2 前仍有複製帶來的會友資料（實機只用 F12 測試租戶、推播只推測試租戶）；建設公司與協會組織只放合成資料；轉正式（G5-2、H-10、I-11）後開發改連各自的測試複本，正式組織只能在使用者逐次核准下寫入；任何時候不得連 8.2 現行正式組織。LINE 官方帳號：「好牧人」＝goodshepherd20 開發專屬 Channel、「好管家」「好學會」＝各自產品池的第一個 Channel（皆 2026-11-25 已建立）；另有測試 Channel（T01–T03，待建）與永豐沙箱。實機測試標 `Category=Live3P`，不進一般測試。
11. **自主範圍**：Codex 依 `AGENTS.md` 與 D24 自行操作測試環境（含 D365-9.1、閘道設定），事後留一頁紀錄。只有下列情況找使用者：P0 標「使用者」的項目、規劃 v2.5 第 18 章的決策（D1–D18；D10、D13、D14 已定案）、任何正式環境作業、停止放行條件發生且無法在時間盒內修好。
12. **租戶**：三個產品都是「一個組織、很多租戶」；共用引擎介面一律用 `TenantId`；每筆業務資料必掛租戶；A 租戶的任何資料 B 租戶讀不到、寫不到；金流商店與電子發票開立人依租戶分開。名額池程式三個產品共用，但每個產品只有自己的 Channel 池（好牧人池在 goodshepherd20、好管家池在 construction、好學會池在 association），配發只從本產品的 Channel 挑，互不混用；好管家、好學會是產品共用官方帳號（D14 已定案），租戶自有帳號（白牌）列之後再說。
13. **範圍凍結**：共通層就是本資料夾 90 列的 14 個工作包（F0–F12、FS）與 M1。新點子寫進 `wp-reports/3P-之後再說.md`，不在本階段做；使用者要加項目時，必須換掉一個同等大小的工作包，或明確同意延後 M1。
14. **截止日**：M1 最晚 2027-01-04（第 6 週第一天）完成。任何時候累計落後超過 3 個工作天，就依第 15 條由上往下延後，不另開會，只寫一頁回報給使用者說明延了什麼。
15. **共通層可延後清單（核定本計畫即生效）**：1. F10 永豐補強：整包移到第 6–7 週（G4 第 18 週才用到；M1 不需要）（約 4 天）；2. F11 觀測與健康：營運看板雛形移到 G4-4；追蹤編號與健康檢查保留（約 1 天）；3. F12 測試租戶：Live 版的宮格清理先手動確認，自動核對延到 G1（約 0.5 天）。平常不動，只在第 14 條觸發時使用。
16. **分工**：Codex 依本資料夾與 `AGENTS.md` 執行（寫程式、測試、佈署到測試組織、每包寫一頁報告）；Claude 負責審查每包的報告與程式差異，只回 Critical／High，不得加碼完成定義（審查依 `AGENTS.md` 的 CCG 入口執行）；使用者核定。
17. **D365 結構與畫面**：實體、欄位、表單、檢視表一律用 `SpeechMessage.Dynamics.Deployment` 建立與更新（D365 SDK，HTTPS＋ADFS）：結構走分層清單的 plan／apply／verify，畫面走分層 UI 方案或由清單產生的 FormXml／FetchXml；網頁手動只用來試做，定案一律收進 repo；WinRM 只做主機作業（建組織、IIS、服務、備份、AD 帳號）；禁止直接寫 SQL。平台層三個組織都有；教會專屬元件只進好牧人產品層。發布前列出該範圍所有未發布變更，有不在計畫裡的就停止，不用 PublishAllXml；每個表單、檢視表記錄 FormId／SavedQueryId 與 XML 雜湊，不依顯示名稱覆寫。新實體建立時就定擁有權類型（建立後不能改）：租戶業務資料用「使用者或小組擁有」，平台技術資料（Channel、名額、配發鎖、發送紀錄）用「組織擁有」。
18. **宮格預算與速率**：每個 Channel「系統保留＋所有租戶使用中的宮格＋一個租戶的換版暫存 ≤ 1,000」，超出就 fail closed；模板換版一律逐租戶進行；建立與刪除宮格各為每 Channel 每小時 100 次（LINE 官方參考，2026-11-25 查證），開通、換版、清理都由排程器依 Channel 分批。好牧人每教會宮格上限 45，實際數量在 G1-4 依流程圖計算；好管家、好學會各自計算。
19. **D365 後台人員**：經 LINE／LIFF／網頁進來的人由程式驗證租戶；直接登入 D365 的人由 D365 原生權限（安全性角色、擁有者小組、業務單位）決定，Account 欄位與檢視表篩選不是安全邊界。租戶人員是否直接登入依 D17；若會，驗收必含其他檢視、進階尋找、查閱、匯出與 API 都不越權。
