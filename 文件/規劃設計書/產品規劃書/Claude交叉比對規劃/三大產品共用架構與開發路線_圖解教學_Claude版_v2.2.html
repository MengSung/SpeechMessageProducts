  • 蓋法：先打一層薄地基（13 包），再把好牧人 2.0 的功能一個一個做、一個一個實機驗收、你審核通過才往下；建設公司或協會也會用到的，第一次做就放進共用層。
  • Pilot：約 10 間全新試用教會，分三波進場（1 間 → 3 間 → 10 間），每一波都要通過驗收清單才進下一波；Pilot 前要完成 41 個工作包。

  • 每個說法都標證據等級：「你已決定」「已驗證（P8 有測試或實機證據）」「程式存在、待驗證」「建議」「本階段不做」；狀態只能照五級階梯宣稱，不可越級。
  • 每個功能固定五項完成定義；隔離、重複、資源釋放寫成自動測試，不靠每次人工審查；出現跨教會外洩、重複 ID 被吃掉、資源不回收、機密進 log 等情況立即停止放行。

05目標分層架構與依賴修正

✔ 已有｜△ 要改（粗框）｜＋ 新做（虛線框）；有顏色框線的是某一產品專屬。

白話說明就像大樓：上層可以踩在下層上，下層不能吊在上層。現在有兩塊「共用」的地板反過來掛在好牧人的房間上，建設公司和協會一搬進來就會被拖著走，所以地基第一件事就是把它拆開。
架構規則
  • 上層可以參考下層；下層永遠不參考上層。
  • 產品之間不互相參考（2.0 不參考 ChurchReport，報修不參考協會）。
  • 共用層不得參考任何產品領域層或產品層；用架構測試在 CI 擋住。
  • 新專案名稱都是暫定；新增 .csproj 必須當下加入 SpeechMessageProducts.sln（AGENTS.md 規則）。
  • 每個產品自己的 IIS 應用程式集區、服務帳號、Webhook 主機、D365 9.1 組織；組織上線前當測試用、上線時照固定步驟轉正式；共用的是程式庫，不是資料、連線或身分。
  • 每個產品自己的 Plugin／Workflow 組件，共用 net462 規則程式庫（教會沿用現有兩個組件）。

第一件要修的：依賴方向（F1）

06四層隔離：一個請求要穿過四道門

白話說明同一個 Channel 裡有 20 間教會，所以「這個人屬於哪間教會」永遠由伺服器查出來，不能相信手機送來的教會代碼。每道門都有對應的自動測試。
邊界要分開的東西
產品各自 IIS 應用程式集區、服務帳號、Webhook 主機、D365 組織、平台 SQL 資料庫、告警路由；D365 連線子池依產品分開。
Channel逐 Channel 驗簽；token 依 Channel 解密；事件冪等鍵＝產品＋Channel＋webhookEventId；宮格 ID 屬於 Channel。
租戶所有業務資料必掛租戶；伺服器由「Channel＋userId」或 LIFF 身分找租戶，postback 再帶租戶代碼雙重確認；快取鍵含租戶；推播收件人必屬同租戶；alias 加租戶代碼前綴；金流商店與發票開立人依租戶分開。
使用者與角色每次請求在伺服器檢查權限矩陣（本人／本組／全教會）；Session 與 Cookie 不攜帶授權結論；快取含驗證時期（epoch）。

06AD365 9.1 三個組織與租戶設計

三個系統各一個組織；上線前都當測試組織，上線時照固定步驟轉正式。三個產品都是一個組織、很多租戶。

白話說明「上線前先當測試」的意思是：同一個組織先給 Codex 開發測試，上線那天把測試資料清乾淨、改標正式。改標之前先複製一份「只有結構」的組織給之後的開發用，這樣上線後修程式不會碰到真的資料。
組織轉正式的固定步驟
  1. 從要轉正式的組織匯出「只有結構、不含資料」的未受管理方案，匯入新的測試複本組織；佈署專案 verify 通過。
  2. 用 F12 的清理指令清掉所有測試租戶；核對業務實體筆數為 0（只留系統設定）。
  3. 輪替該組織服務帳號的密碼與所有測試用 token；測試 Channel 不再指向這個組織。
  4. 佈署專案的組織清單把它改標「正式」；之後任何寫入都要你逐次核准（ProductionGuard）。
  5. 開啟每日備份與異地保存；健康檢查全綠；你書面核准後才讓真實租戶進來。
組織誰建立當測試組織正式之後的開發環境

租戶規則
  • 每個產品組織裡，「租戶」就是一筆標記為租戶的 account（2.0＝教會、建設公司維修＝建設公司、協會管理＝協會）。
  • 每一筆業務資料都必須掛到租戶：2.0 沿用既有的教會 lookup；建設公司與協會一律用 new_tenant 欄位，由 Plugin 在建立時自動帶入、禁止改到別的租戶。
  • 伺服器由「Channel＋userId」或 LIFF 身分查出租戶，不相信手機或網址送來的租戶代碼。
  • 共用引擎（排程、推播、LIFF、圖片、權限、修改紀錄、審核、匯入、報名收費、時段預約、統計、電子發票）的介面一律用 TenantId，不出現「教會」字眼。
  • 每個租戶可以有自己的 LINE 官方帳號、永豐商店設定與電子發票開立人設定；這些設定都掛在租戶上、秘密加密保存。

14Pilot：三波進場與驗收清單

白話說明不要一次讓十間教會進來：第 1 波只有一間，把流程跑順；第 2 波再加兩間、刻意放在同一個 Channel，看三間會不會互相串；第 3 波才到十間、分兩個 Channel。
教會招募條件
  • 全新教會（不是 1.5 的教會），會友約 50–300 人；至少一位管理員、一位財務、兩位小組長願意每週回饋。
  • 同意 Pilot 同意書與個資告知；了解訊息會顯示「from 好牧人」字樣與共用 Channel 名稱。
  • 第 1 波選你最熟、溝通最快的一間；第 2 波兩間放同一個 Channel，用來驗證同 Channel 隔離；第 3 波七間分兩個 Channel。
問題分級與支援
  • P1（立即停止該功能）：任何跨教會外洩、金額錯誤、重複扣款；4 小時內回應，修好前暫停。
  • P2（3 個工作天內修）：功能錯誤但有替代做法。
  • P3（進之後再說）：體驗與建議。
  • 每週一次 30 分鐘回饋（可線上）；問題一律記在一份清單，附 correlation id。
結束與退出
  • 通過：驗收清單全過、沒有未解的 P1、十間教會至少八間願意轉正。
  • 延長：有 P2 未解或使用量不足；延長 2–4 週。
  • 退出的教會：進入保留期 30 天，期滿清理或匿名化（依個資政策），不影響同 Channel 其他教會。
驗收清單（勾選會存在這台電腦）

15什麼情況必須立刻停止放行

停 1任何跨教會、跨 Channel、跨產品或跨使用者的資料外洩（回應、快取、佇列、log、附件、匯出）。
停 2合法的不同 ID 被合併，或重複 ID 被靜默刪除、覆蓋、隱藏。
停 3Task、Timer、Stream、連線、取消註冊、佇列或連線租借在停止、取消、逾時後沒有回到基線。
停 4Token、Secret、Cookie、密碼、卡號、綁卡 Token 或完整個資進入 log、告警或錯誤訊息。
停 5程式中出現 broadcast 呼叫，或推播對象混入其他教會的 userId。
停 6宮格建立沒有上限（重試或部署一直新建），或宮格實際數與帳上不一致仍繼續配發名額。
停 7測試流程誤呼叫正式組織、正式 Channel 或正式金流。
停 8真正失敗沒有告警、無法從 correlation id 追查，或停用與清理無法執行。

20名詞小辭典

Channel（官方帳號）
一個 LINE 官方帳號；有自己的 token、secret、1,000 個宮格額度、月費方案。
名額
一個 Channel 裡可以放一間教會的位置；每個 Channel 20 個。
宮格（Rich Menu）
聊天室下方的圖片按鈕選單；每個官方帳號最多 1,000 個。
alias
宮格的代號，用來在頁籤之間切換；同一 Channel 內不能重複，所以加教會代碼前綴。
LIFF
在 LINE 裡打開的網頁，可以知道是誰在用。
sender
每則訊息可以換顯示名稱與頭像，用來顯示教會名稱與 Logo。
Webhook
LINE 把使用者的動作送到我們主機的入口。
postback
按下 Flex 卡片按鈕時，送回主機的一段資料。
Reply／Push
Reply 是回覆使用者的動作（免費）；Push 是主動推播（計費）。
broadcast
發給該官方帳號所有好友；同一 Channel 有 20 間教會，所以程式裡禁止。
冪等
同一件事送兩次，結果只發生一次。
沙箱
金流商提供的測試環境，不會真的扣款。
平台 SQL
我們自己的 SQL 資料庫，放去重、排程、佇列這類不適合放 D365 的資料。
correlation id
一個事件從頭到尾帶著的追蹤編號，出問題時用它查全部紀錄。
時間盒
每個工作包的天數上限；超過就拆小或縮減。
