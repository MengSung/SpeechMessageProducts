### 與 v3.2 Word 的一處技術修正

Word 10.9 節寫「Token 以 AES-GCM 加密」。但 .NET Framework 4.8 **沒有** `AesGcm` 類別，Plugin 端無法解密。

本計畫改用以下做法：
- **演算法：** AES-256-CBC＋HMAC-SHA256，先加密再驗證（Encrypt-then-MAC）。
- **封包格式：** 版本化，例如 `v1:`（規格見附錄 A.5）。
- **跨框架：** 4.8 與 .NET 10 都能用同一份程式。
- **安全性：** 同等。

實作時以本計畫為準，並在階段 2 結束時提醒使用者更新 Word。

## 5. 測試導向設計（TDD）：每個 WP 都必須遵守

### 5.1 三種情況，三種寫法

| 情況 | 寫法 | 例子 |
|---|---|---|
| **新程式** | 紅 → 綠 → 重構：先寫會失敗的測試並執行、確認失敗原因正確，再寫剛好讓它通過的程式，最後在測試保護下重構 | Localization、LineMessagingProcessor.Core、Tenancy、OutboundTask 認領 |
| **搬移或合併舊程式** | 先寫特性測試（characterization test）鎖住舊行為：把舊程式「現在怎麼做」錄成黃金檔，新程式必須產生相同結果；行為要改的地方，先改測試期望值並在回報說明理由 | ToolUtilityClass 副本合併、關鍵字路由、舊 Plugin 規則、PushUtility 合併 |
| **D365／外部系統整合** | 先寫契約測試（用假的 `IOrganizationService`、假的 `HttpMessageHandler`），再寫整合測試或使用者執行的驗收腳本 | Plugin 外殼、Token 解密、LINE 推播、宮格 API |

### 5.2 每個 WP 的 TDD 步驟

1. **列測試清單：** 把 WP 的「先寫的測試」列成測試方法名稱。可以增加，不可以刪除；要刪除必須說明理由。
2. **寫測試、先跑一次：** 確認全部失敗（紅）。失敗原因必須是「功能還沒做」，不能是編譯錯誤以外的環境問題。
   - 新型別還不存在時，先建只丟 `NotImplementedException` 的空殼，讓測試編得過、跑得紅。
3. **寫實作：** 每次只讓一小組測試變綠。
4. **重構：** 全部綠了之後再重構，重構後再跑一次。
5. **回報：** 在 WP 回報附上第 2 步的紅燈摘要（失敗的測試名稱與訊息）與第 4 步的綠燈摘要。範本見附錄 F。

### 5.3 測試的寫法規定

- **框架：** xUnit 2.6.6、FluentAssertions 6.12.0、Moq 4.20.70（沿用主方案版本；net48 也支援）。
- **命名：** `方法或情境_條件_預期結果`，例如 `Resolve_ChurchOverrideExists_ReturnsOverride`。可以用英文；`DisplayName` 用繁體中文。
- **測試類別與方法要有繁體中文 XML 註解（AGENTS.md 規定）**，寫明三件事：
  1. 保護的契約；
  2. 注入的失敗或錯誤情境；
  3. 決定性的斷言。
- **雙目標專案的測試在 `net48` 與 `net10.0` 各跑一次**，結果必須相同。
- **時間：** 測試不得依賴系統時間、時區、文化設定或網路。時間一律用假的時鐘（`FakeChurchClock`／`TimeProvider` 的假實作）。
- **跨教會隔離：** 每個有快取、佇列、靜態資料或背景工作的元件，都要有 A／B 教會並行測試，並斷言資源計數回到基線（AGENTS.md「跨使用者隔離」）。
- **黃金檔：**
  - 放在測試專案的 `Golden\` 資料夾，UTF-8 無 BOM、CRLF；
  - 內容不得含真實個資、Token、密碼；以假資料取代，產生器要做遮罩；
  - 黃金檔變更必須在回報說明「為什麼行為改變」。
- **覆蓋率：**
  - 新的雙目標專案與新 net10.0 專案：行覆蓋率 ≥ 80%（CI 報告，未達標視為 WP 未完成）；
  - 既有專案不設門檻，但新增或修改的程式要有測試。

### 5.4 不能單元測試的部分怎麼辦

D365 註冊、Plugin 在沙箱實際執行、LINE 實機收訊、IIS 部署、網頁版面，這些部分改用以下方式：
- **使用者執行的驗收腳本：** 逐步操作與預期結果，寫在各階段的「使用者驗收」小節；
- **自動化煙霧測試：** 由 Codex 寫好、使用者在測試環境執行的 ps1 或 console 工具。

這些也要「先寫腳本、再做功能」：腳本寫好時，功能尚未完成，執行結果應為失敗。

## 6. 分支、提交與 Trellis

### 6.1 分支

- **基底：** 目前分支 `1.0.0.10.IntegrateWebhook_SDK.worktree`（提交 `18331f3a` 之後）。
- **每個階段一個分支：** `1.0.0.11.Integration.P0`、`.P1`、…、`.P8`。
  - 下一階段從「上一階段經使用者驗收後的最後提交」開分支。
  - 用 `git worktree add` 放在 `.worktrees\1.0.0.11.Integration.P0.Worktree`，不在現有 worktree 上直接改。
- **不要用斜線命名**（例如 `1.0.0.11.Integration/P0`）：會和同名分支產生 ref 衝突。
- 不推送、不合併到 `main`，除非使用者明確要求。

### 6.2 提交

- 提交時機：每個 WP 通過驗證後，提交到該階段分支。若使用者另有指示，以使用者指示為準。
- 訊息格式：`<WP 編號> <繁體中文摘要>`，例如 `P0-04 套件版本集中管理並統一 Extensions 10.0.0`，內文列出驗證結果。
- 一個提交只做一個 WP。測試與實作放在同一個提交；紅燈證據寫在 WP 回報，不必另外提交失敗狀態。
- 禁止：`--no-verify`、跳過簽章、提交密碼／Token／`.snk`／`appsettings.*.json` 中的真實機密。

### 6.3 Trellis 任務

在階段 0 的 P0-01 建立：

```powershell
python .\.trellis\scripts\task.py create "方案整合與國際化 v3.2 實作" --slug integration-v32
python .\.trellis\scripts\task.py create "階段 0 準備守門與可行性驗證" --slug integration-p0 --parent <上一步建立的父任務目錄>
```

- 之後每個階段開始時建立一個子任務，在子任務的 `prd.md` 引用本資料夾對應的階段檔案。
- 依 `.trellis/workflow.md` 執行。

### 6.4 外部審查（AGENTS.md 規定的入口）

每個階段結束前，用專案自癒入口做一次審查；階段 0 在 P0-11 完成後、P0-12 之前執行，WP 之間以本機驗證為準，不逐 WP 重跑外部審查：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\docs\scripts\Start-CcgDualModelRun.ps1" `
  -Role reviewer -Title "integration-p0-review" `
  -PromptFile ".\.ccg\dual-model-runs\integration-p0-review-input.md" `
  -RepositoryPath "<worktree 根目錄>" -OutputDirectory ".\.ccg\dual-model-runs" `
  -AllowSingleModelWhenQuotaBlocked
```

- 不得直接呼叫 Gemini 或 Claude。
- 使用者指定的 `-ClaudeOnly` 可以作為階段審查，必須寫明「單模型（使用者指定 ClaudeOnly）」；是否雙模型完成只看 `dualModelComplete`，不得由 `ok` 或結束碼推定。
- 審查若只有單一模型完成，回報時要寫明「單模型降級」。
- 上述「單模型降級」限於配額／session fallback；使用者明確指定 ClaudeOnly 不屬於配額降級。自癒入口逾時或失敗時，準備審查包並停下等使用者回報。
- 審查發現的 Critical／High 問題必須修完，才能請使用者驗收。

## 7. 每個 WP 的固定流程

1. **讀：** 讀 `AGENTS.md`、本檔、該 WP 段落、相關附錄；用 `rg` 或 `Glob` 確認 WP 提到的檔案與行號仍然正確（行號可能已變動，以內容為準）。
2. **列：** 列出要新增或修改的檔案與測試清單；如果與 WP 描述不同，先說明原因。
3. **TDD：** 依第 5 節：紅 → 綠 → 重構，或先鎖黃金檔再搬移。
4. **文件註解：** 每個新增或實質修改的 `.cs`／`.cshtml` 都要有完整繁體中文註解（AGENTS.md）。
   - 型別、建構式、方法、重要屬性要有 XML 註解；
   - 涉及快取、佇列、計時器、串流、取消、背景工作、Token 的地方，要寫明最長生命週期、釋放路徑與跨教會隔離方式。
5. **驗證：** 依第 8 節的命令清單，全部通過。
6. **回報：** 依附錄 F 範本，寫在 Trellis 子任務資料夾的 `wp-reports\<WP 編號>.md`。
7. **提交：** 依第 6.2 節。

7. 任何會刪除或覆寫資料、跨教會讀寫、不可逆的 D365 操作（例如日期欄位行為轉換）。
