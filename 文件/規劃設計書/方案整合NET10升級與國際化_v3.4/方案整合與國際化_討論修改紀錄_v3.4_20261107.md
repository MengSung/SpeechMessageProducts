## 二、討論內容

### 1. 稽核結果（2026-11-07，快照提交 30d2f02b）
- P0（18／18）、P1（12／12）做得扎實：程式品質高，獨立重跑 4,596 個測試中 4,595 個通過。
- P2 第一天出現流程問題：最新提交無法建置（P2-09 的紅燈測試被提交）、同時做三個工作包、提交混合多包、提交後約 5 秒就推到 GitHub。
- 計畫 3.3 被 22 次提交就地修改；P2-01 的 R2 規則對 MVC 網站不可行，導致永遠無法驗收；P2-03 被自行加上實機條件而卡住。
- 流程紀錄（.ccg 31 MB、.trellis 11 MB）約是產品程式的 12 倍。

### 2. 使用者的四個選擇（2026-11-07）
- 測試環境權限：**維持全自主**，包括進 VM、SQL 備份還原。
- GitHub 推送：**工作包驗收後才推**。
- 平行：**最多 2 包，需互不相依**。
- 證據：**只留摘要，舊的保留**。

### 3. 使用者追加的要求
- 「盡量兩手放開」：除非必要或確實需要協助，全程由 Codex 伸手進 D365-9.1、D365-DC01 等主機自動處理；計畫書要寫到這個程度。→ D24 修訂、實作計畫 3.4 第 9、10、11 節；原本「使用者驗收」的步驟（P2-04 前置、P2-12、P3-09、P4-06、階段 5 影子模式、P6 頁面驗收、P7 切換、P8-04）全部改為 Codex 執行。
- 「計畫要收斂、能落地，不要無限擴張」→ D29、D35；實作計畫 3.4 每個工作包都附依賴、時間盒、實機與完成定義；專案終點寫死。
- 「計畫要詳細、深入完整，並確定能收斂及落地」→ 剩餘 53 個工作包的規格全部保留，並加上工作包總表、建議順序、關鍵路徑與路線圖（實作計畫 3.4 第 15 節）。
- 「3.4 完成後 3.2、3.3 是否移除，以免誤用」→ 採**封存**而非刪除：搬到 `文件\規劃設計書\_封存_請勿依據\`，進度頁與驗收紀錄搬進 3.4，AGENTS.md 指向 3.4（實作計畫 3.4 第 14 節）。E: 規劃資料夾的歷代設計檔照舊保留。

### 4. 仍需要使用者的時間點（其他都由 Codex 自己處理）
1. 回一句「3.4 生效」。
2. P2-04 前置之前：建立測試 LINE channel，把 `TestChannelToken`、`TestLineUserId` 放進 Deployment 的 User Secrets，手機加好友。
3. 階段 3、4 前：Codex 取不到時才需要提供正式平台 SQL 連線、永豐測試金鑰。
4. 階段 7：每個正式組織第一次寫入前回「可以」。
5. 階段 8：奉獻類別要不要合併（例如十一／什一）。
