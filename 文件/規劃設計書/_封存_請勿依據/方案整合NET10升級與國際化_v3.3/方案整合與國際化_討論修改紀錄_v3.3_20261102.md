## 二、討論內容

### 1. 新的開發測試組織 goodshepherdback（計畫書 10.14 節、圖解 08C）
- 使用者建立 https://goodshepherdback.speechmessage.com.tw，並確認它是從正式組織複製的。
- 複本帶來的風險：真實會友個資、舊 Plugin／Workflow 仍註冊、等候中的系統作業、記錄中存有正式 LINE token、舊程式寫死正式 token、會友的 LINE ID 是真的、記錄 ID 與正式組織相同。
- 使用者要先做的清理：
  1. 取消等候中的系統作業；
  2. 停用舊 Plugin 步驟與自訂流程；
  3. 清除記錄中的 LINE token，或換成測試頻道的 token；
  4. 清空會友的 LINE ID，只留自己的測試聯絡人。
- 清理完成並告訴 Codex 之前，任何程式、工具、測試都不連線。

### 2. 開發環境的安全防護（P0-SEC、P0-ENV）
- Codex 在 P0-ENV 發現：ChurchReport 有 11 個類別與 LineMessagingProcessor 自己讀基底 appsettings.json，看不到 Development 的設定，只改設定無法保證開發時不用到正式 token。
- 使用者核定另立 P0-SEC：Development 啟動守門（只能連 goodshepherdback、取不到正式 LINE token），非 Development 的行為逐鍵不變。
- 環境名稱的判斷與網站主機相同：先看 DOTNET_ENVIRONMENT，再看 ASPNETCORE_ENVIRONMENT，都沒有就是 Production（Codex 以實測確認，使用者已核定）。

### 3. 佈署改用 Solution 內的佈署專案（計畫書 10.11、10.12 節、圖解 08A）
- 使用者要求：Plugin、Workflow 的佈署改由 Solution 內新增的佈署專案完成，不再到 Plugin Registration Tool 操作。
- 佈署專案依 repo 中的清單（schema、registration）執行：plan 預覽 → 使用者審核 → apply 執行 → verify 比對 → smoke 實測；可 export 備份、rollback 回復、switch 切換新舊步驟。
- 原計畫的三個工具（D365Provisioning、ShadowCompare、D365StepSwitch）併入這一個專案。
- 階段 0 的 P0-12 改為「佈署專案最小版」，先驗證從 .NET 10 能對地端 9.1 完成註冊。

### 4. 先在 Solution 內測，再到測試組織（計畫書 10.13 節、圖解 08B）
- 使用者希望能在 Solution 內測的先在 Solution 內測。
- 五層驗證：L0 單元測試、L1 佈署規劃測試、L2 清單與 DLL 一致性都不需要 D365；L3 才到 goodshepherdback；L4 是正式組織。
- 使用者可以配合在 goodshepherdback 建立實體與欄位；改由佈署專案建立後，使用者只需審核 plan、執行 apply，表單版面等畫面工作仍在 D365 畫面完成。

### 5. 實作計畫的版本資料夾
- 使用者把原本的 `實作計畫\` 改為 `實作計畫-3.2\`（凍結），並複製出 `實作計畫-3.3\`。
- v3.3 的計畫修改只寫在 `實作計畫-3.3\`；進度頁以 `實作計畫-3.3\實作進度.html` 為準。
