### 與 v3.2 Word 的一處技術修正（v3.3 Word 已更正）

v3.2 Word 10.9 節寫「Token 以 AES-GCM 加密」。但 .NET Framework 4.6.2 **沒有** `AesGcm` 類別，Plugin 端無法解密。v3.3 Word 已改為下列做法，也已改成「一個 Channel 可由多間教會共用、由教會指向 Channel」（附錄 A.3）。

本計畫改用以下做法：
- **演算法：** AES-256-CBC＋HMAC-SHA256，先加密再驗證（Encrypt-then-MAC）。
- **封包格式：** 版本化，例如 `v1:`（規格見附錄 A.5）。
- **跨框架：** 4.6.2 與 .NET 10 都能用同一份程式。
- **安全性：** 同等。

實作時以本計畫為準。

## 5. 測試導向設計（TDD）：每個 WP 都必須遵守

### 5.1 三種情況，三種寫法

| 情況 | 寫法 | 例子 |
|---|---|---|
| **新程式** | 紅 → 綠 → 重構：先寫會失敗的測試並執行、確認失敗原因正確，再寫剛好讓它通過的程式，最後在測試保護下重構 | Localization、LineMessagingProcessor.Core、Tenancy、OutboundTask 認領 |
| **搬移或合併舊程式** | 先寫特性測試（characterization test）鎖住舊行為：把舊程式「現在怎麼做」錄成黃金檔，新程式必須產生相同結果；行為要改的地方，先改測試期望值並在回報說明理由 | ToolUtilityClass 副本合併、關鍵字路由、舊 Plugin 規則、PushUtility 合併 |
| **D365／外部系統整合** | 先寫契約測試（用假的 `IOrganizationService`、假的 `HttpMessageHandler`），再寫整合測試或使用者執行的驗收腳本 | Plugin 外殼、Token 解密、LINE 推播、宮格 API |

### 5.2 每個 WP 的 TDD 步驟

1. **列測試清單：** 把 WP 的「先寫的測試」列成測試方法名稱。可以增加，不可以刪除；要刪除必須說明理由。
2. **寫測試、先跑一次：** 確認全部失敗（紅）。失敗原因必須是「功能還沒做」，不能是編譯錯誤以外的環境問題。
   - 新型別還不存在時，先建只丟 `NotImplementedException` 的空殼，讓測試編得過、跑得紅。
3. **寫實作：** 每次只讓一小組測試變綠。
4. **重構：** 全部綠了之後再重構，重構後再跑一次。
5. **回報：** 在 WP 回報附上第 2 步的紅燈摘要（失敗的測試名稱與訊息）與第 4 步的綠燈摘要。範本見附錄 F。

### 5.3 測試的寫法規定

- **框架：** xUnit 2.6.6、FluentAssertions 6.12.0、Moq 4.20.70（沿用主方案版本；net48 也支援）。
- **命名：** `方法或情境_條件_預期結果`，例如 `Resolve_ChurchOverrideExists_ReturnsOverride`。可以用英文；`DisplayName` 用繁體中文。
- 嚴格測試專案的 CA1707 例外由 Directory.Build.targets 統一處理（使用者 2026-11-03 核定），其他規則不變。
- **測試類別與方法要有繁體中文 XML 註解（AGENTS.md 規定）**，寫明三件事：
  1. 保護的契約；
  2. 注入的失敗或錯誤情境；
  3. 決定性的斷言。
- **雙目標產品專案的測試須覆蓋 `net462` 與 `net10.0` 兩個產品輸出**，結果必須符合相同契約；測試執行器可留在 `net48`，但必須由測試確認引用的 Framework 產品組件確為 net462。
- **時間：** 測試不得依賴系統時間、時區、文化設定或網路。時間一律用假的時鐘（`FakeChurchClock`／`TimeProvider` 的假實作）。
- **跨教會隔離：** 每個有快取、佇列、靜態資料或背景工作的元件，都要有 A／B 教會並行測試，並斷言資源計數回到基線（AGENTS.md「跨使用者隔離」）。
- **黃金檔：**
  - 放在測試專案的 `Golden\` 資料夾，UTF-8 無 BOM、CRLF；
  - 內容不得含真實個資、Token、密碼；以假資料取代，產生器要做遮罩；
  - 黃金檔變更必須在回報說明「為什麼行為改變」。
- **覆蓋率：**
  - 新的雙目標專案與新 net10.0 專案：行覆蓋率 ≥ 80%（CI 報告，未達標視為 WP 未完成）；
  - 既有專案不設門檻，但新增或修改的程式要有測試。

### 5.4 不能單元測試的部分怎麼辦

先盡量在 Solution 內測（五層驗證，設計 10.13 節）：
- **L0 單元測試：** 規則（雙目標）、Plugin 外殼（假的 `IOrganizationService`、假的執行內容）、Workflow 活動（`WorkflowInvoker`）、黃金資料對照；
- **L1 佈署規劃測試：** 佈署專案的 plan 比對邏輯，用假的組織結構與 `d365\snapshots\goodshepherdback\` 的結構快照離線執行；
- **L2 清單與 DLL 一致性：** 讀取建置出的 DLL，比對清單與外掛類別、篩選欄位、映像欄位、簽章、版本、合併結果。

L0～L2 由 Codex 在本機與 CI 執行，不需要 D365。只有 Solution 內模擬不了的部分（L3：Plugin 在沙箱實際執行、非同步作業、安全性角色、LINE 實機收訊；以及 IIS 部署、網頁版面）改用以下方式：
- **佈署專案的 `smoke` 指令：** 由 Codex 寫好情境、使用者在 goodshepherdback 執行；
- **使用者執行的驗收腳本：** 逐步操作與預期結果，寫在各階段的「使用者驗收」小節。

L3 失敗時，先在 L0～L2 補上能重現的測試，再修正。

這些也要「先寫腳本、再做功能」：腳本寫好時，功能尚未完成，執行結果應為失敗。

## 7. 每個 WP 的固定流程

## 9. 停止條件（遇到就停下來回報，不要繞過）

1. 需要真實的 D365 帳號、密碼、Token、金鑰，或需要連到正式組織。連 goodshepherdback 原則上只限使用者回報清理完成後、以不寫入的指令進行（D23、D24）；P0-13 另依 D23 的使用者 2026-11-04 trace 例外，由使用者操作，Codex 不連線。
2. 需要使用者在 D365 畫面、LINE Developers 後台、IIS 上操作，或需要執行佈署專案會寫入 D365 的指令（`apply`、`smoke`、`switch`、`rollback`、`ui-import`）。寫好步驟清單後停下，等使用者回報結果。
3. ChurchReport 的既有測試因本次修改失敗，且無法在不改變既有行為的情況下修好。
4. 舊程式的行為無法判斷（例如兩份副本邏輯不同，又沒有資料能證明哪一份是對的）。列出差異，請使用者決定。
5. 建置需要 `NoWarn` 新的警告、降低既有檢查，或關掉 `TreatWarningsAsErrors` 才能通過。
6. 發現本計畫與 v3.3 設計、或與程式現況有矛盾。
7. 任何會刪除或覆寫資料、跨教會讀寫、不可逆的 D365 操作（例如日期欄位行為轉換）。
8. 外部審查回報 Critical 問題，且修正方式會改變已定案的決定。
