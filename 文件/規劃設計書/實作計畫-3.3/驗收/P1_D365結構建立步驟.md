## 條件成立後的apply與verify

以下是已準備的產品命令介面；其中`<本次已審核plan完整路徑>`必須換成上述實際操作目錄檔案，

```powershell
dotnet run --project SpeechMessage.Dynamics.Deployment -c Release -- apply --org goodshepherdback --schema d365/schema/speechmessagecore.schema.json --plan <本次已審核plan完整路徑>
dotnet run --project SpeechMessage.Dynamics.Deployment -c Release -- verify --org goodshepherdback --schema d365/schema/speechmessagecore.schema.json
```

apply先重新讀取server、核對完整plan、將`before-metadata.json`以CreateNew寫入並flush／close，再只新增與納入solution，最後定向發布本次受影響表並重讀。
發生錯誤保留before／原例外，不刪元件、不修改舊欄位、不自動還原VM。應保存失敗結果，調查後重新plan，不使用舊plan強行重試。

- 結束碼0：目前定義與schema一致，所有索引皆Active。
- 結束碼1：有差異或真正失敗，查固定摘要及共用Exception.log安全事件；不把原始SDK訊息／機密貼入紀錄。
- 結束碼2：命令、白名單或路徑拒絕，尚未進入有效操作。
- 結束碼3：索引仍Pending／InProgress，不能算完成；稍後只讀verify，Failed必須另行調查，不重建掩蓋。
- 結束碼130：明確caller取消，已入場SDK仍須回來排空，不能提前關閉程序來偽稱完成。

第一次完整verify=0後重新plan應為0項新增，第二次套用新的零差異plan不得發任何metadata寫入；
要保存這兩輪的實際證據，不能把單元測試的零寫入當實機結果。

## D365後台與唯一鍵驗收

在未受管理`SpeechMessageCore`確認全部本次元件與`new`前綴發行者；核對四張新表為組織擁有，
`new_localizedtext`及`new_offeringcategory`的entity／field稽核、`new_outboundtask`的樂觀並行，
兩個加密token／secret欄位啟用欄位安全。工具不得建立帳號、角色或擴權profile。

在上述指定測試教會建立一筆可辨識`new_localizedtext`：`new_key=Org.Level.Group`、`new_culture=*`、`new_text=細胞小組`，
名稱加本次驗收標記並保存server正式ID。再建立相同教會／key／culture的第二筆，必須由**資料庫已Active的替代索引鍵**拒絕；
不同教會或不同文化的合法資料不得因顯示文字相同而被刪除、合併或隱藏。
測試期間不得發LINE或執行無關業務流程；如果既有Plugin／流程可能觸發，停止資料測試並先完成環境安全確認。

以finally等價流程只清理本次建立且已記錄正式ID的測試列，不按名稱搜尋刪資料，不刪既有記錄。
如果第二筆意外成功，先保存兩筆正式ID與索引狀態，僅刪除本次自己的測試列並將驗收判為失敗，不能隱藏重複。
