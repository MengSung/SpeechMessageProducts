## P0-05　編碼檢查與編碼轉換工具

**新增** `tools\RepoQuality\Test-TextEncoding.ps1`，需相容 PowerShell 5.1 與 7。

- `.ps1` 只允許註解包含非 ASCII 字元；程式語法、字串常值與識別字須維持 ASCII。以 PowerShell token 區分註解，避免 UTF-8 無 BOM 被 PowerShell 5.1 依 CP950 解讀時改變可執行內容。

| `-Scope All -ReportPath <md>` | 全部掃描，只輸出報告、不讓建置失敗，用來盤點舊檔 |
| 檢查的副檔名 | `.cs .cshtml .csproj .props .targets .json .md .ps1 .resx .xml .yml` |
| 失敗條件 | 有 BOM；不是合法 UTF-8；有 LF-only 或混用換行；檔尾不是 CRLF；含 U+FFFD 替代字元（亂碼跡象） |

- **輸出 manifest JSON：** 每個檔案記錄路徑、原始編碼、轉換前後的 SHA256，以及「中文字串常值清單轉換前後是否一致」。
  - 中文字串常值以 Roslyn 或正則抽出，轉換前以 CP950 解碼，轉換後以 UTF-8 解碼；兩邊必須完全相同，否則該檔不寫入並列為失敗。

**先寫的測試：** `tools\RepoQuality\Tests\Test-TextEncoding.Tests.ps1`，使用 Pester。若環境沒有 Pester，以純 PowerShell 斷言腳本代替。

- UTF-8 BOM：失敗；
- LF-only：失敗；
- CP950 中文：失敗；
- 檔尾無換行：失敗；
- 含 U+FFFD：失敗。

轉換腳本另外測三件事：
- 「CP950 → UTF-8 後中文字串相同」；
- 「-DryRun 不寫檔」；
- 「無法無損轉換時不寫檔」。

**驗證：** 測試全過；以 `-Scope All` 產生 `tools\RepoQuality\reports\encoding-baseline.md`。預期會列出 `Trace\` 的 CP950 檔、`Line.Messaging` 的 BOM 檔等既有問題，作為後續階段的待辦。

## P0-SEC　Development 防護：不得使用正式 LINE token、只能連 goodshepherdback（使用者已核定，D27）

**為什麼要做：** P0-ENV 調查發現，ChurchReport 有 11 個類別自建 `ConfigurationBuilder`、只讀基底 `appsettings.json`，看不到 Development 的設定：
`LineUtilityClass`、`QrCodeUtility`、`PersonalQrCodeUtility`、`SmallGroupQrCodeUtility`、`SundayQrCodeUtility`、`LineNotifyUtility`、`DonationPaymentManager`、`DonationFeePaymentProcessor`、`RecurringDonationPaymentProcessor`、`DonationPaymentProcessor.Core`、`PaymentNotificationService`（其中 9 個直接用讀到的 token 建立 `LineMessagingClient`）。
共用程式庫 `LineMessagingProcessor\LineMessagingProcessorClass.cs` 的 `ResolveDefaultChannelAccessToken` 也只讀基底檔加環境變數。只改 Development 設定，無法保證開發時不用到正式 token；而 goodshepherdback 有真實會友的 LINE ID。

**不變式：**
- Development 時，任何程式路徑都拿不到基底 `appsettings.json` 的正式 LINE token；沒有測試 token 時要「發不出去」，不可退回正式 token。
- Development 時，ChurchReport 只能連 goodshepherdback。
- 非 Development（含未設定環境，視為 Production）的行為逐鍵不變。

**做法：**
1. `SpeechMessageProducts.ChurchReport.csproj` 加固定的 `UserSecretsId`（目前沒有，所以 User Secrets 從未生效）。Host 只在 Development 載入 User Secrets。
2. 新增共用的 Development 設定層（ChurchReport 內 internal 靜態擴充方法，例如 `AddChurchReportDevelopmentOverrides`）：
   - **環境判斷與網站主機相同（已以實測確認）：** 先看 `DOTNET_ENVIRONMENT`，再看 `ASPNETCORE_ENVIRONMENT`，都沒有就是 Production；比對 Development 不分大小寫；
   - 只有 Development 才加入 `appsettings.Development.json`（optional）與 ChurchReport 的 User Secrets（optional），順序與 Host 相同；非 Development 一個 provider 都不加；
   - 11 個自建 `ConfigurationBuilder` 各自在 `AddJsonFile("appsettings.json", …)` 後面接這個方法；保留原本的 `optional`、`reloadOnChange` 與 static `Lazy` 結構，不做其他重構；
   - `LineMessagingProcessorClass` 不能參考 ChurchReport：只在 Development 加 `appsettings.Development.json`（optional），不加 User Secrets；結果是 Development 的預設 token 路徑拿到空值而失敗（fail closed）。在回報列出走這條路的呼叫端。
3. `appsettings.Development.json`：
   - `LineMessaging:DefaultOrganization` 改為測試別名 `DevTest`；
   - 基底中每個 token 非空的別名（目前是 `Jesus`、`JesusBack`）的 `ChannelAccessToken` 覆寫為空字串，附繁中註解說明原因；
