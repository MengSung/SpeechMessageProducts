# 分析報告：`global-isolation-memory-leak-guardrails`

**方向正確，但規劃尚未達到可執行（ready-to-implement）標準。**

將「跨會話/跨使用者/跨租戶洩漏」與「記憶體洩漏」列為零容忍發布阻斷項，並把持久化防護面放在個人全域 `C:\Users\Administrator\.codex\AGENTS.md`（CCG-managed block 之外）而非依賴按需觸發的 Skill，這個選擇本身是合理的——它符合「不必每個 prompt 重複提醒」的目標，且不與現有 CCG/Trellis 管理區塊在結構上衝突（目前該檔案 100% 位於 `<!-- CCG:START -->...<!-- CCG:END -->` 內，區塊外目前為空，附加不會產生語法衝突）。

但規劃文件（`requirements.md` / `prd.md`）目前只描述「要寫什麼內容」，缺少「如何與既有機制共存、如何避免被判斷為裝飾性文字、如何避免誤觸發」的設計細節。這些缺口如果不在 PRD 階段解決，會導致：(a) 新規則實際上可被既有 CCG 決策矩陣繞過，(b) "release blocker" 的措辭與實際可行的強制力不匹配，(c) 對日常低風險開發造成不成比例的驗證負擔。建議在正式寫入全域檔案前，先補強規劃。

## Confirmed strengths

1. **範圍界定正確**：明確鎖定「個人全域檔案、CCG-managed block 之外」，未誤觸專案層級的 `AGENTS.md`（本 repo 的 AGENTS.md 屬於 Trellis 管理，兩者是不同檔案、不同管理慣例，PRD 沒有混淆）。
2. **效能從屬關係已明確寫入**：`requirements.md`/`prd.md` 均包含「效能與記憶體效率目標必須從屬於安全性、正確性、清理、可維護性」，直接對應任務目標三「效能指引必須服從隔離/正確性/確定性清理/驗證」，措辭清楚、無模糊空間。
3. **驗證意圖具備風險觸發概念**：「當變更產生可信的洩漏風險時，要求針對性測試/壓力測試/剖析」——已經比純粹口號式的宣告更具可操作性。
4. **選擇不依賴 Skill 的理由站得住腳**：Skill 是「按任務相關性載入」，而全域 AGENTS.md 是「自動注入的個人預設」，兩者定位不同，這個判斷正確且已在 notes 中說明。

## Critical issues

**C1. "Zero-tolerance release blocker" 的措辭與實際強制力不匹配。**
這份指引最終只會存在於**單一操作者本機**的個人設定檔中，不進版控、不出現在 PR diff、不會被其他協作者或 CI 讀取到。它能提高「這一個 Codex 會話」注意到問題的機率，但**無法**真正構成「release blocker」——沒有任何 CI/lint/測試/PR checklist 與之綁定去實際擋下發布。如果 PRD 的意圖真的是「零容忍發布阻斷」，僅靠個人 AGENTS.md 是不夠的；至少要在 acceptance criteria 或 notes 中誠實標注：這是「單一操作者的行為預設」，不是「團隊/發布層級的強制閘門」，並建議同時評估是否要把同等規則沉澀到 repo 內的 `.trellis/spec/guides/`（會被所有貢獻者與未來 session 讀到）。目前規劃文件完全沒有這層區分，容易讓後續驗收時誤以為「寫進個人檔案」=「發布真的被擋下」。

**C2. 與既有 CCG 決策矩陣（同一檔案內）存在未處理的優先序衝突。**
現有 `~/.codex/AGENTS.md` 的 CCG-managed block 內建「複雜度 × 風險」決策矩陣：`S + 低風險 → 直接寫，跳過審查也可以`；風險分級目前完全由代理人主觀判斷，沒有把「觸碰共享快取/訂閱/計時器/跨會話狀態」自動視為高風險的規則。新指引若只是「附加在區塊外」而不明確聲明「凡涉及隔離或洩漏風險的變更，一律視為高風險，覆蓋掉 S+低風險的免審查快速路徑」，就會出現一個真實的漏洞：一個表面上「S 複雜度、看似低風險」的小改動（例如加一個全域快取或訂閱）完全可能在現有矩陣下被判定為「直接寫、跳過審查」，與新指引的零容忍意圖直接矛盾。**PRD 目前沒有提到這個交互，是規劃階段最需要補的一塊。**

**C3. 與 CCG「鐵律 5：scope 是邊界，不自作主張擴大範圍」存在潛在衝突，尚未聲明優先序。**
新指引要求「當變更產生可信洩漏風險時，即使使用者沒有明確要求，也要做針對性測試/剖析/清理」。但既有鐵律明確禁止「自作主張擴大範圍」。若沒有在新指引中明確聲明「隔離/洩漏相關的驗證與清理工作，屬於鐵律 5 的既定例外，永遠視為隱含在範圍內」，未來的 Codex 會話很可能援引「不擴大範圍」來正當化跳過額外驗證，等於讓新規則名存實亡。

## Warnings

**W1. 未界定適用範圍，可能對無關情境過度觸發。**
「跨會話/跨使用者/跨租戶」與「記憶體洩漏」的用語沒有註明僅在「涉及共享可變狀態、單例、靜態欄位、無淘汰快取、長駐行程」等情境才適用。這是一份**全域個人**設定，會套用到操作者接觸的所有專案，包括與多租戶/長駐服務完全無關的一次性腳本。若字面照搬，可能導致 Codex 對無關程式碼強加不必要的洩漏檢查或剖析要求，造成雜訊與抵抗心理（進而被使用者忽略，違背「持久防護」的初衷）。建議在寫入正文前，加一句適用性判準（例如：「當變更涉及共享/全域可變狀態、跨請求快取、長駐背景任務、或多租戶資料路徑時適用」）。

**W2. 「可信風險（credible risk）」缺乏判準，驗證力度可能兩極化。**
目前完全沒有給出啟發式（heuristic）清單，例如：新增/修改 static 欄位、單例、全域快取、事件訂閱未搭配取消訂閱、背景 timer/task、跨請求共用連線池等。沒有這份清單，「要求測試/剖析」這句話在實務上會變成主觀判斷——風險是被無限上綱（每次改動都要求壓測）或形同虛設（因為沒有具體觸發條件而從不觸發）兩個極端之一。建議在 requirements 中補一份簡短、非窮舉的觸發清單。

**W3. 未指定新內容的區塊分隔格式。**
Requirements 只說「加在 CCG-managed block 之外」，沒有指定用什麼樣的標記包起來（例如仿照本 repo `AGENTS.md` 的 `<!-- TRELLIS:START/END -->` 慣例，用一個獨立的 `<!-- PERSONAL:START/END -->` 或類似標記）。若不指定，未來 CCG 更新工具重新生成/覆寫 managed block 時，邊界判斷完全依賴人工小心操作，容易在編輯時不慎把新內容誤包進 CCG 區塊、或被未來的自動化工具誤判為可覆寫內容。這是一個「managed-block 風險」，建議在 PRD 驗收標準中明確要求「新增內容須有自己的顯式分隔標記」。

**W4. 實際交付物不進版控，缺少可追溯紀錄。**
最終產出（對 `C:\Users\Administrator\.codex\AGENTS.md` 的編輯）位於 repo 之外，不會出現在 `git diff`、PR、或此專案的版本歷史中。按照 CCG 工作流慣例，任務完成後會歸檔到 `.ccg/tasks/archive/`，但歸檔只保留 task.json/requirements.md，不保留「實際寫入全域檔案的最終文字」快照。建議在完成時，把最終寫入的段落原文也存一份到本任務目錄（例如 `design.md` 或 `implement.md`）中，作為可審計、可版控的紀錄，避免日後想追查「當時到底寫了什麼」卻無跡可循。

## Recommended planning changes

1. 在 `requirements.md`/`prd.md` 新增一節「強制力邊界聲明」：明確寫出這是**單一操作者的個人預設**，用以提高合規機率，但**不是**團隊/CI 層級的發布閘門；如果要真正做到「release blocker」，需另外評估是否同步寫入 repo 內的共用 spec（`.trellis/spec/guides/`）或建立對應的 PR checklist / CI 檢查。
2. 新增一條「與既有 CCG 決策矩陣的優先序」規則：任何變更一旦涉及隔離或洩漏風險，一律覆寫「S+低風險→跳過審查」的快速路徑，強制視為高風險並觸發雙模型審查。
3. 新增一條「與鐵律 5（scope 邊界）的優先序」聲明：隔離/洩漏相關的驗證、清理工作視為既有範圍的隱含延伸，不受「不自作主張擴大範圍」限制。
4. 補一份簡短、非窮舉的「可信風險」觸發清單（單例/靜態欄位/全域快取/未取消訂閱/背景 timer/連線池/跨租戶資料路徑等），降低主觀判斷造成的兩極化。
5. 加一句適用性判準，避免規則被字面套用到與共享狀態、多租戶、長駐行程完全無關的一次性程式碼。
6. 指定新內容的顯式分隔標記格式（例如 `<!-- PERSONAL:START/END -->`），並在驗收標準中加入這一項。
7. 任務完成/歸檔時，把實際寫入全域檔案的段落原文額外保存一份到本任務目錄內，供版控與日後審計。

## Acceptance readiness

**尚未就緒（Not ready）。** 目前 5 條驗收標準都只描述「內容要包含什麼」，屬於必要但不充分：C1–C3 三項屬於關鍵規劃缺口（強制力邊界、與既有決策矩陣的優先序、與鐵律 5 的優先序），若不先在 PRD 中解決，寫入全域檔案後很可能出現「規則存在但被既有機制繞過」或「規則存在但被誤解為比實際更強的保證」的落差。建議先完成上述「Recommended planning changes」1–3 項（強制力邊界聲明 + 兩處優先序聲明），再進入實際撰寫全域檔案內容的階段；4–7 項可視為品質加分項，非阻斷項。
