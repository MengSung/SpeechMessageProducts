### Warning 🟡

- **進度單一資料 JSON → `alert` 欄位（經 `Test-ProgressPage.cjs` 的 `No alert hides the warning region...` 測試斷言）**
  測試斷言 `activePage.get('alert').innerHTML` 要符合 `/P1-02 複審完成，接續 P1-04/`，但同一份 JSON 的 `headline`／`tiles[階段 1 驗收]` 已將 **P1-03** 一併列為驗收完成（含 20261105-140350 最終雙模型複審）。alert 橫幅（頁面最上方、最先被看到的訊息）卻只提到 P1-02 複審完成，完全沒提 P1-03。
  - Why：頁首／卡片與頂部 alert 對同一事實（「目前驗收到哪裡」）給出不一致的敘述，讀者可能誤以為 P1-03 尚未完成複審或不確定其狀態，與「進度卡片/phase 是否與 WP 相同」這項審查重點直接相關。
  - Fix：將 `alert.body`／`steps` 同步更新為反映 P1-03 已於 20261105-140350 完成最終複審，或至少兩者並列；測試中對應的正規表達式也要跟著更新，否則舊字串會一直「合法通過」卻掩蓋內容未同步的事實。

- **`Test-ProgressPage.cjs` 第 5 個 `test('Summary cards and phase meters agree with accepted work packages', ...)`**
  `accepted`／`active` 是用同一份 `original.p1Wps[].status` 現場重新計算，再拿去比對 `stage.done`／`tile.value`／`tile.meter.*`；三者全部來自同一個 DATA 物件。這能保證「卡片、階段表、工作包清單彼此不互相矛盾」，但**不能**驗證 `status` 欄位本身是否真的對應實際驗收事實（例如若有人把某工作包狀態誤標或被意外改回，只要三處同步跟著錯，測試仍會 5/5 全綠）。
  - Why：需求裡提到「新一致性測試先紅 0≠1，修後 5/5」，若把這當作「已證明不會再出現舊的零值 Bug」的充分證據，會高估測試的保護範圍——它防的是「卡片間抄寫不同步」，不是「狀態欄位本身對不對」。註解「不把 P1 初始的零永久寫死」也印證：修復重點是讓測試不要用字面常數卡住未來合法更新，而非新增一個獨立 ground truth 來源。
  - Fix（建議，非強制）：若要真正攔截「狀態欄位本身被錯誤清零／誤標」，需要一個獨立於 DATA 物件之外的驗證來源（例如由 `wp-reports/*.md` 是否存在、或由驗收日期自動推算 done 清單），而不是全部從同一份 DATA 自我比對。

- **進度單一資料 JSON → `p1Wps[P1-12].status = "you"`**
  其餘 11 筆工作包的 `status` 只用 `done` / `active` / `todo` 三種值，`P1-12` 卻用了第 4 種非標準值 `"you"`。`Test-ProgressPage.cjs` 中唯一對狀態轉 CSS class 的斷言只覆蓋 `P1-02`（`class="wp is-done"`），沒有任何測試覆蓋 `P1-12` 這筆的渲染結果（class、是否計入任何 meter）。
  - Why：若實際渲染腳本（未在本次審查材料內）只對 `done`/`active`/`todo` 三種值做樣式分支，`"you"` 可能落入預設分支而失去「這是卡在使用者授權、不是一般排隊中」的視覺區分，削弱了這張卡片原本想傳達的語意（目前筆記文字已經講得很清楚，但樣式/互動層面未被驗證）。
  - Fix：建議補一則針對 `P1-12` 的渲染斷言（至少確認其 class 不是 falsy／undefined），或將其狀態值正規化為既有列舉並透過額外旗標（如 `gated: true`）表達「待使用者授權」。
