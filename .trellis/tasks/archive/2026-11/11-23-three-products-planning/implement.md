# 執行計畫

## Phase 1 研究與文件輸入

1. 盤點五個外部資料夾的檔案清單、類型與版本。
2. 讀取需求 Word、PDF、PPTX、Draw.io、HTML 的可用文字與圖形資訊。
3. 盤點目前分支的方案、專案、核心介面、DI、Webhook、Tenancy、Hosting、測試與部署。
4. 唯讀分析全坤建設與國稅局程式碼，記錄可重用能力與待驗證風險。
5. 將事實、推論、建議與未知項目分開記錄。

## Phase 2 文件規劃

1. 建立三產品共用／獨立能力矩陣。
2. 建立 LINE Channel、Webhook、租戶與 Rich Menu 配額策略。
3. 建立好牧人 2.0 Pilot Run 劇本與放行閘門。
4. 建立好牧人、建設公司、協會的功能依賴圖與建議順序。
5. 建立後續工作包清單，每個工作包寫清楚前置依賴、測試與驗證證據。
6. 產製 Word 計畫書。
7. 產製內嵌 SVG 圖形為主的 HTML 教學文件。

## Phase 3 品質檢查

1. Word：結構檢查、文字抽取、欄位與表格檢查。
2. Word：執行 `render_docx.py`，逐頁檢查 PNG，修正版面後重跑。
3. HTML：執行 HTML 結構檢查，確認 SVG、標題階層、連結與響應式版面。
4. 執行專案規定的文件檔案說明、UTF-8、CRLF 與進度檢查；若檢查與本次輸出格式不適用，記錄原因。
5. 檢查輸出只包含規劃文件與必要資產，不修改外部程式碼與正式設定。

## Phase 4 後續執行建議

1. 先核准規劃文件與 Pilot 邊界。
2. 建立共用平台與測試環境工作包。
3. 先完成好牧人第一條縱向流程。
4. 每個功能完成一輪自動化、實機、隔離、資源生命週期與人工審核後才進下一功能。
5. 好牧人 Pilot 穩定後，抽取已證明可重用的共用能力，再啟動建設公司工作包。
6. 建設公司 CRM 2011 與電子發票整合各自先做沙盒／離線契約驗證，再做受控實機驗證。
7. 最後建立協會產品，重用已驗證的平台能力，但不直接複製產品資料模型。

## 主要驗證命令與工具

- `dotnet build SpeechMessageProducts.sln --no-restore`
- 相關測試專案的 `dotnet test`
- `python tools/RepoQuality/check_file_documentation.py`
- 文件技能提供的 `render_docx.py`
- HTML 靜態檢查與瀏覽器開啟檢查
- `git diff --check` 與 `git status --short`

## 回滾點

- 文件輸出前：只刪除本次產生的輸出檔即可回復。
- 外部資料盤點：唯讀，不需要回滾。
- 後續程式工作包：每個工作包各自建立可停用版本、資料遷移回滾與佇列 drain 方案。
