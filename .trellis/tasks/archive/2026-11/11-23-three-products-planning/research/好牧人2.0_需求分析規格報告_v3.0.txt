2. 系統概述與架構決策
2.1 產品定位與設計原則
LINE 為唯一前台：會友與管理員全部經由宮格＋LIFF 操作，零安裝。此為本產品相對於競品（愛無界、YOOV、eChurch 等 App 型態）最具結構性的差異化優勢，尤其面對教會高齡族群。
標準化、不客製：所有教會共用同一套功能與流程；差異僅允許出現在模組十「教會設定」之資料層自訂（委身類型、牧養架構、奉獻類別、祝福規則）。任何程式級客製一律婉拒——此為 SaaS 低維運模式之經濟基礎，須在面對大型教會壓力時同樣堅守。
金流不經手：奉獻與課程費經永豐豐收款直接入各教會帳戶；音訊科技僅就訂閱月費向教會收款。任何與金流機構之分潤安排，一律轉為對教會可見之透明列示費用。
月租訂閱＋自助客服：模組十二自動出帳扣款；模組八 FAQ 為第一線客服。
2.2 單一 LINE 官方帳號多租戶架構
好牧人 2.0 採「單一官方帳號、單一 Organization、多教會 Account」之三層架構。全台各教會會友加入的是同一個 LINE 官方帳號，系統於每次互動時依 LINE userId 判定其所屬教會，據以決定資料範圍與品牌呈現。
2.3 資料隔離設計
所有實體均新增對 Account 之 Lookup 欄位，標示所屬教會；所有查詢、報表、推播與權限，均以「目前使用者所屬教會之 Account」為過濾條件。

3. 多租戶品牌化：讓每間教會感覺是「自己的」
口述規格提出的核心體驗需求是：即使所有教會共用一個好牧人 2.0 官方帳號，每間教會的會友仍應感覺這是「自己教會的小幫手」。本章說明此需求在 LINE 平台上可以做到什麼程度、做不到什麼，以及對應的設計與話術。
3.1 可行的部分：逐則訊息切換名稱與 Logo
LINE Messaging API 的訊息物件支援選填的 sender 屬性，可逐則指定顯示名稱與頭像圖示，且適用於 push、reply、multicast、narrowcast、broadcast 五種發送方式，不限訊息型別——文字訊息與 Flex 訊息皆可。
實作要求：所有對外發送訊息一律經由統一的發送封裝層，該層強制注入 sender 物件。任何繞過封裝層直接呼叫 LINE API 的程式碼，視為缺陷。
3.2 不可行的部分（必須誠實面對）
此限制的產品意涵需要明講：好牧人 2.0 無法做到「讓教會會友完全不知道有好牧人這個系統」。若某教會的採購前提是「必須完全白牌、不得出現廠商名稱」，則單一 OA 架構不適用，該教會需走「自有官方帳號」路線（此路線需教會自行申請官方帳號並自付訊息費，且需另行評估 LINE Module Channel 合作夥伴資格）。此判斷應納入客戶篩選框架。
3.3 教會 Logo 規格與代管
sender.iconUrl 必須是 LINE 伺服器可公開存取的 HTTPS 圖片位址，不能是 D365 內部附件連結（需驗證）。因此系統須自建圖片代管。
3.4 Flex 訊息的教會識別設計
除 sender 之外，Flex 訊息本身的版面也應承載教會識別，這是會友視覺上最直接的「專屬感」來源，且不受 from 字樣影響。
4. 模組二：教會識別與訊息發送封裝（系統核心）

5. 模組一：會友註冊綁定（雙入口）
依口述規格，使用者可能透過兩種完全不同的路徑進入好牧人 2.0，兩者在「教會如何被決定」上有根本差異，因此需分流設計。
5.1 入口 A：掃描教會專屬 QR Code
教會將專屬 QR Code 印於週報、佈告欄或由小組長轉發。QR 內含教會代碼參數。
5.2 入口 B：未經 QR 直接加入（教會清單搜尋）
若使用者是從搜尋、朋友分享或其他途徑直接加入官方帳號，系統無從得知其教會，必須由使用者自行指定。
5.3 名單比對邏輯
比對範圍一律限縮於「該教會」之名單，絕不跨教會比對。
重要原則：「系統名單查無」不等於「直接拒絕」，也不等於「直接建立」。查無者一樣送交管理員審批，通過後才建立聯絡人並綁定。綁定與聯絡人建立一律發生在審批通過之後，不在申請當下。
5.4 審批流程
送出申請 → 系統以 multicast 推送審批 Flex 予該教會之管理員（多位管理員同時收到）。
審批 Flex 內容：申請人姓名、電話、介紹人、入口類型（QR／清單）、比對結果摘要、候選聯絡人（如有）。
Flex 提供兩個 postback 按鈕：「核准」與「退回」。
核准 → 建立或關聯 Contact → 寫入 LINE UserId → 系統自動綁定該教會會友宮格 → 推播通知申請人「已通過」。
退回 → 記錄退回原因（可選：非本教會、資料有誤、重複申請）→ 推播通知申請人並附說明。
防重複審批：任一管理員完成處理後，其他管理員點擊同一 Flex 按鈕時回覆「此申請已由○○○處理」。
5.5 驗收條件
掃 A 教會 QR 進入者，教會欄位鎖定為 A 教會且不可更改。
直接加入者搜尋教會時，清單中同時出現已簽約與未簽約教會，外觀無任何差異。
選擇未簽約教會者收到制式回覆，且系統未建立任何 Contact。
審批通過後 1 分鐘內，申請人收到通知且宮格已切換為該教會會友宮格。
已綁定者再次開啟註冊頁，直接顯示「您已完成綁定」，不重複建立。
兩位管理員同時點擊核准，僅第一次生效，第二次收到已處理提示。

以永豐信用卡授權檔自動扣款。成功則回寫已收與付款狀態，推播收據予教會財務；失敗則記錄原因並推播，3 日後自動重試，最多 2 次。

FR-02-01 強制品牌注入 | 所有發送一律經 SendService；該服務依 accountId 取得 sender 物件並注入每一則訊息。未帶 accountId 之呼叫直接拋錯。
FR-02-02 快取 | 教會品牌資料（名稱／Logo／主題色）以記憶體快取，TTL 10 分鐘；教會設定變更時主動失效。

FR-02-05 速率控制 | 發送佇列化，遵循 Messaging API 速率限制；multicast 限 200 requests/秒。
FR-02-06 失敗處理 | 發送失敗記錄至發送紀錄實體（含錯誤碼），429（額度用盡）觸發營運告警。
FR-02-07 額度歸戶 | 每次發送記錄所屬 Account 與則數，供第 11 章成本分攤使用。
FR-02-08 冪等 | Webhook 可能重送（deliveryContext.isRedelivery），以 webhookEventId 去重，避免重複回覆或重複記錄出席。
嚴重風險：broadcast 誤用 / 在逐教會獨立官方帳號的架構下，broadcast 的爆炸半徑僅限一間教會；在單一 OA 架構下，一次誤用 broadcast 會將某教會的內部訊息（例如小組聚會通知、奉獻提醒）發送給全台所有教會的所有會友。 / 這同時是資料外洩事件、品牌信任事件，以及一次性大額訊息費用事件。 / 因此 broadcast 不是「謹慎使用」，而是「在程式中不存在」。

開通流程的大幅簡化（單一 OA 架構之直接效益） / 前版架構下，開通需要教會自行至 LINE 官方帳號管理後台建立官方帳號、啟用 Messaging API、選定 Provider、取得 Channel ID 與 Secret、回填至開通精靈，再由系統簽發 Token——整段流程涉及多次人工往返，是導入期最大的摩擦點，也是教會端最容易卡住的環節。 / 單一 OA 架構下，上述步驟全部消失。審核通過後，系統自動產製宮格即完成開通，教會端零技術操作。 / 此為本架構最具體的商業價值，應納入銷售話術：「簽約後當天即可使用，教會不需要任何技術設定。」

關鍵發現：訊息成本佔訂閱收入之比例 / 以 1,200 位綁定會友、每月訊息成本約 NT$1,920 計，若訂閱收入為每月 NT$20,000（跨數間教會合計），訊息成本約佔 9.6%——尚在可承受範圍。 / 但此比例對「推播頻率」極度敏感：若每人每月推播由 8 則增為 16 則，訊息成本翻倍至約 19%，將顯著侵蝕毛利。 / 因此推播頻率不是產品功能問題，而是毛利控制問題，必須以系統設計加以約束（見 §13.3）。

FR-15-01 | 拉取優先於推播 | 凡可由會友主動點擊宮格取得之資訊（課程清單、個人紀錄、奉獻明細、週報），一律不主動推播。宮格點擊觸發之 reply 為免費訊息。
FR-15-02 | 推播頻率上限 | 每教會每月推播次數設上限（預設每人每月 10 則），逼近上限時警示管理員，超出則需音訊科技核准。此為系統強制，非建議。
FR-15-03 | 合併推播 | 同日多則通知合併為單一 Flex（如：本週聚會提醒＋課程提醒合併），減少則數。
FR-15-04 | 分眾發送 | 課程通知僅發送給相關對象（如指定小組、指定委身類型），不全教會群發。
FR-15-05 | 額度監控 | 以 Get quota 與 Get consumption 端點每日取得本月已用則數，於營運儀表板呈現並設 70%／90% 告警。
FR-15-06 | 逐教會歸戶 | 每則發送記錄所屬 Account，產出各教會之則數消耗報表，作為方案級距調整與異常偵測之依據。
FR-15-07 | 超量處理 | 單一教會顯著超出其級距合理用量時，先溝通調整推播習慣；持續超量者調整至更高方案級距。
