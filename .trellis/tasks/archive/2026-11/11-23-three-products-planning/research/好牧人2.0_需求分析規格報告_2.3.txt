1.1 目的
本文件為「好牧人 2.0」LINE 教會資訊管理系統之需求分析規格報告 v2.3。本版依 2026/07/14 口述將模組八「教會設定」升為宮格層級：管理宮格按下「教會設定」後，使用者之 Menu 即切換為「教會設定宮格」，六格為——牧養職分（即委身類型：有哪些牧師、小組長、新朋友等選項）、牧養架構、奉獻類別（有哪些什一、感恩等類別）、權限管理、「匯入資料」（資料匯入入口），以及「返回管理選單」（切回教會管理員原本的 Menu 選項）。設定宮格採全系統共用之通用版（好牧人 2.0 品牌識別、不含教會 Logo）——管理員深層功能頁不需教會識別，且可守住宮格配額；進入與返回均以 postback 觸發、由伺服器以逐人宮格 API 切換（共用版無法以寫死之 richmenuswitch alias 指向各教會不同的管理宮格）。其餘沿 v2.2（課程起訖、金流回傳網址、無複核）、v2.1（入口決定審批）、v2.0～v1.3。所有 LINE、D365 與永豐豐收款規格均經官方文件查證，來源列於第 18 章。

2. 系統概述
2.1 產品定位與設計原則
・LINE 為唯一前台：會友與管理員全部經由「好牧人2.0」官方帳號宮格＋LIFF 操作，零安裝。
・標準化、不客製：功能與流程全教會一致；差異僅允許出現在「資料層自訂」（模組八）、「權限配置」（模組九）與「視覺識別」（宮格 Logo／名稱、sender）。任何程式級客製一律婉拒——此為 SaaS 低維運模式之經濟基礎。
・金流不經手：奉獻與課程費經永豐豐收款直接入各教會帳戶；音訊科技僅就訂閱月費向教會收款；任何與金流機構之分潤安排一律轉為對教會透明列示之費用。
・月租訂閱＋自助客服：模組十一自動出帳扣款；模組七 FAQ 與模組十三自助匯入為第一線客服減量設計。
・平台化共用（v1.5 新增）：租戶管理、匯入引擎、權限矩陣、帳務訂閱、LINE 整合、通知與稽核等能力抽離為共用核心模組，供票款通、建設公司、協會管理、補習班、通告管理等產品線重用（詳第 13 章）。

4. 模組一改版：入口決定審批——適用命中與新增（v2.1）
4.1 需求敘述（依 2026/07/13 補充口述三～五）
註冊表單僅三欄：姓名、電話、介紹人——沒有依教會設定而變動之欄位；使用者按「註冊」後，資料送入程式、再到系統進行比對。這不是單純的名單查找，而是一個完整的註冊流程：不論透過連結或直接註冊，系統後臺判斷「是否註冊成功」的邏輯與流程完全相同（4.2）。透過 QR Code 或教會連結進入者不需經過審批；審批是註冊的最後一關，僅發生於「直接加入且命中系統既有資料」之情況（4.3）。v2.0 補充口述四確立：只要註冊完成——不論是否需要審批——宮格上的「註冊」按鈕即取消（切換時機詳 4.4）。v2.1 補充口述五更正：比對未命中（姓名不在系統）不能直接判定註冊完成，仍須看入口——直接加入者即使是名單外新朋友，判定通過後仍要進入審批流程（4.3）。
4.2 註冊判定規則（兩入口相同）
4.3 審批：註冊的最後一關
v2.1 更正：審批看「入口」而非「命中與否」。凡判定通過者（4.2 前三況：命中既有會友或名單外新朋友）——QR／教會連結入口一律免審批直接完成；直接加入者一律進入審批：系統將註冊結果（含姓名等資訊與案件型態）推送給教會管理員（LINE 審批 Flex），由管理員決定是否接納此人。判定失敗（電話不吻合）則兩入口一致立即告知，不進審批。
「接納後才執行」原則：直接加入之案件於管理員接納後方執行綁定或新增，駁回不建立任何 Contact——名單品質與計費人數由審批把關，灌名單風險自源頭阻斷。
4.4 宮格切換：必要性審核（回應）與切換時機
結論：必要，予以保留；但其性質為系統後台之自動動作，並非使用者的操作步驟，前版畫法造成困惑，本版正名為「系統自動：切換其宮格為該教會會友選單」。原因：好牧人 2.0 全體使用者共用單一官方帳號，尚未綁定者看到的是「未綁定預設宮格」（會員註冊／教會申請使用等六格）；註冊完成的那一刻，系統必須呼叫 LINE 的逐人宮格 API（Link rich menu to user），把「這一位使用者」看到的選單自動切換為其所屬教會的會友選單（含教會 Logo 與名稱、一鍵出席、課程報名、我要奉獻等）——若缺少此步，註冊完成者打開聊天室仍只見「會員註冊」預設宮格，無法使用任何功能。使用者全程無感、不需點擊任何東西；新增聯絡人（4.2 第三況）完成時亦同步執行。
4.4.1 切換時機（v2.0：註冊完成即取消「註冊」鈕）
4.5 入口動作釐清
QR Code／教會連結進入者：不需要點擊宮格「註冊」按鈕——掃碼或點連結即直接開啟註冊表單（教會已自動帶入）。自行新加入者：於未綁定預設宮格點「會員註冊」鈕進入註冊流程，選擇教會並確認正確後填答送出。兩者送出後之系統判定完全相同。
4.6 通關問題調整
v1.8 曾規劃「答對教會設定之通關問題即免審批」；本次完整流程口述中無此環節，且表單確立為僅三欄，故自主流程移除（FR-08-06 暫緩；教會設定現行結構詳第 7 章宮格層）。機制是否於未來恢復，列 OI-19 待確認。
4.7 已註冊者之註冊入口（沿 v1.6）
綁定完成後宮格切換為會友選單（無「註冊」鈕）；輸入關鍵字「註冊」仍 reply 註冊 LIFF 連結，供協助家人註冊或換機重綁；同一 Contact 重綁須先由管理員後台解除原綁定。
4.8 功能需求（v1.9～v2.0 新增／變更）
4.9 驗收條件
・姓名＋電話皆正確：QR 入口即完成；直接加入產生待審批單且收到等待訊息、宮格切至待審批宮格。
・姓名不在系統：QR／連結入口立即新增聯絡人並完成；直接加入則產生待審批案件（型態＝名單外新朋友）且審批前通訊錄查無此人，接納後才出現。
・姓名相符但電話不同：收到「電話不吻合」，不建案件、不新增聯絡人。
・審批 Flex 含介紹人＋入口別＋案件型態；接納／駁回後 1 分鐘內通知；駁回案件不留任何 Contact。
・待審批者之宮格立即無「註冊」鈕且可查審核狀態；駁回後恢復預設宮格可重新註冊；免審批完成者宮格即為該教會會友選單——全程無需使用者任何操作。

6. 模組三改版：課程管理——檢視表、排程推播與課前通知（v1.6）

6.3 課程實體欄位（依 1.0 標準化分區）
6.4 上架與推播（立即／排程）
6.5 課前通知
上課開始日前 N 天（教會層級參數，預設 3 天，可設多段如 3／1 天）推播「已報名」會友：課程名稱、上課日期時間、教室地點、攜帶教材等課程說明（sender＝教會）。發送量計入第 10 章訊息費成本模型。
6.6 繳費金流：付款方式與永豐回傳網址機制（課程費／奉獻共用，v2.2）
v2.2 更正：付款結果並非經由 LINE Webhook——LINE Webhook 專責接收 LINE 之訊息事件（在 LINE 裡面打字等）。正確機制為：建立收費單並向永豐建單時，一併傳入我方之「付款結果回傳網址」；買家完成付款後，永豐依建單時所給之網址呼叫我方付款結果通知端點，系統據以自動核銷收費單（實收＝應收、款項直入教會帳戶）並推播電子收據。此端點獨立於 LINE Webhook，具驗簽與冪等處理。奉獻 LIFF 表單沿 1.0：奉獻類別（模組八自訂下拉）、奉獻金額＊、付款方式（下表五選項）、備註說明。

10. 模組十二：單一 Channel 多租戶推播與教會識別
10.1 推播管線
10.2 Webhook 事件路由
單一 Webhook 端點驗簽（X-Line-Signature）→ 以事件 UserId 查 Contact → 取得所屬教會 Account → 業務處理 → 以該教會 sender reply（reply 不計費）。未綁定 UserId 之事件路由至註冊／申請流程。Webhook 具冪等處理（LINE 可能重送）。
10.3 Token 治理
註冊 Assertion Signing Key 後以 JWT 換發 Channel Access Token v2.1（效期至多 30 天），加密存於系統 LINE 設定（AES-256、欄位層級安全），排程於到期前自動重簽；Token 一律不落地前端、文件與日誌。
10.4 訊息費用與成本模型（費用主體轉移）
台灣官方帳號月費（2023/9 新制沿用）：輕用量 0 元含 200 則、中用量 NT$800 含 3,000 則（不可加購）、高用量 NT$1,200 含 6,000 則（唯一可加購，加購自每則 NT$0.2 起級距遞減）。計費以發送「人次」計；reply、自動回應與 1:1 聊天不扣額度。單一 OA 架構下，全部推播集中於音訊科技帳號：以 500 教會×平均 200 好友×每月 8 則推播（含課程通知與課前提醒）估算 ≈ 80 萬人次/月，採高用量＋加購約 NT$12～16 萬/月——低於 500 教會各買中用量之總額（NT$40 萬），具規模經濟，但費用主體由教會轉移至音訊科技，必須內建於月費定價（開放議題 OI-09），並以「宮格拉取優先、個人 push 取代 broadcast、Get quota consumption 額度儀表板」三原則省則。

13.2 共用核心模組清單
13.3 落地方式與設計守則
・分層：D365 端以「共用核心 Managed Solution」＋「產品別 Solution」疊加；中介服務以 .NET 共用類別庫（AudioTech.Core.*）＋各產品 API 專案引用；LIFF 前端抽共用元件庫（教會/單位選擇器、匯入精靈、權限矩陣編輯器）。
・守則一：共用模組不得內嵌任一產品之業務字彙（以「租戶」「單位」「成員」抽象命名），產品層再對應「教會/會友」「協會/會員」「補習班/學員」。
・守則二：共用模組僅經介面與事件耦合，禁止產品層反向修改共用層；共用層版本化發佈（SemVer），破壞性變更須遷移指引。
・守則三：檢核規則、範本欄位、通知樣板以設定資料（非程式碼）表達，讓新產品以配置為主、開發為輔。
・演進策略：不預先過度抽象——好牧人2.0 先以清晰模組邊界實作，第二個產品（建議挑流程最像的協會管理）啟動時執行第一次抽離重構，以真實雙載體驗證介面。

類別 | 需求
安全 | Channel Secret／Token：AES-256 加密＋欄位層級安全，永不落地前端/文件/日誌；Webhook 驗簽；教會名錄之「是否為客戶」欄位僅限後台，任何 API 回應與匯出不得包含。
隔離 | 所有查詢/報表/推播/匯入必經 Account 過濾；滲透案例「以 A 教會身分請求 B 教會資源必 403」納入每版自動化測試。
匯入控管 | 單檔 ≤10MB、≤5,000 列；上傳端點限流（每教會每小時 ≤10 批）；原檔處理完即刪；明細不留完整名單快照；範本版本相容檢核。
防爬取 | 教會搜尋不標示申請狀態、限流（UserId 每分鐘 ≤10 次）、異常查詢告警。
可用 | 扣款/推播排程失敗自動重試＋告警；Webhook 冪等；宮格部署失敗自動重試並保留前一版。
效能 | 一鍵出席 postback 於 2 秒內 reply 且冪等；LIFF 首屏 <2s；multicast 分批 500 人、遵循 200 req/s；push 2,000 req/s 上限內佇列化。
備援 | D365 每日完整備份＋異地；Organization 加密金鑰離線保管；宮格底圖與 areas JSON 版本庫留存。
法遵 | 個資最小蒐集與告知；匯入個資檔即用即刪（OI-13 定保存政策）；發票依統編開立；金流費用透明列示。
