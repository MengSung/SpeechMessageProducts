# 三大產品共用架構與開發路線規劃

## 目標

依據既有研究資料、目前工作分支與使用者補充的營運前提，產出一套可執行的三大產品規劃文件：

1. 好牧人 2.0（第一優先）
2. 全坤建設維護系統（CRM 2011 整合）
3. 協會管理系統

成果包含一份完整 Word 計畫書與一份以圖形為主的 HTML 教學／規劃圖譜。文件必須說明共用平台與產品獨立邊界、LINE Channel／Webhook 佈局、Pilot Run、功能開發順序、驗證閘門、整合風險與後續落地方式。

## 已確認事實

- 三個產品的 Webhook 各自獨立。
- 全部約 50 個官方帳號 Channel；每個 Channel 約服務 20 間教會；每個 Channel 有 1,000 個圖文選單限制。
- 建設公司目前為 CRM 2011，全坤建設的程式碼位於 `D:\全坤建設簽名\GtgSignature`。
- 國稅局電子發票 API 初步程式位於 `D:\國稅局電子發票API呼叫`，尚未驗證與上線。
- 好牧人 2.0 上線第一天預計由約 10 間全新試用教會進行 Pilot Run，驗證完整流程。
- 使用者希望依序開發好牧人 2.0、建設公司、協會管理系統。
- 使用者希望以「一個功能開發、驗證、審核通過後再進下一功能」作為主要開發節奏。
- 本階段僅做研究、盤點、規劃與文件產出；不得連線正式組織，不得未經授權啟動新工作包或正式上線作業。

## 需求

### 1. 研究與盤點

- 讀取使用者指定的五個外部資料來源資料夾。
- 盤點目前分支已有的共用基礎、測試、部署與產品領域能力。
- 以唯讀方式分析建設公司與電子發票程式碼，不修改、不呼叫正式外部服務。
- 明確區分已確認能力、待驗證能力與尚未具備能力，不得把目錄存在誤寫成已完成能力。

### 2. 共用架構與產品邊界

- 建立平台共用層、身份／租戶層、LINE 整合層、共用工作流程層與產品領域層的分層建議。
- 說明三個獨立 Webhook 的運行邊界。
- 說明 Channel、教會／組織、使用者、Rich Menu、事件、快取、佇列與告警的隔離規則。
- 防止跨產品、跨 Channel、跨教會、跨租戶與跨使用者資料或狀態洩漏。

### 3. 好牧人 2.0 Pilot Run

- 以第一天 10 間全新試用教會為主要情境。
- 描述各角色第一個行為與最小完整縱向流程。
- 設計從教會建立、使用者／會員、LINE 綁定、服事、通知、回應到結果檢視的 Pilot 驗證路徑。
- 提供 Pilot 前置條件、每日執行程序、證據、停線條件、回滾與通過標準。

### 4. 開發順序

- 提出好牧人 2.0 的可實施功能依賴順序。
- 提出建設公司與協會在共用基礎完成後的建議順序。
- 對每個階段說明前置依賴、輸入、輸出、測試、實機驗證與放行條件。
- 明確區分「程式完成」「測試通過」「Pilot 通過」「正式可用」。

### 5. 文件交付

- 產出繁體中文 Word 計畫書，內容深入、可作為正式執行依據。
- 產出繁體中文 HTML 文件，使用大量 SVG／CSS 圖形與流程圖教導讀者理解架構、角色、資料流、開發閘門與產品路線。
- 文件應包含版本、日期、前提、限制、決策紀錄與待確認事項。
- Word 文件必須經過轉檔、逐頁 PNG 視覺檢查與必要修正。
- HTML 必須進行瀏覽器或靜態結構檢查，確保圖形、文字與連結可讀。

- [ ] HTML 圖形教學文件完成，具備至少總覽架構圖、LINE Channel／Webhook 圖、Pilot 使用者旅程圖、功能依賴圖、開發閘門圖、風險矩陣與三產品時間／順序圖。
- [ ] 所有外部來源與目前分支盤點結果均標示為已確認、待驗證或建議，不混淆事實與推論。
- [ ] 文件明確標出尚未具備或尚未驗證的框架與功能。
- [ ] 文件遵守不連線正式組織、不修改外部程式碼的限制。

## 範圍外

- 不在本任務直接實作三個產品功能。
- 不修改 `D:\全坤建設簽名\GtgSignature` 或 `D:\國稅局電子發票API呼叫`。
- 不呼叫正式 LINE、CRM、D365、國稅局或其他正式組織服務。
- 不把規劃文件當成已完成的生產驗證證據。

- 50 個 Channel 的實際產品／租戶／教會分配表是否已建立。
- 好牧人 2.0 第一批 Pilot 必須包含哪些完整業務功能。
- Word 與 HTML 文件的最終存放位置是否使用本工作樹的 `docs/` 與本任務輸出目錄。
