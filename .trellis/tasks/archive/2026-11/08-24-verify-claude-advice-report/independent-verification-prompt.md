# Claude 建議獨立查證提示詞

你是一位資深 ASP.NET Core、非同步並行、資料一致性與發布風險審查者。請對一份由 Claude 提出的技術建議做獨立查證；不要把任何模型的敘述當成事實，也不要修改產品程式碼、Git 歷史、遠端分支或正式資料。

## 目標

針對附件中的每項主張，使用目前工作樹的程式碼、測試、追蹤腳本、Git 圖譜與可重現命令輸出進行裁定，並交付繁體中文報告。請特別區分：

1. 新版是否相對舊版降低某些風險。
2. 新版是否符合專案定義的正常發布門檻。
3. 哪些項目僅能靠人工 CRM 煙霧測試確認，而不能由靜態閱讀或 trace 腳本證明。

第一項為真，不得自動推導第二項為真。

## 待查證主張

- C3：快照逐欄複製 `Member` 時，若寫入端未與 `SyncRoot` 共用同步協定，是否能靜默得到新舊欄位混合的資料並上傳 CRM。
- 快取：`ListManager` cache 到期／未命中後，是否會得到空白物件；現有登入或使用者資料校正流程是否會重新載入 CRM 資料。
- C4：背景 lambda 在 `UploadData()` 前失敗時，完整例外資訊是否可能完全遺失。
- `bg.end`：它是否只代表背景 scope 結束，而非上傳成功；`verify_trace_invariants.py` 實際驗證哪些條件。
- Git：功能提交 `71b42c31` 是否已併入 `1.0.0.6.DesignNewArchitector`，以及是否應重寫功能分支歷史。
- 前端成功提示：HTTP 回應只代表工作排入背景時，是否不得宣稱 CRM 已成功上傳。
- 發布門檻：既有、未受管理的 fire-and-forget `Task.Run` 與此次變更的關係；比較「漸進式改善」與「正常發布合規」時不得混淆。

## 證據與方法

1. 先閱讀完整控制流與相關資料結構，不能只讀模型引用的片段。
2. 以檔案路徑和行號標示直接證據；若行號會隨工作樹差異變動，改以方法名稱與精確程式片段說明。
3. 使用 Git 祖先關係／提交圖譜驗證合併事實，不能以分支名稱猜測。
4. 對每個 assertion 說明其涵蓋範圍，不能把 `Dispose()`、scope 結束或 HTTP 202 等同於業務成功。
5. 找不到證據時明確寫「證據不足」，不得補完推測。
6. 評估建議的修復方案是否會引入更嚴重回歸，例如 cache 清除後把使用者資料變空白。
7. 保護所有既有未提交變更；只讀取，不覆寫。

## 報告格式

對每項主張以「正確」「部分正確／需修正」「錯誤」「證據不足」裁定，並列出：

- 直接證據
- 實際影響與嚴重度
- Claude 遺漏或誤判之處
- 建議的發布處置：正常發布阻斷、可接受的緊急修補風險、或上線後優先改善

最後提供：

- 已驗證事實與未驗證事實清單
- 正常發布的最低門檻
- 若業務必須緊急發布時的風險接受、限縮曝光、監控、CRM 人工驗證與回滾條件
- 不重寫歷史、也不把本次審查直接變成大範圍重構的理由
