# P7.2 Slice C fresh fixture provisioning design

## Purpose

The existing Slice A descriptor proves only a local contact GUID, profile, and
Windows-owner shape. Its referenced CE contact does not have the required
remote `p7.2-contact-basic-info` marker. The existing expected relationship
list is task-namespaced and static, but its race leader does not match the
descriptor-bound task-owned leader. Neither fact may be repaired by labeling
the pre-existing records as task-owned.

This document defines a separate, opt-in lane that creates a fresh Slice C
fixture subgraph. It is a P7.2 test-fixture control plane only: it does not
change ChurchReport production code, a feature flag, live product traffic,
P6.2, or P8.

## Boundary and data flow

```text
operator explicit -ProvisionFreshFixture -ReplaceStaleDescriptor
  -> parent validates local profile/descriptors/current Windows identity
  -> child acquires one CE 9.1 Data8 runtime scope
  -> child proves existing operational lists are task-owned/static/readable
  -> child creates fresh source contact, fresh leader contact, fresh relationship list
  -> child reads each created entity back exactly once
  -> parent atomically replaces only local fixture descriptor IDs and records local ledger
  -> existing -RepairProbe verifies the complete new graph
```

The lane must never issue Update/Delete/Execute/Associate/Disassociate against
the stale source contact or stale expected relationship list. The existing
operational static lists remain read-only inputs to provisioning.

## Exact remote mutation allowlist

The child may issue at most three `Create` calls:

1. `contact`: `lastname` starts with `P7.2-SC-SOURCE-`; `description` is exactly
   `p7.2-contact-basic-info`.
2. `contact`: `lastname` starts with `P7.2-SC-LEADER-`; CRM read-back must expose
   a `fullname` starting with `P7.2-SC-`.
3. `list`: `listname` starts with `P7.2-SC-REL-`; `type=false`;
   `createdfromcode=2`; `new_contact_race_leager_list` points to the fresh leader.

No caller-selected entity, field, endpoint, connector, profile, CE version,
credential, FetchXML, QueryExpression, or OrganizationRequest is accepted.
The deployment-owned selection remains `crm91` + `Data8` + CE 9.1.

## Provenance and descriptor contract

Before creating data, direct Retrieve must prove every reused operational list
is the exact descriptor ID, logical name `list`, static, contact-list-origin,
and has a `P7.2-SC-` name. This prevents an invalid descriptor from becoming a
write target.

Only after all three Create calls return and exact read-backs pass may the
parent replace these local-only descriptor scalars:

- source fixture `contactId`
- Slice C fixture `smallGroupTargetLeaderContactId`
- Slice C fixture `smallGroupExpectedRelationshipListId`

The parent also writes a local-only ledger containing the created IDs, prior
descriptor bytes, current Windows identity, and a schema version. It is never
written to the repository, console, TRX, evidence JSON, or chat.

## Failure, retry, cleanup, and lifecycle

- Without both explicit switches, no credential is read and no child process
  starts.
- Before a Create begins, `operationExecuted=false`. Once a Create is sent,
  transport/timeout uncertainty becomes `provisioning-ambiguous`: no retry,
  no automatic Delete, no descriptor replacement, and a local pending ledger
  is retained for later read-only reconciliation.
- Every created entity is read back with an exact logical-name/ID/marker
  projection before later work starts. A read-back mismatch is `no-go`.
- A later cleanup lane may delete only ledger-listed IDs after re-proving their
  fresh marker. It deletes the list first and contacts last. An uncertain
  Delete is `no-go`, retains the ledger, and never falls back to stale records.
- The parent snapshots/restores every process environment variable in `finally`,
  destroys its one nonce temporary directory, clears the password reference,
  and disposes Process. The child has exactly one owner each for fixture store,
  Data8 runtime, logger factory, WCF channel/factory, and cancellation scope;
  disposal runs in reverse construction order. Cleanup failure overrides every
  otherwise-green result to release-blocking `no-go`.
- No state is static or shared across requests, processes, profiles,
  organizations, users, or fixture executions. Evidence contains only bounded
  classifications, never IDs, names, nonces, credentials, endpoint, tokens,
  cookies, baseline values, raw exceptions, or CRM responses.

## TDD and acceptance tests

1. A focused store test must fail before implementation if any stale descriptor
   contact/list receives a mutation.
2. Tests must prove the three fresh entities use only the fixed allowlist and
   each has exact read-back before descriptor publication.
3. Tests must prove Create failure/timeout is non-retryable, leaves descriptors
   unchanged, and reports sanitized `provisioning-ambiguous`.
4. PowerShell contract tests must prove parameter-set mutual exclusion, missing
   explicit confirmation/no credential access/no child start, strict evidence
   shape, parent environment restoration, temporary-directory cleanup, and
   `operationExecuted` semantics after timeout or child failure.
5. Focused C# tests, PowerShell contract suite, coverage validator, Release
   build, full solution tests, `git diff --check`, and byte-level UTF-8-no-BOM,
   CRLF-only/final-CRLF checks must pass before any operator is offered the new
   command. The command itself is not run as part of repository verification.

## 2026-08-10 rebaseline: a complete fresh graph is required

This section supersedes the earlier three-Create-only description where it
conflicts. The read-only `RepairProbe` proved that the old source contact lacks
the source marker, the old expected relationship list has a different race
leader, and its area fields are blank. The old records are not remediation
targets. Adding a marker, changing their race leader, or using them as an
implicit owner baseline would turn unknown CRM data into purported task data.

### Selected approach and rejected alternatives

The selected approach is a distinct, explicit fresh-fixture control plane. It
creates a new source contact, new leader contact, and new expected-relationship
list, then establishes the two required memberships and a proven non-service
baseline owner. This is the smallest route that can prove all five Slice C
execution baselines without modifying the stale source or relationship rows.

The following alternatives are deliberately rejected:

- Repairing the stale source marker or stale race leader: this relabels an
  unproven record and breaks provenance.
- Reusing the generic ProductClient `change-race-leader` operation: its input
  accepts arbitrary list and leader IDs and is not a fixture control plane.
- Discovering an owner, weekly report, or list by scanning the Organization:
  this weakens both provenance and bounded-performance guarantees.

### Fixed preflight and read-only proof

Before the first remote mutation, the provision child must create one
request-local CE 9.1 `crm91` + Data8 runtime, validate its WhoAmI result, and
directly prove all of the following. A failed proof emits a sanitized `no-go`,
does not create a ledger entry that authorizes writes, and sends no mutation.

1. The five reused operational lists (`add`, `remove`, `small-group`,
   `transfer-source`, and `transfer-target`) are exact descriptor IDs, static
   contact lists, and carry the `P7.2-SC-` marker.
2. The existing descriptor-bound target leader is a task-marked contact. Its
   `ownerid` resolves by exact ID to an active `systemuser` that differs from
   the Data8 WhoAmI service user. This is the only permitted source for the
   fresh source-contact baseline owner.
3. The transfer target list has either zero or exactly one active weekly report
   for the descriptor's fixed UTC-Sunday date. The query uses the exact list ID
   and date with `TopCount = 2`; it does not enumerate the Organization. Zero
   is a normal no-weekly-report branch; exactly one produces an exact present-
   record lookup; two-or-more, paging, malformed data, or unavailable reads are
   duplicate/unavailable no-go states and must never select or repair a report.
4. The old source contact and old expected relationship list are not read as
   write targets and are never repaired, updated, associated, deleted, or
   re-published by this lane.

### Exact remote mutation allowlist

After that proof, the child may perform only the following fixed operations,
all with server-owned entity names and attributes:

1. Create one `contact` whose `lastname` begins `P7.2-SC-SOURCE-` and whose
   `description` equals `p7.2-contact-basic-info`.
2. Create one `contact` whose `lastname` begins `P7.2-SC-LEADER-`; an exact
   read-back must expose a `fullname` beginning `P7.2-SC-`.
3. Create one static contact `list` whose `listname` begins `P7.2-SC-REL-`,
   `type=false`, `createdfromcode=2`, and whose area leader plus race leader
   both reference the fresh leader while `new_area_name` equals the fixed
   expected value. This new list replaces only the descriptor's expected
   relationship-list scalar; it is not the operational small-group list.
4. Execute exactly two `AddListMembersListRequest` calls to add the fresh
   source contact to the already-proven `remove` and `transfer-source` lists.
5. Execute exactly one `AssignRequest` to assign the fresh source contact to
   the pre-proven active non-service baseline owner.

Every successful mutation receives an exact read-back before the next one.
The final graph proof must show that the source is absent from the add and
transfer-target lists, present in the remove and transfer-source lists, has no
matching present record, has a primary-list value other than the transfer
target, and has an owner different from the Data8 service user. The existing
`TryProveFixtureGraph` execution gate remains the final authority before any
Slice C capability dispatch.

### Pending ledger, publication, ambiguity, and cleanup

The parent supplies one internally generated, non-reparse, current-user local
ledger path to the child. The ledger is recovery data, not live evidence: it
contains only the fresh IDs, nonce-derived markers, profile binding, Windows
owner, and completed mutation stage; it is never written to the repository,
TRX, console, sanitized JSON, browser, or chat. After every mutation that
returns an ID or succeeds, the child atomically advances that ledger before
starting the next mutation.

An exception or timeout after a mutation begins is `provisioning-ambiguous`.
The child never retries the request, never guesses an ID, never changes the
active descriptors, and never auto-deletes potentially committed data. It
retains the pending ledger for a separate exact-ID, read-only reconciliation
or an explicitly requested cleanup lane.

Only after all final graph reads succeed and the child exits successfully may
the parent atomically replace the two local descriptors with fresh source,
leader, and expected-relationship IDs. The parent must never restore or
reactivate the stale descriptor bytes. Descriptor publication failure is
`no-go`, leaves the pending ledger recoverable, and does not make the fresh
records eligible for normal execution.

An explicit cleanup lane first proves every ledger-listed entity by exact ID,
logical name, and marker. It removes the two source memberships with exact
read-backs, deletes the fresh relationship list, then deletes the fresh source
and leader contacts. It removes the active descriptor only after all remote
cleanup read-backs succeed. Any ambiguity or cleanup failure retains the ledger
and blocks further writes in this family; no record is deleted based on a name
search or a stale descriptor.

### Required offline proof before the operator handoff

The implementation must add test-first proof for the complete sequence:

1. stale IDs receive zero mutation calls;
2. missing static-list, duplicate/unavailable weekly-report, active-owner, or
   WhoAmI preconditions produce zero mutations, while zero-active weekly-report
   remains a proven normal branch;
3. each allowed Create/associate/Assign request has the exact fixed shape and
   is read back before the next request;
4. timeout or post-dispatch fault produces one non-retryable ambiguous result,
   leaves descriptors unpublished, and retains only the bounded pending ledger;
5. cleanup accepts only ledger-proven fresh entities and follows the reverse
   membership/list/contact order; and
6. PowerShell parameter sets, evidence schemas, environment restoration,
   temporary cleanup, and current-user descriptor binding remain fail-closed.
