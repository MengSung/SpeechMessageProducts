# CE 9.1 live smoke evidence — 2026-07-31

## 結論

CE 9.1 的真機驗證尚未通過，但阻塞已從模糊的「缺少可用 Kerberos/WinRM
工作階段」縮小為 D365APP01 CRM Web 應用程式內部的 URI 處理例外。此文件
只記錄不含密碼、權杖、Cookie、完整 HTTP header 或 ticket 的診斷事實。

這不是 Gateway connector 已失敗的證據，也不是可以透過放寬驗證、改 DNS、
修改 hosts、使用 Basic/明文 WinRM 或建立密碼型登入來繞過的 gate。

## 對 Gateway 的影響

1. 真機 CE 9.1 的 `WhoAmI`、metadata、operation、paging 證據仍為 **blocked**。
2. 這個 500 必須由 CRM 管理端在受控主控台依完整 ASP.NET 事件 stack trace 及受支援的
   Dynamics Deployment Manager／Claims-IFD 設定流程處理；診斷工具只輸出安全摘要，不要猜測或直接修改
   DC、DNS、ADFS、IIS 或 CRM 資料庫。
3. Gateway 的本機安全與契約工作可繼續，不可因這個外部 gate 空轉。
4. CRM 修正後，必須以明確目標重新執行 connector-owned smoke；不要把匿名
   `HEAD` 或瀏覽器既有 Cookie 視為 Gateway 的驗證證據。

## 本次 repository 修正

`docs/scripts/Invoke-DynamicsLiveSmoke.ps1` 不再內建 `jesus` 或任何 CRM host。
啟用 `-EnableLive` 必須明確提供 `-WebApiRoot`，缺少時會在任何外部請求前
fail-closed。工具亦移除了與 connector 驗證語意不同的獨立 HTTPS `HEAD`；
真正的 `WhoAmI` 是唯一的 connector-authentication 判斷來源。

## CRMWeb／Claims-IFD 唯讀鑑別工具

已新增 `docs/scripts/Get-DynamicsCrmWebIfdDiagnostics.ps1`，用來把目前 500 的
鑑別工作限制在 D365APP01 的受支援部署邊界。它預設不發送 CRM 要求，也不建立
PSSession、不接收帳密或權杖、不寫檔、不修改 IIS／AD FS／DNS／WinRM／CRM 設定或
資料庫。它只會回傳：

- 明確 Web API root 的本機 URI 驗證結果；
- 有界的 ASP.NET 1309 URI 例外事件；
- `ClaimsSettings`／`IfdSettings` 的欄位名稱與語法形狀（不輸出內部 URI 值）；
- 相關 HTTPS binding 與憑證中繼資料；以及
- 僅在明確傳入 `-ProbeWhoAmI` 時才產生的一次、可確定釋放 HTTP 資源的 WhoAmI
  response-header probe。

在 D365APP01 的既有核准 Deployment PowerShell／管理工作階段中，先執行下列
**無網路 probe** 的最小指令；不要將結果寫入檔案：

```powershell
.\docs\scripts\Get-DynamicsCrmWebIfdDiagnostics.ps1 `
  -WebApiRoot 'https://sunnyvalechback.speechmessage.com.tw/api/data/v9.1/' `
  -LookbackMinutes 120 `
  -MaxEvents 3 | ConvertTo-Json -Depth 8
```

判讀順序如下：

1. `DeploymentSettings` 顯示 `deployment-cmdlet/unavailable` 時，這是 Deployment
   PowerShell／權限邊界，應改在本機 Deployment Manager 的 Claims／IFD 頁面讀取；
   不以 CRM SQL、Registry 或臨時匯入工具替代。
2. 若 URI-like 欄位出現 `Present=false` 或 `AbsoluteUriSyntax=false`，或 host/domain
   欄位出現 `ContainsWhitespace=true`，或必要 setting 顯示 `Enabled=false`，這是可由
   CRM 管理者透過受支援 Claims／IFD 設定流程修正的具體候選。
3. 若設定形狀均正常但 1309 仍出現，保留輸出的事件時間、provider、ID、level、`MatchKind`
   與欄位名稱交由 CRM 管理者比對；診斷輸出刻意不帶 stack trace、cookie、token 或例外訊息，
   不要猜測特定設定值或進行資料庫／IIS 直改。
4. 只有需要建立新事件關聯時才加上 `-ProbeWhoAmI`。目前已經有一次造成 HTTP 500 的
   證據，因此第一次設定鑑別不需要重送要求。

## CRM 修正後的最小重測

在核准的 D365APP01 網域工作階段、且 CRM 管理端已確認上述 500 修正後：

```powershell
.\docs\scripts\Invoke-DynamicsLiveSmoke.ps1 `
  -EnableLive `
  -WebApiRoot 'https://sunnyvalechback.speechmessage.com.tw/api/data/v9.1/' `
  -CeVersion '9.1' `
  -CredentialSource HostIdentity `
  -NoRestore
```

只有這個指令回傳 `WhoAmI` 成功，才可把 CE 9.1 HostIdentity transport 標記為
已驗證。若 CRM 之後轉為 ADFS/IFD redirect，則 HostIdentity 不適用；需另行依
既有規格評估核准的非密碼 service-workload 流程，不能退回 ROPC 或明文密碼。

## 後續唯讀定位與 IFD 精靈證據

2026-07-31 的受控唯讀事件檢視已確認，HTTP 500 的第一個 CRM frame 是：

```text
Microsoft.Crm.Authentication.Claims.CrmFederatedAuthenticationModule
  .UpdateRedirectingEventArgsNonPathBasedUrl
```

這將故障定位在 CRM 的 **federation redirect URI 建構**。事件本身沒有指出特定
設定欄位，因此不能據此猜測性修改 DNS、AD FS、IIS、Registry、CRM SQL 或
Kerberos。

Deployment Manager 的 IFD 精靈畫面也已顯示下列輸入通過 system check：

- External domain：`auth.speechmessage.com.tw`
- Web application root domain：`speechmessage.com.tw`
- Organization Web Service root domain：`speechmessage.com.tw`
- Discovery Web Service root domain：`discodev91.speechmessage.com.tw`

此結果證明這組**精靈中輸入的值**語法與系統檢查相容；它本身不等於已持久化設定，
也不等於 CRMWeb live redirect 已通過。若操作者是在這個精靈工作階段中剛把外部
網域由 URI 改為 hostname，應只透過精靈完成該單一變更，之後才重跑一次 WhoAmI。
若精靈原本就顯示這些值，勿重複套用或重複 smoke；應由既有核准的 Deployment
Manager／DWS 管理工作階段比對 Claims／IFD 的實際持久化設定。

遠端 Negotiate 身分與 CRM Deployment PowerShell snap-in 已可驗證，但該 snap-in
在此環境無法以目前 token 取得 DWS default，並在指定 DWS URL 時要求既有
`PSCredential`。沒有讀取、提示、轉移或保存任何 credential；因此自動 PowerShell
讀取設定在沒有既有核准 DWS 管理 session 時正確地 fail-closed。
