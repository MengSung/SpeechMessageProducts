# 查證設計

## 證據層級

1. 目前工作樹中的可執行程式碼與測試。
2. Git 提交圖譜、分支包含關係與檔案歷史。
3. 可重現的建置、測試及追蹤驗證輸出。
4. 專案規範與既有任務文件。
5. Claude／Codex 的敘述；只作為待驗證假說，不作為證據本身。

## 查證邊界

- 追蹤 `SaveIntegrate` 從 HTTP 回應、背景快照、DI scope、CRM 上傳到 trace 結束事件的完整控制流。
- 追蹤 `ListManager` 的 cache key、到期策略、未命中行為與實際重載入口。
- 追蹤 `SmallGroupData`／`Member` 的讀寫路徑，判斷 `SyncRoot` 是否有所有讀寫端共同遵守。
- 驗證 `verify_trace_invariants.py` 實際檢查的條件，區分 scope 結束與業務成功。
- 用 Git 祖先關係驗證功能提交是否已併入 `1.0.0.6.DesignNewArchitector`。

## 判定格式

每項主張以「正確」「大致正確但需修正」「錯誤」「目前證據不足」之一判定，並列出程式證據、影響、Claude 遺漏的限制，以及本報告的建議。

## 發布判斷模型

分開回答兩個問題：

1. 新版相較目前生產版，是否降低了部分風險？
2. 新版是否達到本專案明定的正常發布門檻？

第一題為真不會自動推出第二題為真。若屬緊急修補，另列風險接受、限縮曝光、監控及回滾條件。

## 不變性與回滾

本任務不修改產品程式碼；若規劃或報告內容有誤，只需修正文檔。既有工作樹變更必須保持原樣，不執行 reset、checkout、rebase、force push 或提交。
