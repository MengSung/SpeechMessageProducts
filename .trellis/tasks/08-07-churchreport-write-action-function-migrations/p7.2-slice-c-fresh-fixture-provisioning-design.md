# P7.2 Slice C fresh fixture provisioning design

## Purpose

The existing Slice A descriptor proves only a local contact GUID, profile, and
Windows-owner shape. Its referenced CE contact does not have the required
remote `p7.2-contact-basic-info` marker. The existing expected relationship
list is task-namespaced and static, but its race leader does not match the
descriptor-bound task-owned leader. Neither fact may be repaired by labeling
the pre-existing records as task-owned.

This document defines a separate, opt-in lane that creates a fresh Slice C
fixture subgraph. It is a P7.2 test-fixture control plane only: it does not
change ChurchReport production code, a feature flag, live product traffic,
P6.2, or P8.

## Boundary and data flow

```text
operator explicit -ProvisionFreshFixture -ReplaceStaleDescriptor
  -> parent validates local profile/descriptors/current Windows identity
  -> child acquires one CE 9.1 Data8 runtime scope
  -> child proves existing operational lists are task-owned/static/readable
  -> child creates fresh source contact, fresh leader contact, fresh relationship list
  -> child reads each created entity back exactly once
  -> parent atomically replaces only local fixture descriptor IDs and records local ledger
  -> existing -RepairProbe verifies the complete new graph
```

The lane must never issue Update/Delete/Execute/Associate/Disassociate against
the stale source contact or stale expected relationship list. The existing
operational static lists remain read-only inputs to provisioning.

## Exact remote mutation allowlist

The child may issue at most three `Create` calls:

1. `contact`: `lastname` starts with `P7.2-SC-SOURCE-`; `description` is exactly
   `p7.2-contact-basic-info`.
2. `contact`: `lastname` starts with `P7.2-SC-LEADER-`; CRM read-back must expose
   a `fullname` starting with `P7.2-SC-`.
3. `list`: `listname` starts with `P7.2-SC-REL-`; `type=false`;
   `createdfromcode=2`; `new_contact_race_leager_list` points to the fresh leader.

No caller-selected entity, field, endpoint, connector, profile, CE version,
credential, FetchXML, QueryExpression, or OrganizationRequest is accepted.
The deployment-owned selection remains `crm91` + `Data8` + CE 9.1.

## Provenance and descriptor contract

Before creating data, direct Retrieve must prove every reused operational list
is the exact descriptor ID, logical name `list`, static, contact-list-origin,
and has a `P7.2-SC-` name. This prevents an invalid descriptor from becoming a
write target.

Only after all three Create calls return and exact read-backs pass may the
parent replace these local-only descriptor scalars:

- source fixture `contactId`
- Slice C fixture `smallGroupTargetLeaderContactId`
- Slice C fixture `smallGroupExpectedRelationshipListId`

The parent also writes a local-only ledger containing the created IDs, prior
descriptor bytes, current Windows identity, and a schema version. It is never
written to the repository, console, TRX, evidence JSON, or chat.

## Failure, retry, cleanup, and lifecycle

- Without both explicit switches, no credential is read and no child process
  starts.
- Before a Create begins, `operationExecuted=false`. Once a Create is sent,
  transport/timeout uncertainty becomes `provisioning-ambiguous`: no retry,
  no automatic Delete, no descriptor replacement, and a local pending ledger
  is retained for later read-only reconciliation.
- Every created entity is read back with an exact logical-name/ID/marker
  projection before later work starts. A read-back mismatch is `no-go`.
- A later cleanup lane may delete only ledger-listed IDs after re-proving their
  fresh marker. It deletes the list first and contacts last. An uncertain
  Delete is `no-go`, retains the ledger, and never falls back to stale records.
- The parent snapshots/restores every process environment variable in `finally`,
  destroys its one nonce temporary directory, clears the password reference,
  and disposes Process. The child has exactly one owner each for fixture store,
  Data8 runtime, logger factory, WCF channel/factory, and cancellation scope;
  disposal runs in reverse construction order. Cleanup failure overrides every
  otherwise-green result to release-blocking `no-go`.
- No state is static or shared across requests, processes, profiles,
  organizations, users, or fixture executions. Evidence contains only bounded
  classifications, never IDs, names, nonces, credentials, endpoint, tokens,
  cookies, baseline values, raw exceptions, or CRM responses.

## TDD and acceptance tests

1. A focused store test must fail before implementation if any stale descriptor
   contact/list receives a mutation.
2. Tests must prove the three fresh entities use only the fixed allowlist and
   each has exact read-back before descriptor publication.
3. Tests must prove Create failure/timeout is non-retryable, leaves descriptors
   unchanged, and reports sanitized `provisioning-ambiguous`.
4. PowerShell contract tests must prove parameter-set mutual exclusion, missing
   explicit confirmation/no credential access/no child start, strict evidence
   shape, parent environment restoration, temporary-directory cleanup, and
   `operationExecuted` semantics after timeout or child failure.
5. Focused C# tests, PowerShell contract suite, coverage validator, Release
   build, full solution tests, `git diff --check`, and byte-level UTF-8-no-BOM,
   CRLF-only/final-CRLF checks must pass before any operator is offered the new
   command. The command itself is not run as part of repository verification.
