# 條件式修正設計（尚未實施）

## 邊界與判斷
使用者看到的 Work 模型選單與 coding 模型清單可能使用不同來源，不能以名稱、medium 標籤或模型摘要能力推斷實際上游支援。
下一個決定性證據是同一帳號、同一 Work 畫面的即時模型能力：僅讀 6.1 Sol 與 6.2 Sol 的 slug、configurable_thinking_effort、thinking_efforts、default_thinking_effort、product_features.attachments；不記錄認證、URL query、帳號識別或對話。

## 分支方案
1. Work 原始回應缺能力：先核對供應端實際宣告；若供應端也未支援，記錄限制，不在本機偽造支援。
2. 原始回應完整但本地轉換丟失：只修已確認的轉換層，以精確 slug 限縮，不改其他模型或提供者。先獨立測試，再經使用者核准切換。
3. 回應與轉換完整但畫面仍隱藏：追到控制項的過濾或快取判斷；不先清空所有聊天資料、不任意改簽章安裝包。
4. 單純 coding 圖片宣告缺失不是 Work 已證實根因；僅當來源與上游支援均證實後，才評估更新其產生器，不手改會被覆蓋的產物冒充永久修正。

## 隔離與回復
不動 LINE、登入、API key、Cookie、金流、產品設定或其他進行中的聊天。任何修改前取得方案同意，確認資源擁有者，備份精確目標及雜湊。若來源為第三方專案，另遵守該專案指引。
不開長駐代理、不新增排程、不關閉使用者工作。若必須重啟，先說明會中斷的對象並獨立取得同意。

## 驗證層次
分別報告：畫面出現控制項／圖片可加入、請求含指定 effort／圖片、上游接受、上游有效處理。不能以 HTTP 200、medium 標籤或 token 數變化冒充後兩項。
使用合成非敏感圖片與不含私有資料的最小請求，待使用者同意才發出；以 6.1 行為不變及其他模型設定雜湊不變作回歸檢查。
