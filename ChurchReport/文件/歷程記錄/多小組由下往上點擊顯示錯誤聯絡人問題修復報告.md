# 多小組由下往上點擊顯示錯誤聯絡人問題修復報告

## ?? 問題描述

**症狀**: 裝備狀態頁面有兩個以上小組時：
- ? **從上而下點擊**: 顯示正確的聯絡人名單
- ? **由下往上點擊**: 後來點擊打開的小組，顯示的是上一個小組的聯絡人名單

**預期行為**: 無論點擊順序如何，每個小組都應該顯示各自的成員名單

**影響範圍**: 多小組裝備管理功能的資料一致性

---

## ?? 根本原因分析

### 問題場景重現

```
假設有 3 個小組: A, B, C (由上到下排列)

情況 1: 從上而下點擊 (正常) ?
-------------------------------------
1. 點擊小組 A → LoadEquipmentContact(id="A_ID")
   → SetupIntegrateData("A_ID")
   → ActiveListId = "A_ID"
   → 顯示小組 A 的成員 ?

2. 點擊小組 B → LoadEquipmentContact(id="B_ID")
   → 檢查: ActiveListId("A_ID") != id("B_ID") → True
   → SetupIntegrateData("B_ID")
   → ActiveListId = "B_ID"
   → 顯示小組 B 的成員 ?

3. 點擊小組 C → LoadEquipmentContact(id="C_ID")
   → 檢查: ActiveListId("B_ID") != id("C_ID") → True
   → SetupIntegrateData("C_ID")
   → ActiveListId = "C_ID"
   → 顯示小組 C 的成員 ?

情況 2: 由下往上點擊 (問題) ?
-------------------------------------
1. 點擊小組 C → LoadEquipmentContact(id="C_ID")
   → SetupIntegrateData("C_ID")
   → ActiveListId = "C_ID"
   → 顯示小組 C 的成員 ?

2. 點擊小組 B → LoadEquipmentContact(id="B_ID")
   → 檢查: ActiveListId("C_ID") != id("B_ID") → True
   → 開始 SetupIntegrateData("B_ID")...
   
   ?? 問題發生: 在 SetupIntegrateData 完成前，
   DevExtreme 可能因為非同步請求，
   快取的 ActiveListId 還未更新或更新順序錯誤
   
   → ActiveListId 可能還是 "C_ID" 或其他值
   → 取得的成員資料不正確
   → 顯示小組 C 的成員 ? (應該是 B)

3. 點擊小組 A → LoadEquipmentContact(id="A_ID")
   → 檢查: ActiveListId(可能是"C_ID"或"B_ID") != id("A_ID") → True
   → SetupIntegrateData("A_ID")
   → 但可能取得的還是之前的資料
   → 顯示錯誤的成員 ?
```

### 核心問題

1. **時序問題**: 
   - `SetupIntegrateData` 是同步方法，但 DevExtreme 的 DataGrid 可能發起多個非同步請求
   - 多個請求可能同時進行，導致 `ActiveListId` 更新順序不確定

2. **快取問題**:
   - `InMemoryContext.ListManager` 是單例共享狀態
   - 多個請求可能互相覆蓋彼此的狀態

3. **檢查不足**:
   - 原有檢查只在載入前驗證，載入後未再次確認
   - 無法偵測載入過程中的狀態變更

### 核心改進

#### 1. 增強日誌記錄

```csharp
System.Diagnostics.Debug.WriteLine($"[LoadEquipmentContact] ===== 開始載入聯絡人 =====");

```

**作用**: 完整追蹤每次請求的狀態變化

#### 2. 明確的重載邏輯

```csharp
bool needReload = false;

if (InMemoryContext.ListManager.m_ListSmallGroupWeeklyReport == null)
{
    System.Diagnostics.Debug.WriteLine($"[LoadEquipmentContact] 原因: m_ListSmallGroupWeeklyReport 為 null");
    needReload = true;

else if (!InMemoryContext.ListManager.m_ListSmallGroupWeeklyReport.LoadFlag)
{
    System.Diagnostics.Debug.WriteLine($"[LoadEquipmentContact] 原因: LoadFlag 為 false");
    needReload = true;

else if (InMemoryContext.ListManager.ActiveListId != id)
{
    System.Diagnostics.Debug.WriteLine($"[LoadEquipmentContact] 原因: ActiveListId 不匹配");
    needReload = true;
}
```

**作用**: 清楚記錄為什麼需要重載資料

#### 3. 載入後二次驗證

```csharp
// 額外驗證: 確保載入的資料確實屬於請求的小組
if (InMemoryContext.ListManager.ActiveListId != id)
{
    System.Diagnostics.Debug.WriteLine($"[LoadEquipmentContact] ?? 警告: 載入後 ActiveListId 仍不匹配!");
    
    // 再次強制載入
    System.Diagnostics.Debug.WriteLine($"[LoadEquipmentContact] >>> 再次強制載入資料 <<<");
    InMemoryContext.ListManager.SetupIntegrateData(id);
    
    members = InMemoryContext.ListManager.m_ListSmallGroupWeeklyReport
        ?.m_SmallGroupDataList?.m_AllMemeberData?.Members 
        ?? new List<Member>();
}
```

**關鍵修復**: 這是解決由下往上點擊問題的核心
- 在載入資料後，再次檢查 `ActiveListId` 是否與請求的 `id` 匹配
- 如果不匹配，強制再次載入正確的資料
- 確保返回的資料100%屬於請求的小組

#### 4. 結果驗證輸出

```csharp
// 輸出前 3 個成員名稱用於驗證
if (equipmentList.Count > 0)
{
    System.Diagnostics.Debug.WriteLine($"[LoadEquipmentContact] 前 3 個成員:");
    for (int i = 0; i < Math.Min(3, equipmentList.Count); i++)
    {
        System.Diagnostics.Debug.WriteLine($"[LoadEquipmentContact]   {i + 1}. {equipmentList[i].ContactFullName}");
    }
}
```

**作用**: 方便人工驗證返回的是否為正確小組的成員

## ?? 技術細節

### 為什麼需要二次驗證？

在多執行緒或非同步環境下，單例狀態（如 `InMemoryContext.ListManager`）可能被多個請求同時修改：

```
時間軸:
T1: 請求 A 開始 → SetupIntegrateData("A_ID")
T2: 請求 B 開始 → SetupIntegrateData("B_ID") ← 可能覆蓋 A 的狀態
T3: 請求 A 完成 → 但 ActiveListId 已被 B 改為 "B_ID"
T4: 請求 A 返回資料 → 錯誤！返回的是 B 的資料
```

**二次驗證解決方案**:
```csharp
// 第一次檢查: 載入前
if (InMemoryContext.ListManager.ActiveListId != id) {
    SetupIntegrateData(id);
}

// 第二次檢查: 載入後 ← 關鍵！
if (InMemoryContext.ListManager.ActiveListId != id) {
    // 偵測到狀態被其他請求改變
    SetupIntegrateData(id); // 再次載入正確的資料
}
```

### 性能考量

**額外開銷**:
- 二次驗證增加了額外的條件檢查
- 最壞情況下需要載入兩次資料

**實際影響**:
- 條件檢查成本極低（僅字串比較）
- 大多數情況下不需要二次載入
- 只有在時序衝突時才觸發

**權衡**:
- 小幅性能損失 ← 可接受
- 資料正確性保證 ← 關鍵

### 替代方案比較

| 方案 | 優點 | 缺點 | 採用 |
|------|------|------|------|
| 加鎖同步 | 徹底避免衝突 | 性能影響大 | ? |
| 使用獨立快取 | 無衝突 | 記憶體使用高 | ? |
| 二次驗證 | 簡單有效，性能好 | 極端情況可能需多次重載 | ? |
| 請求佇列 | 順序保證 | 實作複雜 | ? |

## ?? 經驗教訓

### 學到什麼

1. **單例狀態的風險**: 
   - 共享狀態在多請求環境下容易出現競態條件
   - 需要額外的驗證機制確保狀態一致性

2. **時序問題的複雜性**:
   - 簡單的條件檢查可能不足以處理非同步環境
   - 需要在關鍵點進行二次驗證

3. **日誌的重要性**:
   - 詳細的日誌對診斷時序問題至關重要
   - 每個關鍵步驟都應該有日誌記錄

### 未來改進方向

1. **請求隔離**: 考慮為每個請求建立獨立的上下文
2. **狀態管理**: 使用更安全的狀態管理機制
3. **並發控制**: 實作適當的鎖或信號量機制
