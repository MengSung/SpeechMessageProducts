## 1. 三大硬性要求 — 逐項判定

### ① 正式環境（Release）不可跑「評估效能(計時器)」程式 — 🟢 大致通過，但有 F-2 例外

**例外（F-2，詳見第 2 節）**：`PerfPhase.cs` 未整檔 `#if DEBUG`，Release 仍存在並被 ~50 處控制器呼叫；`using` 形式近乎零成本，但 `Func<T>` 形式會在 Release 配置 closure。**這是唯一一處「Release 仍有計時相關額外開銷」**，需修正以完全符合第①要求。

### ② Release 絕不可寫入 Trace.log — 🟢 通過（靜態確認，待 DLL 掃描蓋章）

關鍵在於：**全專案唯一會把訊息寫進 `Logs\Trace.log` 的 `TextWriterTraceListener`，整段位於 `Program.cs` 的 `#if DEBUG` 內**（`Program.cs:17,41-43,94-249`）。因此：

1. **Release 配置下根本沒有檔案 Listener** → 任何 `Trace.WriteLine` 都只會落到預設的 `DefaultTraceListener`（OutputDebugString），**不會寫檔**。
2. 剖析子系統一律用 `System.Diagnostics.Debug.WriteLine`（`[Conditional("DEBUG")]`），Release 編譯時**呼叫與字串一起被剝除**（`RequestProfiler`/`StartupProfiler`/`PerfProfilingMiddleware` 皆然）。
3. `TraceLoggerProvider`（ILogger→Trace 橋接，`Logging/TraceLoggerProvider.cs:96`）雖**非** `#if DEBUG`、而是由設定 `EnableTrace`（預設 `env.IsDevelopment()`）控制（`Startup.cs:656-668`），但因第 1 點，Release 即使註冊它也寫不進檔案。正式設定 `appsettings.json:34`、`appsettings.Production.json:16` 皆 `EnableTrace=false`，屬第二層防護。

**結論**：Release 不會有 `[Perf]` 等剖析輸出寫入 Trace.log。**唯一還沒做的是 spec 第 7 節要求的「Release DLL `[Perf` 字串掃描」實證**——靜態推論為通過（`[Perf]` 字面值只存在於 `#if DEBUG` 的 `RequestProfiler`；`PerfPhase` 型別名不含 `[Perf` 子字串），但建議補跑一次以蓋章（見補強計畫 Task 3）。

> ⚠️ **註記（非缺陷）**：保護 Trace.log 的是「`#if DEBUG` 的 Listener」這個**不變量**。若日後有人把 `InitializeTraceListener` 移出 `#if DEBUG`，第②要求即破功。建議把此不變量寫成註解/檢查（補強計畫 Task 3 附帶）。

### ③ 絕不可 Session Leakage — 🟡 剖析子系統通過；但 F-1（伴隨的 FeeManagement 優化）為高風險未驗證

**(a) 剖析子系統本身 — 🟢 通過**

- **每請求狀態只存 `HttpContext.Items`**：`RequestProfiler` 放在 `Items["__PerfProfiler"]`（`RequestProfiler.cs:16`、`PerfProfilingMiddleware.cs:25-26`），請求結束即回收。Action 計時器、route 樣板亦同存 `Items`（`PerfTimingActionFilter.cs:22-23`）。
- **無 static/singleton 可變的「使用者資料」**：`ProfilingSwitch.Enabled`（設定旗標）與 `TimedToolUtilityProvider._wrapLock`（鎖物件）是僅有的 static，皆非個資。
- **裝飾器無跨請求狀態**：`TimedOrganizationService` 只持有「內層服務 + `IHttpContextAccessor`」，每次呼叫以 `_http.HttpContext.Items` 解析**當前請求**的 profiler（`TimedOrganizationService.cs:25-29`）。`TimedToolUtilityProvider` 把 singleton 的 `m_Crm2011OrganizationService` 換成計時版（冪等 + 鎖，`TimedToolUtilityProvider.cs:25-40`），該計時版本身無狀態，併發各請求各自寫入自己的 profiler → 安全。
- **log 不含個資**：輸出只有「數字 + entity 邏輯名 + 操作名」。
  - Route 樣板由 route values 的 **key** 組成（`{id}`、`{discipleLessonsId}`），非實際值（`PerfTimingActionFilter.cs:44-78`）；中間件再以 `SanitizePath` 把 GUID/純數字段落換成 `{id}`（`PerfProfilingMiddleware.cs:59-79`）。2026-06-18 報告中所有 `path=` 皆為樣板（如 `/SmallGroup/IntegrateView/{LoginParameter}`），無實際 GUID/帳號 → 交叉佐證消毒有效。
  - Phase 名稱全為靜態字串字面值（如 `"FeeManagement.Fee.SetupPresentFeeList"`），`phaseName` 變數的實參亦皆字面值（`FeeManagementController.cs:58,88,142,191,244,284`；`PersonalController.cs` 同型），**未夾帶 `discipleLessonsId`/`contactId`**（已逐一查核）。

**(b) 伴隨完成的 FeeManagement 去重優化 — 🔴 F-1 高風險（詳見第 3 節）**

這部分不是「剖析」程式，而是 Codex 一併實作的 2026-06-18 **P2** 瓶頸修正（課程/繳費資料重複載入）。它引入了**未綁定當前 session 登入身分**的重用判斷，命中 2026-06-18 報告自己訂下的「Session Leakage 零容忍」硬性規則第 1、2、3 條。**必須先驗證或還原**。

## 2. F-2 詳述：`PerfPhase` 在 Release 仍有非零開銷（🟠 中）

**現況**（`Diagnostics/Profiling/PerfPhase.cs`，全檔**未**包 `#if DEBUG`）：
```csharp
public static class PerfPhase
{
    public static IDisposable Measure(HttpContext context, string name)
    {
#if DEBUG
        return RequestProfiler.MeasurePhase(context, name);
#else
        return NoopDisposable.Instance;     // Release：回傳共用單例
#endif
    }
    public static T Measure<T>(HttpContext context, string name, Func<T> action)
    {
        using (Measure(context, name)) { return action(); }   // Release：呼叫端 lambda 仍會配置 closure
    }
}
```

**問題**：設計意圖是讓控制器呼叫點不必各自寫 `#if DEBUG`（立意良好），但代價是 `PerfPhase` 型別與其呼叫點**存在於 Release 組件並會被執行**：

- **`using (PerfPhase.Measure(ctx, name)) { … }` 形式（約 34 處）**：Release 回傳 `NoopDisposable.Instance`（單例、**無配置**），`using` 只是 try/finally 呼叫空 `Dispose()`。開銷為奈秒級、無 GC，**可接受但非「零」**。
- **`PerfPhase.Measure(ctx, name, () => …)` 形式（約 16 處，部分在迴圈內）**：呼叫端的 lambda 捕捉 `this`/區域變數，**在 Release 配置下每次呼叫都會配置一個 closure 物件 + delegate**。其中 `EquipmentController.cs:365`（`RetrieveDiscipleLesson`）位於**逐課程迴圈內**、`PersonalController.cs:485`（contact 批次）等屬熱路徑 → 正式環境會產生本來不存在的 Gen0 配置與 GC 壓力。

**受影響呼叫點（`Func<T>` 形式，需處理）**：
`EquipmentController.cs:146,269,311,325,333,341,365,399`；`FeeManagementController.cs:247,302`；`PersonalController.cs:216,232,276,421,485`。

**影響評等**：非安全問題、不寫 log、不影響正確性；屬「違反 spec 第①硬性限制『Release 零額外開銷』」+ 與本專案「零配置/零洩漏」文化不符。鑑於使用者明言「確保正式環境不要有評估效能(計時器)的程式被跑到」，**應修正**（補強計畫 Task 2）。

## 3. F-1 詳述：FeeManagement 去重的登入綁定破洞（🔴 高，須先驗證/補強）

### 3.1 觀察到的程式

Codex 把原本「每次請求都重載」改為「已載入則略過」：

```csharp
// FeeManagementController.cs:410-439
private void EnsureLessonListLoaded(string phaseName)
{
    var account  = InMemoryContext.FeeList.m_Account;     // ← 取自 FeeList 自己存的欄位
    var password = InMemoryContext.FeeList.m_Password;
    if (InMemoryContext.FeeList.IsLessonListLoadedFor(account, password)) return;   // 命中即略過
    using (PerfPhase.Measure(HttpContext, phaseName)) { InMemoryContext.FeeList.SetupLessonList(account, password); }
}
private void EnsurePresentFeeListLoaded(string discipleLessonsId, string phaseName)
{
    if (InMemoryContext.FeeList.IsPresentFeeListLoadedFor(discipleLessonsId)) return;  // 只看 discipleLessonsId
    using (PerfPhase.Measure(HttpContext, phaseName)) { InMemoryContext.FeeList.SetupPresentFeeList(discipleLessonsId); }
}
```
```csharp
// FeeList.cs
public bool IsLessonListLoadedFor(string account, string password)        // :191
    => _lessonListLoaded && LessonList != null && IsSameLogin(account ?? "", password ?? "");
public bool IsPresentFeeListLoadedFor(string discipleLessonsId)           // :198  ← 無任何登入綁定
    => !string.IsNullOrWhiteSpace(discipleLessonsId) && FeeDataList != null
       && string.Equals(LoadedPresentDiscipleLessonsId, discipleLessonsId, StringComparison.OrdinalIgnoreCase);
public void SetupPresentFeeList(String DiscipleLessonsId)                 // :132  ← 只用 id 載入、不驗身分
    => FeeDataList = m_FeeDownUpLoader.GetPresentFeeList(DiscipleLessonsId, …);
```

`InMemoryContext.FeeList` 以 **Session ID 為鍵**快取（`Models/InMemoryDataContextSmallGroup.cs:978-982`，key = `GetCurrentSessionId() + "_FeeList"`，30 分鐘）。

### 3.2 風險分析

- **跨 session（A 登出、B 另開瀏覽器登入）→ 目前安全**：FeeList 以 SessionId 為鍵，B 拿到的是不同實例。✅
- **同一 session 內換登入身分（2026-06-18 報告明列的「LINE 與帳密交錯登入 / 同瀏覽器切換帳號」）→ 高風險**：
  1. `IsPresentFeeListLoadedFor(discipleLessonsId)` **完全沒有**登入綁定 —— 只要該 session 之前載過同一 `discipleLessonsId`，就直接重用 `FeeDataList`，**跳過** `SetupPresentFeeList` → 跳過其內 `GetPresentFeeList` 可能含的每請求授權。
  2. `EnsureLessonListLoaded` 的 `account/password` **取自 `FeeList.m_Account` 自身欄位**，於是 `IsLessonListLoadedFor` 內的 `IsSameLogin(m_Account, m_Account)` 形同**自我比較、恆真** → 課程清單的「換登入即清空」防線（`SetupLessonList` 內 `if(!IsSameLogin) ClearUserScopedFeeData()`，`FeeList.cs:108-120,214-224`）**被架空**：因為比較對象不是「當前 session 真正登入者」，而是「FeeList 既存值」。

  也就是說，**安全與否完全押在兩個未證實的前提**：(i) 每次登入都會重生 Session ID（使 FeeList 變新實例）；(ii) 有別的流程在這些 `Ensure*` 之前，把 `FeeList.m_Account/m_Password` 正確同步成「當前 session 登入者」。**這兩點本稽核都尚未在程式中確認成立**，且第 (ii) 點即使成立，也會讓 `IsSameLogin` 的清空判斷失效（比較的是已被覆寫的同一值）。

- **命中 2026-06-18 報告自身的硬性規則**：第 1 條「不得以 `discipleLessonsId` 單一欄位作 cache key」、第 2 條「cache key 必須含 sessionId+userId+loginType+…」、第 3 條「batch/lazy 不可信任前端 id，須以當前 session 重新計算可存取範圍取交集」。目前 `IsPresentFeeListLoadedFor` 正是「只用 `discipleLessonsId`」。

### 3.3 結論與建議（細節見補強計畫 Task 1）

**這是使用者第③要求（Session Leakage 零容忍）下最該優先處理的項目。** 在「A/B + 交錯登入」回歸測試證明安全之前：

- **立即（保底）**：把 `Ensure*Loaded` 的重用判斷**還原為每次無條件重載**，或以「當前 session 真正登入身分」為條件（而非 `FeeList.m_Account` 自身）。寧可慢、不可洩漏。
- **正式（再導入優化）**：依 2026-06-18 報告，重用/快取鍵改為 `sessionId + userId + accountOrLineHash + loginType + discipleLessonsId + permissionScope + version`，並在每次（含命中）對 `discipleLessonsId` 以當前 session 重新授權；以 A/B 交錯登入回歸為上線閘門。

> 嚴格說此項屬「P2 業務優化」而非「剖析子系統」，但因 Codex 一併實作、且直接觸及最高優先的安全紅線，故列為本報告頭號發現。
