## 1. 背景

「小組回報」「會友資訊」網格的大頭照轉圈過久。以暫時性計時碼（`[BatchImg-Timing]`）量測正式路徑後確認：

```
修前：ep=MemberInfo total=6020ms pre=5907ms conn=0ms crm=68ms img=42ms | req=50 photo=19
修後：ep=MemberInfo total=226ms  pre=87ms   conn=0ms crm=96ms img=41ms | req=50 photo=19
```

**真兇不是照片**：CRM 查詢 68ms、影像解碼 42ms 都很快。98% 的時間在 `pre`（授權檢查迴圈）。

**根因**：授權閘門 `CanViewContact` → `IsCurrentContact()` 對**每一個聯絡人各打一支 CRM `Retrieve`**（查 `statecode`/`customertypecode` 判斷在籍）。一頁 50 人 = 50 次 CRM 來回 = 5.9 秒。即使照片都在快取也照樣慢，因為授權查詢與照片快取無關、每次都跑。

> 小組回報走 `/Personal/GetContactImagesBatch`，**沒有**逐人授權閘門，本來就快（~400ms），未修改其邏輯。

## 3. 稽核標準

2026-01-13 Session-Leakage 的三大根因：① 中間層快取誤判、② DI 生命週期錯誤、③ 靜態變數污染。共通本質：**把「使用者專屬資料」放進「跨使用者的共用狀態」**，導致 A 的資料被 B 看到。

因此稽核唯一標準：**有沒有把任何跟「當前登入者」綁定的東西，放進會被別人讀到的地方（IMemoryCache／static／instance 跨請求重用）？授權是否仍以「當前使用者」每請求重新評估？**

---

## 4. 逐項稽核

| 改動 | 是否碰共用/靜態狀態 | 授權是否每請求以當前使用者重算 | 結論 |
|------|------|------|------|
| **`CanViewContactsBatch`** | 全部為 method 內 **local 變數**（`allowed`/`shepherdAllowed`/`validGuids`/`contactsById`）；**無 static、無 instance 欄位、不寫 IMemoryCache、不寫 session** | 是 —— `GetAccess()` 讀 session、`GetShepherdContactIds()` 讀當前 session 的 `InMemoryContext`，每次呼叫重算；**授權結果不快取**（回傳 local `HashSet`） | ✅ 安全 |
| **批次端點 pre-loop** | `parsedGuids`/`allowedSet` 皆 local；照片快取 key 仍為 `member-info-contact-image-thumb:{contactId}:{size}`（**不含使用者身分**，且此段未改） | **先授權（`allowedSet.Contains(guid)`）才讀照片快取**，順序未繞過 | ✅ 安全 |
| **`TryGetClosedCustomerTypeValue` → 共用快取** | 唯一新增的快取互動。但快取內容是 **CRM schema metadata**（「結案」選項對應的整數值），**全使用者相同、非個資**，key 為 entity+attribute（Phase 5.1 已認定此類 metadata 快取安全） | 不涉及使用者 | ✅ 安全 |
| **`[BatchImg-Timing]` 計時碼** | local `Stopwatch` + `Debug.WriteLine`，內容僅「數量/毫秒/位元組」，**無 contactId、無使用者、無照片內容**；`[Conditional("DEBUG")]`，Release 已驗證剝除 | — | ✅ 安全 |

**關於共用 CRM 連線**：`CanViewContactsBatch` 使用的 `ToolUtility.m_Crm2011OrganizationService` 是**共用服務帳號連線**，但原本逐筆版的 `IsCurrentContact` 就在用同一個。我未新增任何跨使用者共享，只是把同一個連線「查 N 次」改成「查 1 次」。它回傳的是聯絡人自身欄位（非使用者專屬），授權決策仍由 per-session 的 `GetAccess`/`GetShepherdContactIds` 把關。

---

## 5. 防洩漏的關鍵不變式

> **授權名單於每個請求，以「當前登入者的 session 上下文」重新計算，且從不被快取。**

`allowedSet` 是每次請求現算的 local。B 的請求只會算出 B 自己的可見名單（來自 B 的 session／牧養名單），結構上不可能取得 A 的結果。照片快取存的是「以 contactId 為 key 的非個資縮圖位元組」，且**一律在授權通過後才讀取**。

## 6. 建置驗證

- Debug 建置：0 警告 0 錯誤；`[BatchImg-Timing]` 字串存在於 `bin\Debug` DLL（診斷可用）。
- Release 建置：0 警告 0 錯誤；`[BatchImg-Timing]` 字串**不存在**於 `bin\Release` DLL（已剝除，正式機不會寫入 `Logs\Trace.log`）。
- 驗證方法：直接掃描編譯後 DLL 的 UTF-16 字串堆，以完整字串（非短 CJK 片段）比對，避免二進位亂掃誤判。

## 7. 確認方式與限制（誠實聲明）

- 本報告以**靜態程式碼稽核 + 結構性論證**確認，**尚未**執行雙裝置 Wi-Fi 交叉登入實測（即 `Session_Bleeding_Fix_TODO.md` 的 Phase 7.1）。
- 但本次改動**完全未觸及**造成 2026-01-13 事故的面向：session 寫入、DI 註冊、靜態欄位、跨使用者快取個資。
- `IdentityAuditMiddleware`（偵測同 Session ID 不同 User）仍在線運作，未受影響。

### 建議的執行期驗證（Phase 7.1）
1. 兩台裝置連同一 Wi-Fi；裝置 A 登入帳號 A、裝置 B 登入帳號 B。
2. 各自開「會友資訊」頁，往下捲動載入大頭照。
3. 交替重新整理，核對：
   - 看到的會友名單是否**各自正確**（A 看到 A 該看的、B 看到 B 該看的）。
   - 大頭照是否對應到正確的人。
   - Log 中 `IdentityAuditMiddleware` 是否出現「同 IP 短時間切換 User」「同 Session 不同 User」等異常。

## 8. 後續

- `[BatchImg-Timing]` 計時碼為暫時性診斷碼（Release 已自動剝除）。效能確認穩定後可移除。
- 附帶觀察（與本次無關，另案評估）：`/Personal/GetContactImagesBatch` 無逐人 `CanViewContact` 閘門，接受傳入 contactId 即回傳頭像；屬低敏感（僅頭像），但可單獨評估是否補授權。
