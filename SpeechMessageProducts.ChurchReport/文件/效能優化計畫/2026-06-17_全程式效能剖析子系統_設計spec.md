## 1. 背景與動機

2026-06-16「會友資訊」照片轉圈過久，事後以暫時性計時碼證實真兇是**授權閘門的 N+1 CRM 查詢**(50 人=50 次 Retrieve=5.9 秒)，而非照片本身。教訓：**不量測就猜，會猜錯**(當時誤判為「拉原圖太大」)。

本子系統把當時的「臨時手動計時」升級為**常駐、集中、Debug-only** 的剖析機制，涵蓋整個程式，讓任何「慢」與「N+1」都能一眼從 log 看出，而不必每次手動埋點。

## 2. 核心安全原則(最高優先)

2026-01-13 的 Session-Leakage(P0) 根因 = **把使用者專屬資料放進跨使用者共用狀態**(中間層快取/DI 生命週期/靜態變數)。本子系統以下列鐵則確保不重蹈覆轍：

1. **每請求計時狀態只存放於 `HttpContext.Items`** —— 每個請求一份、請求結束即回收，**絕不使用 static 欄位、singleton 內的可變狀態、或任何共用快取**保存請求計時資料。
2. **計時內容只含非個資**：數字(毫秒/次數) + entity 邏輯名(如 `contact`) + 操作名(如 `RetrieveMultiple`) + **路由樣板**(如 `/MemberInfo/Detail/{id}`，**非**含實際 ID 的原始路徑)。**不含任何記錄 ID、欄位值、使用者身分、照片或其他內容**。
3. **全部 Debug-only**：以 `#if DEBUG` 與 `[Conditional("DEBUG")]`(`Debug.WriteLine`) 確保 Release 組件中相關呼叫與字串被編譯器整段移除(已於 2026-06-17 實證 `Debug.WriteLine` 在 Release 被剝除)。
4. **不改動既有安全關鍵程式**：不修改已稽核的 `StrictNoCacheFilter`、`IdentityAuditMiddleware`、`PerformanceMonitoringMiddleware`、Session 設定。剖析以**新增、獨立**元件實作。
5. **裝飾器無跨請求狀態**：CRM 計時裝飾器只持有「內層服務 + `IHttpContextAccessor`」，每次呼叫寫入的是「當前請求(由 `IHttpContextAccessor` 解析)的 RequestProfiler」，本身不累積任何請求資料。
6. **Runtime 開關(雙重保險)**：除 `#if DEBUG` 外，另設定 `Profiling:Enabled`(預設 `false`)。剖析僅在「Debug 建置 **且** 設定開啟」時作用。**正式機部署模式不確定/混合**，故採此雙重保險：即使正式機誤以 Debug 部署，未開設定就完全不剖析、不輸出、近乎零開銷。

> 啟動(boot)階段在「沒有任何使用者/session/請求」時執行，本質零 Session-Leakage 風險。

## 3. 架構總覽

涵蓋範圍：**應用程式啟動 → 每個 web 請求(action 時間 + CRM 次數/耗時 + N+1 偵測)**。

| # | 元件 | 型態 | 職責 | 放置位置 |
|---|------|------|------|----------|
| 1 | `RequestProfiler` | 每請求物件(存 `HttpContext.Items`) | 收集單一請求的計時資料 | 新檔 `Diagnostics/Profiling/RequestProfiler.cs` |
| 2 | `PerfTimingActionFilter` | 全域 MVC `IActionFilter` | 量每支 controller action 執行時間 | 新檔 `Filters/PerfTimingActionFilter.cs` |
| 3 | `TimedOrganizationService` | `IOrganizationService` 裝飾器 | 數/計時每次 CRM 呼叫，寫入當前請求 profiler | 新檔 `Diagnostics/Profiling/TimedOrganizationService.cs` |
| 4 | `PerfProfilingMiddleware` | 獨立 Debug-only 中間件 | 請求起建立 profiler、請求結束輸出 `[Perf]` | 新檔 `Middleware/PerfProfilingMiddleware.cs` |
| 5 | `StartupProfiler` | 靜態無狀態計時輔助 | 量啟動各階段，輸出 `[Perf-Startup]` | 新檔 `Diagnostics/Profiling/StartupProfiler.cs` |

## 4. 元件詳細設計

### 4.1 `RequestProfiler`(元件 1)
- **狀態**(皆為本物件實例欄位，不共用)：
  - `Stopwatch` 全程計時(由中間件啟動)。
  - `long actionElapsedMs`(由 Filter 寫入)。
  - CRM 統計：`int crmCount`、`long crmTotalMs`、最慢單次 `(string entity, string op, long ms)`、以及「超過門檻的慢呼叫清單」`List<(entity, op, ms)>`(僅存 entity/op/ms，無 ID)。
- **執行緒**：單一請求的非同步流程內可能有並行 CRM 呼叫，計數累加以 `Interlocked` 或簡單鎖保護(同一 profiler 內)。
- **介面**：`RecordCrmCall(string entity, string op, long ms)`、`SetActionElapsed(long ms)`、`BuildSummaryLine()`、`BuildEscalationLines(thresholds)`。
- **存取鍵**：`HttpContext.Items["__PerfProfiler"]`。

### 4.2 `PerfTimingActionFilter`(元件 2)
- 實作 `IActionFilter`：`OnActionExecuting` 起跑 stopwatch；`OnActionExecuted` 計算 action 毫秒，寫入當前請求的 `RequestProfiler.SetActionElapsed(...)`。
- **註冊**：`Startup.cs` 的 `.AddMvc(options => …)` 內，以 `#if DEBUG options.Filters.Add<PerfTimingActionFilter>(); #endif`。Release 不註冊。

### 4.3 `TimedOrganizationService`(元件 3)
- 實作 `IOrganizationService` 全部方法(`Create/Retrieve/RetrieveMultiple/Update/Delete/Execute/Associate/Disassociate`)，每個方法：起 stopwatch → 呼叫內層 → 計時 → 取當前請求 profiler(`_httpContextAccessor.HttpContext?.Items[...]`，null 則略過) → `RecordCrmCall(entity, op, ms)`。
- **相依**：內層 `IOrganizationService` + `IHttpContextAccessor`(已註冊，Session_Bleeding 稽核列為安全)。
- **套用點(兩條 CRM 取得路徑，皆 `#if DEBUG`)**：
  1. 連線池路徑：`BaseChurchController.GetConnection()` 回傳前以裝飾器包住。
     - ⚠️ **`ReleaseConnection()` 必須解包**，把「內層真實連線」歸還連線池(池追蹤的是真實連線，不能把裝飾器還回去)。裝飾器需提供 `Inner` 屬性供解包。
  2. 靜態服務路徑：`ToolUtility.m_Crm2011OrganizationService` 的賦值點以裝飾器包一次(共用一個裝飾器實例，靠 `IHttpContextAccessor` 寫入各自請求 profiler，per-request 安全)。
- **Release**：兩處皆回傳未包裝的原始服務 → 與現行完全相同、零額外開銷。

### 4.4 `PerfProfilingMiddleware`(元件 4)
- 管線**較前段**(在 `UseRouting`/MVC 之前，能涵蓋整個請求)註冊，但**僅 `#if DEBUG`**。
- `Invoke`：建立 `RequestProfiler` 啟動全程 stopwatch → 放入 `HttpContext.Items` → `await _next(context)` → 結束時輸出 `[Perf]` 摘要行；若觸發門檻則加印 `[Perf-N+1]`/`[Perf-Slow]` 明細行。
- 輸出一律 `Debug.WriteLine`(Release 剝除)。
- **不修改** 既有 `PerformanceMonitoringMiddleware`(維持其已稽核狀態)。

### 4.5 `StartupProfiler`(元件 5)
- API：`using (StartupProfiler.Phase("ConfigureServices")) { … }` —— `Phase` 回傳一個 `IDisposable`，內含自己的 label + Stopwatch，Dispose 時 `Debug.WriteLine($"[Perf-Startup] phase={label} ms={ms}")`。
- **無共用可變狀態**(不做跨 Phase 累積)，僅在 `Startup.cs` 啟動流程使用。
- **包覆階段**：`ConfigureServices`、`Configure`(中間件管線)、**CRM 連線池初始化/預熱**(冷啟動最大宗，每連線一次 Dataverse OAuth)、任何 metadata/資料預載。

## 5. 資料流

```
[啟動] Program/Startup → StartupProfiler.Phase(...) 各階段 → [Perf-Startup] 行

[請求] 進入 → PerfProfilingMiddleware 建 RequestProfiler 入 HttpContext.Items
        → (路由/Filter) PerfTimingActionFilter 計 action 時間 → 寫入 profiler
        → action 內每次 CRM 呼叫經 TimedOrganizationService → profiler.RecordCrmCall
        → 回到 middleware → 輸出 [Perf] 摘要 (+ 視門檻加印明細)
        → 請求結束，HttpContext.Items(含 profiler) 隨之回收
```

## 6. 輸出格式(Trace.log，Debug-only)

**每請求摘要(一律一行)**
```
[Perf] path=/MemberInfo/GetContactImagesBatch total=226ms action=210ms crm{n=2,ms=160} gap=50ms slowest=contact.RetrieveMultiple:96ms
```

**疑似 N+1(同請求 CRM 次數 > 門檻)加印**
```
[Perf-N+1] path=/MemberInfo/Xxx crm.n=51 詳列: contact.Retrieve ×50 (Σ5740ms), annotation.RetrieveMultiple ×1 (68ms)
```

**單次慢呼叫(> 門檻)加印**
```
[Perf-Slow] path=/Xxx contact.RetrieveMultiple 1240ms
```

**未歸因時間過大(action − 已計時 CRM > 門檻)加印 — 用來揪「盲區」(proxy CRM 路徑或 CPU/記憶體工作)**
```
[Perf-Gap] path=/Xxx action=900ms crm.ms=120 gap=780ms (未歸因:可能 m_OrganizationService proxy 路徑或非 CRM 運算)
```

**啟動階段**
```
[Perf-Startup] phase=ConnectionPoolWarmup ms=2300
```

### 預設門檻(可調)
| 門檻 | 預設值 | 用途 |
|------|--------|------|
| N+1 偵測 | 同請求 CRM 次數 > **10** | 加印 `[Perf-N+1]` |
| 單次慢呼叫 | > **100ms** | 加印 `[Perf-Slow]` 並列入慢呼叫清單 |
| 未歸因時間(gap) | action − 已計時 CRM > **150ms** | 加印 `[Perf-Gap]`，標記盲區(proxy 路徑/CPU 工作) |
| (參考)慢請求 | total > **500ms** | 既有 `PerformanceMonitoringMiddleware` 已處理，不重複 |

> **精度**：CRM 時間以 `Stopwatch` 的 **ticks** 累計、輸出時才換算毫秒，避免大量 <1ms 呼叫被各自捨入為 0 而低報(2026-06-16 照片計時的教訓)。

## 7. Release 無痕的保證機制
- 中間件註冊、Filter 註冊、CRM 裝飾器包裝：全部 `#if DEBUG`。
- 所有輸出：`System.Diagnostics.Debug.WriteLine`(`[Conditional("DEBUG")]`)。
- csproj 已確認 Release 僅定義 `RELEASE`(不含 `DEBUG`)。
- **驗收**：Release 建置後掃描 `bin\Release\...\ChurchReport.dll`，確認 `[Perf`、`[Perf-Startup` 等字串**不存在**(比照 2026-06-17 對 `[BatchImg-Timing]` 的驗證法)。

## 8. 範圍與非目標
- **範圍**：應用程式啟動 + 所有經 MVC 管線的 web 請求(controller actions)。
- **非目標(本期不做)**：背景工作(LINE webhook 處理、`LineMessagingProcessor`、排程任務)的細部計時 —— 因使用者「操作功能」走的是 web 請求；日後可另案以相同 `RequestProfiler`/`StartupProfiler` 模式延伸。
- **已知盲區(以 `[Perf-Gap]` 偵測，非靜默)**：CRM 計時裝飾器只能包 `IOrganizationService`(即 `m_Crm2011OrganizationService`)。資料層另有具型別欄位 `m_OrganizationService`(`OrganizationServiceProxy`，`WebServiceConnector\` 多處使用)**無法直接被 `IOrganizationService` 裝飾器包裝**。此路徑的 CRM 時間會落入「未歸因時間(gap)」，由 `[Perf-Gap]` 標記，引導對該端點手動深入。規劃階段先確認此 proxy 路徑是否仍活躍(`文件\升級ToolUtility\` 顯示正自舊 proxy 遷移)。
- **靜態檔**：剖析中間件註冊於 `UseStaticFiles` **之後**，避免每個 css/js/圖都印 `[Perf]` 灌爆 log。
- **非目標**：自動修瓶頸。本子系統只負責**量測與定位**；每個瓶頸的修正各自獨立評估、各自確認 session 安全後再實作。

## 9. 工作流程(量測 → 找瓶頸 → 修)
1. 實作本子系統(Debug-only)，建置驗證 Release 無痕。
2. 使用者在 **Debug 模式**操作所有功能。
3. 由 `Trace.log` 的 `[Perf]`/`[Perf-N+1]`/`[Perf-Gap]`/`[Perf-Startup]` 行，**以分析腳本 `Tools\parse-perf-log.ps1` 自動彙總**(依 total / CRM 次數 / gap / 端點分組排序)，列出最慢項、N+1 與盲區端點，避免人工掃描數千行。
4. **逐一瓶頸**：系統化除錯找根因 → 提出「session 安全」修法 → 使用者確認 → 實作 → 驗證(計時數字下降)。
5. 重複 3–4 直到整體順暢。

## 10. 規劃/實作階段待確認事項
1. **靜態 `ToolUtility.m_Crm2011OrganizationService` 的賦值點**位置與可包裝性(確保兩條 CRM 路徑都被計時涵蓋；否則會有盲區)。
2. **`ReleaseConnection` 解包**邏輯(歸還內層真實連線給池)。

## 11. 風險與緩解
| 風險 | 緩解 |
|------|------|
| `m_OrganizationService`(proxy)路徑無法被 `IOrganizationService` 裝飾器包裝 → 計時盲區 | 以 `[Perf-Gap]`(action − 已計時 CRM)偵測未歸因時間，引導手動深入；規劃階段先確認 proxy 是否仍活躍 |
| 正式機若以 Debug 部署 → 剖析誤在正式機跑 | `Profiling:Enabled` 預設 `false`，需明確開啟才作用(第 2 節 #6)；於 `#if DEBUG` 之上的雙重保險 |
| `ReleaseConnection` 未解包 → 連線池損壞 | 裝飾器提供 `Inner`；`ReleaseConnection` 一律解包後歸還；多次操作後驗證池健康 |
| ToolUtility 共用欄位執行期改寫競態 → 雙重包裝/計數膨脹 | 依生命週期：singleton 啟動時包一次；否則冪等檢查 + 鎖 |
| 大量 <1ms CRM 呼叫被捨入為 0 → CRM 時間低報 | 以 ticks 累計，輸出才換 ms |
| 靜態檔/資產請求灌爆 log | 中間件註冊於 `UseStaticFiles` 之後 |
| Release 誤輸出 | 以 DLL 字串掃描驗收(第 7 節) |
| 計時本身拖慢 | 僅「Debug 且設定開啟」才作用；`Stopwatch`/`Items` 查找為奈秒~微秒級 |
| 不慎把使用者資料寫入 profiler | 只接受 entity/op/ms + 路由樣板；程式碼審查 + 第 2 節為準則 |
