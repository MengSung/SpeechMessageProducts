# 會友細節頁面：捲動與照片問題修復報告

> 對象檔案：
> - `Views/MemberInfo/MemberInfoGrid.cshtml`（彈窗外殼、捲動控制、頭像範本）
> - `Views/MemberInfo/_MemberDetailPopup.cshtml`（細節內容、聚會/裝備子網格）
>
> 執行環境：ASP.NET Core (net10.0) + DevExtreme 21.2.7，於 LINE 內建瀏覽器(LIFF / WKWebView) 與手機 Safari/Chrome 上使用。

---

## 一、原始三大症狀

1. **照片要滑動才出現**：會友清單頭像、會友細節大頭照常常要點一下或滑動後才顯示。
2. **細節頁無法順暢上下滑**：一進入就停在頁面中間（看不到大頭照），手指滑動會「彈回中間」，且很卡、甚至沒反應；**只有壓在網格上才勉強能捲，壓在非網格區域完全沒反應**。
3. **聚會紀錄網格沒有左右卷軸**：欄位超出螢幕卻無法左右滑動查看右側資料。

---

## 二、真正的根本原因

### 1) 部署層（前幾輪「改了卻毫無變化」的主因）
本專案是 **net10.0 且未引用 `RazorRuntimeCompilation`**，所有 `.cshtml` 會在編譯時被打包進 `ChurchReport.dll`。因此**只改 `.cshtml`、沒有重新 publish／沒覆蓋到伺服器上的 DLL／沒重啟 IIS／或被 WebView 快取**，畫面都不會變 —— 跑的仍是舊版視圖。

### 2) 照片
- 清單頭像用了 `loading="lazy"`，而照片欄是 `Fixed(true)`，DevExtreme 會把欄位範本渲染在「絕對定位的固定欄覆蓋層」(`.dx-datagrid-content-fixed`)。瀏覽器原生 lazy 的 IntersectionObserver 在初次繪製時偵測不到絕對定位容器內的圖片 → 必須滑動才載入。
- 細節大頭照原本抓 `size=0`（Dataverse `entityimage` 原始檔，可能數 MB），卻只顯示成約 104px → 在手機解碼大圖會卡住主執行緒。

### 3) 捲動（最核心）
- 彈窗內形成「**巢狀捲動容器**」：外層要垂直捲、內層 DataGrid 要水平捲。在 iOS / LINE WebView 上，原生捲動的手勢路由不可靠，造成**非網格區的觸控不被外層接手**、整頁滑不動。
- DataGrid 預設會在初始化／資料載入後，把可捲動的父層 **scroll-into-view 到焦點列／網格本身** → 彈窗被往下拉到「頁面中間」，且使用者一碰又被拉回。

---

## 三、最終解法為何能正常運作（逐項對應）

### A. 照片第一時間就看得到
- **清單頭像 `loading="eager"`**（`MemberInfoGrid.cshtml` 的 `memberInfoAvatarCellTemplate`）：固定欄覆蓋層 + lazy 偵測不到 → 改 eager，網格初始化後立即載入，不需點擊或滑動。
- **細節大頭照改 `size=256` 縮圖 + `loading="eager" decoding="async"`**（`_MemberDetailPopup.cshtml`）：體積小、解碼快，初次繪製即顯示，也不再拖慢捲動。
- 另保留批次預載 (`GetContactImagesBatch`) 作為快取最佳化。

### B. 整頁上下滑順暢、任何區域都能滑、且不再跳到中間
這是 Codex 這次的關鍵重構 —— **不再依賴瀏覽器的原生垂直捲動，改由 JavaScript 自己掌控垂直捲動**，徹底繞開 iOS/WebView 的巢狀捲動手勢問題。四個機制環環相扣：

1. **單一捲動容器，並關閉瀏覽器原生垂直手勢**
   - 彈窗內容只保留一個原生捲動層 `.member-info-detail-scroll`（`height:100%; overflow-y:auto`），不再額外包 `dxScrollView`。
   - 在 `.member-info-detail-popup-content`、`.member-info-detail-scroll`、`.member-info-detail-scroll-inner` 上一律設 **`touch-action: pan-x`**：等於告訴瀏覽器「這裡只做水平原生手勢」，把垂直手勢的主導權**收回來交給 JS**，避免和內層網格互搶。

2. **自製 JS 垂直捲動（在 capture 階段攔截手勢）**
   - `memberInfoBindDetailTouchHandling()` 在捲動容器上以 **capture 階段**監聽 `pointer`/`touch` 事件，依手勢鎖定軸向（`lockedAxis`）：
     - **垂直為主** → 直接設定 `scrollHost.scrollTop` 並 `preventDefault()`。因此**不論手指壓在照片、欄位或網格上，垂直滑動都能捲動整頁**（這正是「只有壓網格才能捲、非網格區沒反應」的解法）。
     - **水平為主** → JS 不處理，讓事件繼續往下傳給網格做原生水平捲動。
   - 結果：外層負責垂直、內層負責水平，各司其職、不再互搶手勢，滑動順暢自然。

3. **關閉 DataGrid 的「自動捲動到焦點列」**
   - 子網格設定 `focusStateEnabled:false`、`focusedRowEnabled:false`、`hoverStateEnabled:false`、`autoNavigateToFocusedRow:false`。
   - 這直接消除了 DataGrid 初始化／載入時把父層 scroll-into-view 的行為 → **不再被拉到頁面中間**。

4. **開啟時先停在頂端（先看到大頭照）**
   - `memberInfoResetDetailScrollSoon()` 會在多個時間點（rAF、40/120/260/520/900/1400/2100/2800ms）把捲動歸零，**直到使用者第一次觸碰**（`memberInfoDetailUserInteracted`）才停止，避免和非同步載入賽跑。
   - 搭配 `history.scrollRestoration='manual'`、內容最上方的頂端錨點 `.member-info-detail-top-anchor`，以及照片/網格載入完成後的再次校正（`memberInfoDetailRefreshScroll`），確保一開啟就停在頂端。
   - 關閉彈窗時（`memberInfoDetailPopupHidden`）清掉觸控監聽並清空內容，避免跨次開啟殘留；開啟以 `memberInfoDetailOpenToken` 防止前一次的 AJAX 回應蓋掉新內容。

### C. 聚會紀錄網格一定有左右卷軸、可左右滑
- 手機端網格 `scrolling.useNative:true`、`showScrollbar:'always'`；欄位給**固定像素寬度**（手機版總寬約 712px > 螢幕）→ **必定水平溢出**而出現水平捲動（因此 `columnAutoWidth` 與否非關鍵）。
- 網格列區 `.dx-datagrid-rowsview .dx-scrollable-container` 設為 **嚴格單軸水平**：`overflow-x:scroll; overflow-y:hidden`，並 `touch-action:pan-x pan-y` → 水平滑動捲網格、垂直手勢交給外層 JS 捲動。
- 自訂 `::-webkit-scrollbar`（高度 12px、藍色 thumb）→ 底部左右卷軸在 Chromium/Android/LINE-Android **常駐可見**（iOS 為滑動時浮現）。

## 四、部署注意事項（避免再次「改了卻沒變化」）

1. 改任何 `.cshtml`/`.cs` 後，**必須重新 publish**（`DotNetPublish-Release-MaxThroughput.bat` 或對應腳本）。
2. 將輸出**覆蓋**到正式站台，務必覆蓋掉舊的 `ChurchReport.dll`（若覆蓋時檔案被鎖 → 先在 IIS **停止應用程式集區**，覆蓋後再啟動）。
3. **重啟 IIS 應用程式集區**。
4. 手機端**清掉 LINE/瀏覽器快取**再測（或先用 Safari/Chrome 排除 LINE 內建快取）。
5. 驗證上線：之前曾在頁面頂端加綠色版本標記，看得到才代表新版生效（現已移除）。

> 補充：DevTools Console 另有一批 `…/lib/devextreme/js/cldr…`、`globalize…`、`jszip…`、`vectormap…` 的 **404 / MIME 錯誤**。那是 `~/lib/devextreme/...` 這條路徑的檔案沒部署到伺服器（與主要的 `~/js/devextreme/dx.all.js` 不同路徑），屬本地化／匯出等附加功能，**與捲動無關**，建議另行清理以減少噪音。

---

## 五、為什麼前面修很多次都沒效

- **大部分是「新版沒真的上線」**：DLL 沒覆蓋、沒重啟、或被快取，使用者一直在測舊版（連「照片改縮圖」這種一定看得出的改動都沒變化，即為明證）。
- **即使上線，早期版本仍依賴 iOS 原生巢狀捲動**，受 WebView 手勢路由限制而不穩定。直到改成本報告第三節 B 的「**JS 自控垂直捲動 + 關閉網格自動捲動 + 單軸水平**」組合，才真正在 iOS/LINE 上穩定運作。
