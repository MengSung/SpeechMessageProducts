下面是一份針對將 ToolUtility 專案從 .NET Framework 4.6.2 升級到 .NET 10 的「升級計畫說明」，包含要修改的項目、如何遵守 Linus-style 原則（簡潔、可維護、小步快送、明確回滾路徑）以及如何善用設計模式以降低風險與提升可測試性。內容精簡、可直接套用到工作區檔案（以 ToolUtility\ToolUtilityClass.cs 為主）。
一、總體步驟（高階）
?	建立分支：建立 upgrade/toolutility-net10 分支，小步驟、多次 commit。
?	先做分析：在分支上做依賴清單（WCF、OrganizationServiceProxy、System.ServiceModel、big5 stream、Microsoft.Xrm.Sdk 等）。
?	建立 CI：在分支上新增自動化 build（dotnet build、單元測試）與靜態分析。
?	新增目標專案：建立或修改 ToolUtility\ToolUtility.csproj 為 SDK-style、<TargetFramework>net10.0</TargetFramework>。
?	逐步替換：先改 package、再改程式碼，採「可回滾的小 PR」策略。
?	驗證與回滾：每個階段都做 build/run 測試，若失敗立即回滾到前一個穩定 commit。
二、具體修改項目（檔案/程式碼層）
1.	專案檔案（ToolUtility\ToolUtility.csproj）
?	換成 SDK-style 並設定 TargetFramework 為 net10.0。
?	移除不支援的組件引用（直接 .dll 引用改成 NuGet package）。
?	加入必要 NuGet 套件（範例）：Microsoft.CrmSdk.CoreAssemblies（如需兼容）、PowerPlatform.Dataverse.Client（workspace 已含）、Microsoft.Extensions.*（DI/Logging/Configuration）。
2.	移除/替換 WCF 與 OrganizationServiceProxy 用法
?	OrganizationServiceProxy 與 WCF 在 .NET Core / .NET 10 上不建議使用。用 ServiceClient（Dataverse/PowerPlatform 客戶端）或直接使用 IOrganizationService 實作的現代客戶端。
?	建立一個 ICrmClient 抽象（介面），實作兩種 Adapter：
?	CrmOnPremAdapter（若仍需支援舊 on-prem；用 modern libraries 或 Web API）
?	DataverseServiceClientAdapter（使用 ServiceClient，支援 OAuth）
?	將 ToolUtilityClass 內所有直接 m_OrganizationService / OrganizationServiceProxy 調用改由 ICrmClient 提供：Retrieve, RetrieveMultiple, Create, Update, Delete 等。
3.	調整驗證/認證流程
?	移除直接使用 NetworkCredential / ClientCredentials 進行 Windows-auth 的硬編碼（例如 GetClientCredentials），改用：
?	環境變數 / appsettings.json / 使用者祕密儲存（secret manager）注入設定。
?	OAuth2 / client id+secret / managed identity（視 CRM/Dataverse 環境而定）。
?	實作 ICrmCredentialProvider，統一提供權杖建立流程。
4.	移除/替換同步阻塞呼叫，改為支援非同步
?	將可改為 async 的 API 改寫為 async Task（例如 CreateEntityAsync 已有，補齊其它需求）。
?	使用 CancellationToken 作為多數 I/O 呼叫的參數。
5.	日誌與追蹤
?	將自訂的 BugslayerTextWriterTraceListener 保留或改造，但把日誌整合進 Microsoft.Extensions.Logging.ILogger<T>。
?	移除硬編碼檔案路徑（D:\除錯追蹤\），改用可配置的日誌目錄或平台日誌（Console / file provider）。
?	檔案編碼：不要硬編 Encoding.GetEncoding("big5")，改為 UTF-8 或可配置。
6.	結構與可注入化
?	把ToolUtilityClass 拆成更小的服務（單一職責）或把其方法拆入多個專責類別（e.g. ContactRepository, ListRepository, AttachmentService）。
?	建立 IToolUtility 介面，並把 ToolUtilityClass 註冊成 DI 服務（AddScoped<IToolUtility, ToolUtilityClass>()）。這利於單元測試與替換實作。
7.	測試
?	新增單元與整合測試（mock ICrmClient），保證主要邏輯正常。
?	針對外部 API（Dataverse）使用契約測試或整合測試環境。
8.	相容性維護（回滾）
?	若短期內需要同時支援 .NET Framework 與 .NET 10，可考慮用 multi-targeting 或在短期內維持舊 API 的 Adapter 層，逐步切換上游消費者到新介面。
三、如何遵守 Linus（Linus Torvalds）風格原則（實務化）
?	小而頻繁的變更：每一步改動做小 commit、附上清楚的說明、保持變更可讀性。
?	簡潔優先：避免過度抽象；當實作足夠簡單且可測試時就停止再抽象。
?	可回滾：每階段都能 build/run；若失敗可回到上一個明確 commit。
?	以事實為準（pragmatism）：優先能通過測試的實用做法，而非理想化設計（例如短期保留 adapter 以保持系統運作）。
?	清楚的 API 與介面：公開介面應簡潔、穩定，內部實作可自由演進（保持向後兼容）。
四、設計模式應用（推薦與理由）
?	Adapter（介面轉接器）
?	目的：隔離舊的 OrganizationServiceProxy 與新的 ServiceClient，讓上層呼叫保持不變。
?	實作：ICrmClient + DataverseAdapter、LegacyAdapter。
?	Factory / Factory Method
?	目的：根據設定（CRM_TYPE）建立正確的 ICrmClient 實例（不在業務邏輯中切換具體類別）。
?	Strategy
?	目的：不同查詢/查找策略（例如 FetchXml vs QueryExpression vs WebAPI）封裝成策略，運行時切換。
?	Repository
?	目的：把資料存取（contact、list、fee 等）標準化，方便測試與 mock。
?	Facade
?	目的：暴露高階簡潔 API 給上層（例如：GetContactByLineIdAsync），將複雜 QueryExpression/FetchXml 隱藏在內部。
?	Decorator
?	目的：在 ICrmClient 上加上 logging / retry / tracing（重試策略、指標紀錄）。
?	Template Method（若多個類別有類似的 fetch 流程）
?	目的：把固定流程抽出，子類只實作差異部分（例如建立 Filter）。
?	Null Object
?	目的：減少 null 檢查（回傳空集合而非 null）。
五、相容性與風險控制（必要注意事項）
?	風險：CRM SDK 行為在不同版本可能不同（尤其是認證、序列化、WCF 移除），需實際測試 Dataverse/CRM 連線。
?	測試覆蓋：把頻繁使用的 CRUD 路徑寫入單元/整合測試。
?	秘密與 config：把密碼/憑證移入安全管道（環境變數、Key Vault、user-secrets），避免硬編碼。
?	回滾計畫：每一次大的改動都有對應回滾點與 CI gate。
六、建議的遷移順序（最小破壞）
1.	建立分支與 CI，跑一次現有專案 build。
2.	更新 ToolUtility.csproj → target net10.0（先不改程式碼），嘗試 restore、build，記錄 compile errors。
3.	逐一替換 NuGet（將 .dll 改為 package），解決 compile errors。
4.	新增 ICrmClient 與 DataverseAdapter skeleton，並在 ToolUtilityClass 中注入 ICrmClient（保留舊方法做暫時轉發）。
5.	新增 IToolUtility 介面，把高階方法轉呼叫 ICrmClient。逐步把每一類別方法移至 repository/adapter。
6.	改寫認證流程為可配置的 OAuth（或 service client）。
7.	將同步方法改成 async（分階段）。
8.	把日誌整合 ILogger。
9.	完成測試、整合測試，並在 staging 驗證。
